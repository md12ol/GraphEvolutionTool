## #61 — `set_base_graph`'s node-count check does not catch the failure it was written to prevent

**Status: Decide.** *Either answer amends §8; blocks GitHub #28 / `jsargant_set_base_graph`.*

§8's check 1 exists so that "out-of-range edges are silently dropped" cannot happen, but the check
compares the caller's `num_nodes` argument against `config.network_size` and never inspects the edge
list. A caller who reads `num_nodes` off their config — which is what GitHub #28's own example does,
`refine.set_base_graph(100, edges)` — passes `100 == 100` while every edge touching nodes 100–199 is
dropped by `Graph::set_edge`. Measured on the branch with a since-removed test: `network_size = 8`
and `set_base_graph(8, [(0,1,1), (2,9,1), (3,3,1), (4,5,1)])` returns `Ok(())` and stores two of the
four edges, no error, no warning, and no Python getter to read the graph back. `Graph::set_edge`
itself should not change — the nine opcodes decode vertex indices out of a random payload and are
all no-ops when preconditions fail, so a fallible `set_edge` becomes an error path in all nine; the
asymmetry between engine-generated indices and caller-supplied data is the point. The same argument
already decided the cap check (`decisions.md` 2026-08-12: `set_edge` clamps, so `set_base_graph`
re-checks rather than trusting it). The fix is one condition inside the loop already walking `edges`.

**Q1. Is endpoint validation a fourth check, or check 1 done properly?**
- **(a) Check 1 done properly** — §8's wording already promises it; amend check 1 to say the edge
  list is validated against `num_nodes`, and the code was simply incomplete. *(James's framing —
  he presents both readings but the evidence he gathered argues this one.)*
- **(b) A fourth check** — §8 gains a new numbered check, leaving check 1 as the argument/config
  agreement it literally describes. Costs a renumber; buys a sheet that matches what each check does.
- **(c) Neither — leave it** — accept silent dropping at the FFI boundary. Cheapest now, and
  reproduces the exact failure §8 names.

**Q2. Self-loops — this model has none, so what should `set_base_graph` do with one?**
- **(a) Reject, same as an out-of-range endpoint** — loud, consistent, and a self-loop in caller
  data almost always means the indices are wrong.
- **(b) Drop them, but say so** — documented as intended semantics rather than an accident.
- **(c) Keep dropping silently** — status quo; the thing #61 objects to.
