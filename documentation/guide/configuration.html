Using GET

Configuration reference

Every key GET accepts, what it means, what it defaults to, and what makes it invalid. A config document describes the experiment; the seed, the replicate count and the core cap describe this invocation and are arguments to run instead.

The shape of a config

Four tagged sections plus a handful of top-level keys. Each type field selects a variant, and the rest of that section's keys depend on which variant you chose. 

population_size       = 200
network_size          = 100
max_edge_multiplicity = 1     # 1..=255; 1 = unweighted (the default)
crossover_rate        = 0.9
mutation_rate         = 0.2   # roll 1: is this child mutated at all?
max_mutations         = 1     # roll 2: how many, uniform 1..=max

[evolution]                   # generational | steady_state
type            = "generational"
num_generations = 500
elite_count     = 1

[selection]                   # tournament
type            = "tournament"
tournament_size = 5

[genome]                      # edge_edit | sda
type        = "edge_edit"
gene_length = 256
# [genome.operation_weights]  relative, all default 1.0, 0.0 disables

[fitness]                     # epi_spread | epi_length | epi_prof_match | python
type           = "epi_spread"
infection_rate = 0.05
num_epidemics  = 30
TOML ordering rule, and it bites everyone once. The top-level keys must appear before the first [section] header. Once a table header opens, every following key belongs to that table — so a population_size written below [evolution] becomes evolution.population_size, which is not a key GET knows, and the error you get is a missing population_size.

Top level

KeyTypeDefaultMeaningValidation
population_sizeintegerrequired Individuals in the population. Must be ≥ tournament_size.
network_sizeintegerrequired Nodes in every expressed graph. Fixed for the whole run. Bounds patient_zero. See memory — cost is quadratic in this.
max_edge_multiplicityinteger1 Edge-weight cap. 1 gives a simple unweighted graph. Also derives the SDA alphabet as cap + 1. 1 ≤ v ≤ 255
crossover_ratefloatrequired Probability a selected pair recombines. None — see the warning below.
mutation_ratefloatrequired Probability a child mutates at all. None
max_mutationsinteger1 How many mutations a mutating child takes, drawn uniformly from 1..=max. See Crossover & Mutation. ≥ 1
Probabilities are not range-checked. crossover_rate, mutation_rate and infection_rate are all read as plain floats, and a negative value or one above 1.0 parses and runs without complaint. This is a gap in the design as well as the code — the spec sheet's constraint list omits them too. Until it is closed, check your own numbers: it is the first thing people get wrong.

[evolution] — the strategy

Pick one. Full explanation on Evolution Strategies.

KeyApplies toTypeDefaultMeaning
typeboth"generational" | "steady_state"requiredWhich strategy.
num_generationsgenerationalinteger requiredGenerations to run. The run ends here; there is no convergence detection.
elite_countgenerationalinteger 1 Best individuals copied forward unchanged each generation. Must be strictly less than population_size — equal means nothing breeds and the run is a fixed point. 0 is legal and makes the GA non-elitist.
num_mating_eventssteady_stateinteger required Mate-and-replace events. One row is logged per population_size events, so this is not comparable to num_generations one-for-one.

[selection]

KeyTypeDefaultMeaning
type"tournament"required The only scheme today. Adding another is one variant and one match arm.
tournament_sizeintegerrequired Entrants per tournament — higher means stronger selection pressure. Must be ≥ 4 under steady-state only, and never more than population_size.
The tournament floor is strategy-specific. Steady-state needs four distinct individuals per event — two parents and the two they replace — so tournament_size = 3 would make the second parent one of the replaced, and 2 breaks its self-elitism outright. Generational has no such floor. Switching [evolution] type can therefore make a previously valid [selection] block invalid.

[genome] — the representation

Pick one. Full explanation on Genomes.

edge_edit

KeyTypeDefaultMeaning
gene_lengthintegerrequired How many edit operations each genome carries. Fixed for the run.
[genome.operation_weights]tableall 1.0 Relative weights for the nine operations — see below.
 
[genome]
type        = "edge_edit"
gene_length = 256

[genome.operation_weights]
toggle       = 2.0    # relative, NOT percentages — these need not sum to anything
hop          = 1.0
add          = 1.0
delete       = 1.0
swap         = 0.5
local_toggle = 1.0
local_add    = 1.0
local_delete = 1.0
null         = 0.0    # 0.0 disables an operation outright

Weights are relative, not percentages. They are validated once at startup — every value finite and non-negative, and at least one strictly positive — and compiled into a sampler that the whole population shares, so a weight error surfaces from config rather than mid-run. Set null = 0.0 to make every gene do something.

This is the one sub-table that rejects unknown keys. A misspelled local_del is an error naming the key, rather than a weight silently staying at its default. Everywhere else in the config, a stray key is ignored.

sda

KeyTypeDefaultMeaning
num_statesintegerrequired States in the automaton. Must be in 1..=65536.
max_resp_lenintegerrequired Longest response a single transition may emit. Must be ≥ 1.
init_stateinteger0 The state the automaton starts in. Must be < num_states — it indexes the response table, so an out-of-range value would panic during expression.
There is no num_chars key, deliberately. The alphabet is derived as max_edge_multiplicity + 1, so characters are exactly 0..=cap and every character is a legal edge weight. Configuring it separately would allow two silent failures — an oversized alphabet biases the graph toward the cap as surplus characters clamp down onto it, and an undersized one makes the upper weights unreachable. Raising the cap therefore widens the automaton's alphabet as a side effect. Reasoning on Genomes.
Two SDA dimensions are checked later than the rest. num_states outside 1..=65536 and max_resp_len = 0 are caught when the population is minted rather than when the config is validated — so a config that loads cleanly can still fail on your first run() call with a ValueError.

[fitness] — the objective

Four choices. The three SIR objectives share one flattened parameter block, so their keys sit directly in [fitness] rather than a sub-table. Full explanation on Fitness & Orientation and The SIR Model.

typeReadsDirectionExtra keys
"epi_spread"Total ever-infectedMaximize —
"epi_length"Timesteps to burn outMaximize —
"epi_prof_match"RMSE against a target curve Minimizetarget_profile
"python"Your own callable Declared at registrationnone — it takes no config keys at all

Direction is never a config field. One objective is always maximized or always minimized; it is a property of what the function computes, not of the run. A Python objective declares its direction when you register the callable.

Shared SIR keys

KeyTypeDefaultMeaningValidation
infection_ratefloatrequired Per-edge, per-timestep transmission probability. None — not range-checked.
num_epidemicsintegerrequired How many independent outbreaks one evaluation averages over. This dominates run time. ≥ 1
patient_zerointegeromitted Pin the outbreak's starting node. Omit it and a fresh node is drawn per epidemic. < network_size when present
min_epidemic_lengthinteger3 Outbreaks shorter than this are discarded and re-simulated. Set 1 to disable the re-roll entirely. ≥ 1
max_epidemic_retriesinteger5 Attempts before keeping whatever came out. ≥ 1
target_profilearray of numbersrequired for epi_prof_match Newly-infected count per timestep, compared verbatim. Non-empty, all finite. Rejected under any other objective.

num_epidemics deliberately has no default: a single SIR draw is very noisy, and a silent default would quietly change what every fitness number means. The two re-roll keys default to the constants the original C++ used (mepl = 3, rse = 5) — see why the re-roll exists and what it biases.

A target_profile copied from a legacy C++ run will be wrong twice over. The old loader prepended patient zero — so a stored file omitted its own first element — and multiplied every value by verts / 128. GET does neither. Supply the profile you actually want, at the size of the network you are building.

Unknown keys, and the two GET checks for

Most stray keys are silently ignored. A typo in an existing key usually surfaces as a missing field error for the correct spelling, which is a good signal; an extra key that simply does not belong — a top-level elite_count, say — vanishes without a word, which is not. Two are checked by name because they are migration hazards:

RejectedWhy
[fitness] seed An older schema had one. All randomness now derives from the single seed you pass to run. A separately configured fitness seed would mean replicates at different evolution seeds still faced identical epidemics — exactly what replicates exist to vary.
target_profile under any objective but epi_prof_match It is a contradiction rather than a harmless extra, so it is reported instead of ignored.

Validation, and what it promises

Validation is a function, not a side effect of parsing — Config::validate — and both front ends call it. That matters because the Python builder bypasses the TOML parser's own checks entirely; without one shared validator, the Python path would silently accept configurations the file path rejects, which is the worse direction because Python is the path users actually take.

  • It runs before anything is built — before a population is minted or a graph allocated. Everything downstream may assume a valid config.
  • It returns an error, never panics. You get a Python exception naming the offending field and its constraint, not an opaque PanicException from across the FFI boundary.
  • From Python, the field name is translated back to the attribute you actually set — num_epidemics is reported as config.fitness.sir.num_epidemics.

Every constraint, in one list

  • 1 ≤ max_edge_multiplicity ≤ 255
  • max_mutations ≥ 1
  • population_size ≥ tournament_size
  • tournament_size ≥ 4 — steady-state only
  • elite_count < population_size — generational only
  • init_state < num_states
  • operation weights finite, non-negative, at least one positive
  • num_epidemics ≥ 1
  • min_epidemic_length ≥ 1 · max_epidemic_retries ≥ 1
  • patient_zero < network_size when pinned
  • target_profile non-empty and finite, present for epi_prof_match and absent otherwise
  • base graph node count and cap narrowing planned
Planned: the base-graph checks. Once a base graph can be supplied, validation also confirms its node count matches network_size and rejects narrowing the edge cap — piping a cap-5 result into a cap-1 run would otherwise collapse every weight to 1 in silence. Today no base graph can be set, so an edge-edit run always starts from an empty graph.

Two error messages that name the wrong field

Worth knowing, because the message will send you to the wrong line:

  • num_states = 0 is reported as an init_state problem — the init_state < num_states check fires first, and 0 < 0 is false.
  • population_size = 0 is caught only indirectly, and reports elite_count or tournament_size depending on the strategy. It cannot slip through, but the field named is not the one you wrote.

A complete, realistic config

# A steady-state SDA run matching a target infection curve on a 100-node multigraph.

population_size       = 200    # must be >= tournament_size
network_size          = 100    # every expressed graph has 100 nodes
max_edge_multiplicity = 3      # parallel edges up to 3; fixes the SDA alphabet at 4 characters
crossover_rate        = 0.9    # 90% of selected pairs recombine
mutation_rate         = 0.2    # 20% of children mutate at all
max_mutations         = 2      # a mutating child takes 1 or 2 mutations, uniformly

[evolution]
type              = "steady_state"   # one mate-and-replace event at a time
num_mating_events = 100000           # logs one row per 200 events -> 501 rows

[selection]
type            = "tournament"
tournament_size = 6            # >= 4 REQUIRED here, because the strategy is steady_state

[genome]
type         = "sda"           # an automaton that writes a graph from scratch
num_states   = 12
max_resp_len = 4               # each transition emits 1..=4 characters
init_state   = 3               # must be < num_states

[fitness]
type                 = "epi_prof_match"   # RMSE against the curve below; minimized
infection_rate       = 0.05               # per-edge, per-timestep
num_epidemics        = 30                 # each evaluation averages 30 outbreaks
patient_zero         = 0                  # pinned; omit for a fresh node per epidemic
min_epidemic_length  = 3                  # re-roll outbreaks shorter than 3 timesteps
max_epidemic_retries = 5                  # after 5 attempts, keep whatever came out
target_profile = [1, 3, 8, 17, 24, 19, 11, 5, 2, 1]

The same experiment built out of Python objects is on the Python API page, and more variations are in Examples. The repository also ships config.example.toml, which is parsed and validated by the test suite — so it is always a working document.
