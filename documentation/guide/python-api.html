Using GET

Python API

GET is a compiled extension module. From Python you build a config, hand it to a GraphEvolver, and call run. This page is the whole surface.

Two ways in, one parser

You can point GET at a TOML file, or build the same configuration out of typed Python objects. The Python objects are a builder for the config format, not a second parser of it — they serialize to TOML, and that TOML is what Rust parses: 

Python config objects ──serialize──> TOML ──serde──> Config ──validate──> run
                                              hand-written TOML ─┘

So there is exactly one parser and one validator, and the Python path cannot accept something a file would reject. It also gives you provenance for free: config.to_toml() is the document Rust actually parsed, and re-running it reproduces the experiment verbatim. 

import get

# Route A — a file you wrote
evolver = get.GraphEvolver("experiment.toml")     # reads, parses AND validates

# Route B — objects you built
evolver = get.GraphEvolver.from_config(config)    # renders, parses AND validates

Put together

import get

config = get.Config(
    evolution       = get.EvolutionConfig.SteadyState(num_mating_events=100_000),
    population_size = 200,
    network_size    = 100,
    crossover_rate  = 0.9,
    mutation_rate   = 0.2,
    selection       = get.SelectionConfig.Tournament(tournament_size=6),
    genome          = get.GenomeConfig.Sda(num_states=12, max_resp_len=4, init_state=3),
    fitness         = get.FitnessConfig.EpiProfMatch(
        sir = get.SirParams(
            infection_rate       = 0.05,
            num_epidemics        = 30,
            patient_zero         = 0,
            min_epidemic_length  = 3,
            max_epidemic_retries = 5,
        ),
        target_profile = [1, 3, 8, 17, 24, 19, 11, 5, 2, 1],
    ),
    max_edge_multiplicity = 3,
    max_mutations         = 2,
)

with open("provenance.toml", "w") as f:
    f.write(config.to_toml())        # the exact document Rust will parse

evolver = get.GraphEvolver.from_config(config)

Running

GraphEvolver.run(seed) -> RunResult
lib.rs:235

Runs the evolution and returns everything that run produced — the best fitness, the best network, the winning genome and the convergence log.

One seed drives everything — the starting population, the evolution loop, and the epidemics. The same seed and the same config give the same result, on any machine, forever. See Seeds & Reproducibility.

Nothing is cached on the evolver. The result is the returned value and nowhere else, so one evolver drives as many runs as you like without a previous one's numbers surviving into the next.

The long Rust portion releases the GIL, so other Python threads keep running while a run is in progress. 

result = evolver.run(seed=20260812)

print(result.best_fitness)       # in your units
print(result.best_edges)         # (u, v, multiplicity) triples
print(result.best_genome_repr)   # the winning genome, printed

for row in result.history:       # the convergence log
    print(row.iteration, row.best_fitness, row.mean_fitness, row.std_dev)
RunResult
py_result.rs:68

Read-only. best_fitness is in your objective's own units — infected nodes for epi_spread, an RMSE for epi_prof_match. The engine's internal lower-is-better orientation is converted away before you see it.

best_edges is the best network as (u, v, multiplicity) triples with u < v; pairs with no edge are not listed. best_genome_repr is the winning genome's printed form, which is how a result records which individual won without the API needing to know the representation.

history builds a fresh list on each access, so bind it once rather than re-reading it inside a loop.

GenerationStats
py_result.rs:34

One row of history: iteration, best_fitness, mean_fitness, std_dev. iteration counts generations under the generational strategy and mating events under steady-state.

The two fitness columns are in your units; std_dev is left exactly as computed, because a spread reads the same whichever direction the objective runs in. It is the population deviation — see Logs & Results.

GraphEvolver.set_fitness_function(callable, direction)
lib.rs:148

Registers your own objective. direction is "minimize" or "maximize", case-insensitive, and is declared here because nothing can infer it from your function.

It refuses if the config did not select type = "python" — silently accepting a callable that will never be consulted is indistinguishable from success. Full guide on Add an Objective.

Replicates planned

The design lets one call do n replicate runs — which is what research use actually looks like — returning a list of the result objects above, one per replicate: 

results = evolver.run(seed=20260812, runs=30, max_cores=8)   # a list, one per replicate

best = min(results, key=lambda r: r.best_fitness)
print(best.best_fitness)
ArgumentMeaning
seed The master seed. It seeds a generator whose output stream is the per-run seed list — run i takes draw i. So asking for 50 runs reproduces the first 30 exactly, and extending an experiment never invalidates the replicates you already have.
runs How many replicates. Results come back in run order, never completion order.
max_cores Upper bound on concurrency. Unset means all available; 1 is fully sequential. There is no point exceeding runs.

Whether replicates actually run in parallel is decided by the engine, not by you: native Rust objectives run replicates in parallel, and fitness = "python" runs them sequentially, because n concurrent runs would be n threads contending for one GIL — slower than sequential and contended. Exposing that as a setting would only create a way to choose wrong.

max_cores is a memory knob as much as a CPU one. Each concurrently-executing replicate holds its own expressed population, and a graph is a dense network_size × network_size matrix however sparse it is. Raising max_cores to use a bigger machine multiplies peak memory by the same factor, and can exhaust it on hardware that handled the smaller setting comfortably. The arithmetic is on Performance & Memory.
Today: run(seed) takes exactly one seed and performs one run, returning a single RunResult rather than a list. To do replicates now, call run in a Python loop with your own seeds — but note that this does not give you the stream-derived seeding described above, so extending the loop later will not reproduce your earlier runs unless you record each seed you used.

Saving results planned

GraphEvolver.save_logs(path) GraphEvolver.save_results(path)
lib.rs:266, lib.rs:272

Write the convergence log as CSV, and the best individual plus the generated TOML as the results record. Both convert fitness back into your units on the way out and leave std_dev and ci_95 alone, since a spread is identical under negation. Column list on Logs & Results.

Today: both raise, and they still take the evolver rather than a result — which now holds nothing to write, since a run's state lives in the returned RunResult. Write the CSV yourself from result.history until they are re-homed onto the result object.

Supplying a base graph planned

GraphEvolver.set_base_graph(num_nodes, edges)

The starting graph that an edge-edit genome edits. It is not a config value — it is either data you bring or the output of a previous run. Since run already returns (u, v, multiplicity) triples, the two representations stack with no new data format: evolve a topology with SDA, then refine it with edge-edit.

The setter owes three checks, all of which fail quietly if skipped:

  • the node count must match network_size, or out-of-range edges are silently dropped;
  • narrowing the edge cap must be rejected or warned — set_edge clamps, so piping a cap-5 result into a cap-1 run silently collapses every weight to 1. This is the main stacking trap;
  • with no base graph, the run starts from an empty one — which leaves five of the nine opcodes inert until Add or Toggle build some structure.
Today: there is no base-graph setter, so every edge-edit run starts from an empty graph. Early generations genuinely do look like they are doing nothing while Add/Toggle build the first structure — that is self-correcting, not a bug.

Errors you will see

ExceptionMeans
ValueError: invalid config: `field` … A validation constraint failed. From the Python route the field is reported as the attribute you set — config.fitness.sir.num_epidemics — not the TOML name.
ValueError mentioning a missing field or unknown variant A parse error: a required key absent, a wrong type, or a type string GET does not know.
ValueError: num_states must be between 1 and 65536 An SDA dimension. These are checked when the population is minted, so they surface on your first run() rather than at config time.
RuntimeError about a fitness function Either type = "python" with nothing registered, or set_fitness_function called when the config selected a native objective.

A bad config is a user mistake, so it is always a proper Python exception naming the field — never a panic crossing the FFI boundary. More on Troubleshooting.

The other front door: Rust

Python is not a fallback for Rust or the other way round — both routes are supported. If your objective is hot enough that Python arithmetic dominates the run, depend on get as a crate, implement Fitness for your own type, and drive an evolver directly. That path never touches dispatch or the config schema at all. See Add an Objective.
