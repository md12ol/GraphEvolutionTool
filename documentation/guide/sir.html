How it works

The SIR model

The simulated disease that scores every graph. If you have never met an epidemic model, this page starts from zero — and if you have, note that GET's version has a one-timestep infectious period, which is simpler than the textbook one.

SIR in sixty seconds

Every node in the network is in one of three states, and the letters are the model's name:

StateMeans
SSusceptibleHealthy, and can catch it.
IInfectiousHas it, and can pass it on.
RRecoveredHad it, is over it, and can never catch or spread it again.

Nodes only ever move forwards: S → I → R. Nobody relapses. The disease travels along edges, so the shape of the network completely determines how far and how fast it can go — which is the entire premise of GET.

GET's version, precisely

The infectious period is exactly one timestep. A node infected during step t spends step t+1 infectious, transmitting to each still-susceptible neighbour with probability infection_rate per edge, and then becomes recovered forever.

  • A single patient_zero seeds the outbreak. Pin it in config, or leave it unset and a fresh node is drawn for every epidemic.
  • The simulation runs until no infectious nodes remain. There is no step cap and none is needed — the infectious set can only shrink to nothing.
  • Per edge matters on a multigraph: a pair joined by weight 3 gets three independent chances to transmit each step, so a heavier edge is genuinely a stronger contact.

What one simulation returns

sir_sim(graph, params, rng) -> Epidemic { length, spread, profile }
FieldIs
spread How many nodes were ever infected, counting patient zero.
length How many timesteps the epidemic occupied, including the final step in which the last infectious node recovers without transmitting.
profile The count of newly infected nodes at each timestep. profile[0] = 1 for patient zero, and the last element is always a terminating zero.
The trailing zero and the burnout step catch people out. Two worked cases fix the convention:
  • An outbreak that infects nobody beyond patient zero gives length = 1, spread = 1, profile = [1, 0].
  • A 6-node path burning right through at infection_rate = 1.0 gives length = 6, spread = 6, profile = [1, 1, 1, 1, 1, 1, 0].
So profile is always one element longer than the number of steps that infected anybody, and length counts the burnout pass. This matches the original C++ implementation exactly, and it means a target_profile you compare against should include that trailing zero.

All three objectives read one simulation

The epidemic is the expensive part, so a single run returns everything and each objective is a thin reading of it: epi_spread takes spread, epi_length takes length, and epi_prof_match takes the RMSE between profile and your target. See Fitness & orientation for how a length mismatch is handled — it is asymmetric, and it changes what you are selecting for.

Short epidemics are re-rolled

An outbreak that burns out in fewer than min_epidemic_length timesteps is discarded and re-simulated, up to max_epidemic_retries attempts. Whatever the final attempt produces is kept regardless: 

attempts = 0
repeat
    run = sir_sim(graph, params, rng);  attempts += 1
until run.length >= min_epidemic_length or attempts >= max_epidemic_retries

Why it exists: a fizzled outbreak carries no information about the graph. It reports that the dice went badly, not that the network is poor. Without the re-roll a large share of evaluations return near-nothing, and selection chases the dice instead of structure.

Be clear about what it is: a biased resample, not variance reduction. It shifts expected fitness upward, by an amount that depends on how often a given graph fizzles — so it is not interchangeable with raising num_epidemics, and the two do different jobs. This is accepted deliberately, for comparability with the historical C++ results, and it is why both values are exposed rather than hardcoded.

To disable it, set min_epidemic_length = 1: every epidemic has length ≥ 1 under the convention above, so nothing is ever re-rolled. max_epidemic_retries = 1 gives one attempt and is equivalent. Both must be at least 1 — 0 is a validation error, not a way to switch the feature off.

The defaults, 3 and 5, are the constants the original C++ used (mepl and rse).

The re-roll and reproducibility

A retry consumes extra randomness, which would normally desynchronise the rest of a batch. GET avoids that by seeding epidemics by position: epidemic i, attempt a, takes draw i × max_epidemic_retries + a from the batch's seed stream. Every graph in the batch therefore draws from an identical pool of dice; what differs between graphs is only which of those common draws each one stops on — and that is what a retry is. Full reasoning on Seeds & reproducibility.

Cost, and the one knob that controls it

The num_epidemics simulations inside one evaluation run sequentially, never concurrently. Parallelism comes from the two levels above — the population and the replicate runs — which together already provide far more independent work than any core count. Keeping the epidemics serial also makes each population-level task substantially larger, which improves how well the two parallel levels amortize.

In practice num_epidemics is the dominant term in your run time. Everything else in an evaluation is cheap by comparison. See Performance & memory.
