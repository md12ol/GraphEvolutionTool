How it works

Seeds & reproducibility

One number reproduces an entire experiment. Getting that right under a stochastic objective and parallel execution takes more care than it sounds like, and this page is the whole scheme.

One seed, and it is not in the config

There is exactly one seed for the whole experiment, supplied to the run call, and everything derives from it: the starting population, the evolution loop, and the epidemics.

It lives on run rather than in the config because the seed describes this invocation, while the config describes the experiment. The same reasoning puts the replicate count and the core cap there too. A [fitness] seed key is rejected by name — it existed in an older schema, and a separately configured fitness seed would mean replicate runs at different evolution seeds still faced identical epidemic draws, which is exactly the thing replicates exist to vary.

The generator is pinned, deliberately. Both strategies seed ChaCha8Rng, not the library's default generator — whose algorithm may change between releases, which would defeat the entire purpose of a seed argument. The same seed must mean the same thing in both strategies, on every machine, indefinitely.

How the seed spreads

Replicate seeding planned

Research use is n runs at identical parameters. The master seed seeds a generator whose output stream is the per-run seed list — run i takes draw i. One parameter, fully reproducible, and with one property worth preserving deliberately:

A run's seed does not depend on how many runs you asked for. Drawing from a stream gives that for free: asking for 50 runs reproduces the first 30 exactly, so extending an experiment never invalidates the replicates you already have.

Deriving from master + i or hash(master, i) would work equally well. master ^ i would not, because nearby masters collide across run indices — master 4 run 1 and master 5 run 0 would be the same run.

Today: run performs a single run from a single seed. If you loop in Python to get replicates, you are choosing the seeds yourself and do not get the stream property above — so record every seed you used, or your experiment will not be extensible later.

The epidemic dice

This is where a stochastic objective gets subtle. Two requirements pull in opposite directions, and both matter:

RequirementWhy
Within one evaluation, every population member must face the same epidemic draws. This is common random numbers. Fitness differences then reflect the graph rather than the dice, which is what makes selection meaningful at all under a noisy objective.
Across evaluations, the same network must not keep getting the same epidemic. Otherwise the run optimizes against one frozen sample of the disease rather than against the disease.

The mechanism is forced by the trait — an objective cannot carry a mutable generator across a parallel population — so:

The objective holds a run seed plus an atomic evaluation counter. Each call to the batch scorer increments the counter once and derives that batch's epidemic seed from (run_seed, counter). Every graph in the batch is simulated from that one derived seed; the next batch gets a different one. Reproducible, shared within a batch, fresh across batches.

The counter is per-run state, not shared. Each run owns its own objective instance and therefore its own counter. A counter shared across concurrently executing runs would let thread scheduling decide which run sees which epidemic seed — and reproducibility would evaporate in a way that only shows up under load, which is the worst possible failure mode.

Deriving the seed from the graph's contents or its index would satisfy neither requirement. It reintroduces exactly the between-individual noise that common random numbers removes, and freezes each network's epidemic forever.

Position-indexed epidemics, and why the re-roll survives

Inside one evaluation, the batch seed seeds a generator whose output stream is the epidemic seed list, and epidemic i, attempt a, takes draw i × max_epidemic_retries + a. This is not a second mechanism — it is the identical one applied to a different index.

It is also what keeps the short-epidemic re-roll compatible with common random numbers. Drawing epidemics sequentially from one stream would not: whether a graph re-rolls depends on its own outcome, so a graph that retries consumes extra draws — and every subsequent epidemic in that evaluation would then be offset from the graphs that did not retry, for the rest of the batch. Position-indexed seeds resynchronise at the next epidemic index.

"The re-roll breaks CRN" is the easy misreading, and it is wrong. Every graph in the batch draws from an identical pool of dice — the same h(batch, i, 1) … h(batch, i, max_epidemic_retries) for all of them, none of it graph-specific. What differs between graphs is only which of those common draws each one stops on, and that is what a retry is. The randomness is common; the stopping rule is outcome-dependent, deliberately.

Position-indexing is also what makes scoring order-independent: a population evaluated across parallel workers reproduces exactly regardless of which worker reaches which graph first.

What can still differ between two runs

ChangeSame result?
Same seed, same config, different machineYes.
Same seed, same config, different max_cores Yes — parallelism never affects the outcome, by design.
Same seed, asking for more replicates Yes for the replicates you already had.
Same seed, a different strategy No — and it should not. The seed means "the same dice", not "the same run".
Same seed, one config value changed No. Every downstream draw shifts.
Same seed, a Python Objective that is itself random No. GET cannot seed your callable. If you want reproducibility, seed it yourself from something deterministic.

Provenance

The seed alone is not enough to reproduce an experiment — you also need the exact config. That is what config.to_toml() is for: the Python objects serialize to TOML and that document is what Rust parses, so writing it next to your results gives you a record that re-runs verbatim. Store the seed beside it and the pair is complete.

The design also carries the seed and the run index on every log row planned, so 30 replicate logs can be concatenated into one file and still be separable — which is what makes an across-run convergence band computable later. See Logs & Results.

One accepted limitation

Steady-state carries stale fitnesses: it scores only the two new children per event, so the population's recorded fitnesses were computed under different dice than the children being compared against them. An individual that drew lucky dice keeps its inflated score for the rest of the run. This is reproducible — it is not a randomness bug — but it does mean the comparison is not fair. Prefer generational when the objective is stochastic and the comparison needs to be fair.
