Extending GET

Add a crossover operator

Recombining two parents into two children. Five edits, and one of them is the step people miss: [crossover] is a shared section, so a new operator has to say which genomes can honour it.

Where the operator sits

Crossover is an enum in evolver/common.rs. The caller has already rolled crossover_rate and decided this pair breeds — the operator only chooses how. It receives two genomes and an RNG, and mutates both in place; both children are kept.

The five edits

Every location carries a literal marker in the source. Find the whole chain at once with git grep -n "ADD A CROSSOVER STEP" get/src, and jump to any one step by searching its number. The steps below are in the order the markers number them.

StepWhereWhat
1evolver/common.rs A Crossover variant, plus any parameters it reads from the file.
2evolver/common.rs The arm in Crossover::recombine that performs it.
3config.rs — two sites The mirrored CrossoverConfig variant, and one (operator, genome) pair per representation your operator can honour in the compatibility match.
4dispatch.rs The arm mapping your CrossoverConfig onto the engine variant.
5py_config.rs — two sites Optional. The Python-side variant and its matching arm.

Steps 1 and 2 — the engine side

// step 1 — in `enum Crossover`
MyCrossover { some_param: f64 },

// step 2 — in `Crossover::recombine`
Crossover::MyCrossover { some_param } => { /* recombine `first` and `second` */ }

The shipped TwoPoint arm is not a template. It is the trait call first.crossover(second, rng), because two-point is what Genome::crossover already means for every representation. A second operator will not be — and that is precisely the point at which Genome grows a second method. Genome::crossover takes no context deliberately, so an operator that needs per-representation behaviour adds a trait method rather than branching on the genome inside your arm.

Step 3 — the config variant, and the compatibility pairs

This step is two sites in one file, and the second is the one that gets forgotten. [crossover] names an operator for whichever genome is selected, and the two are chosen independently — so nothing but this match can catch an illegal combination: 

// step 3a — in `config::CrossoverConfig`
MyCrossover { some_param: f64 },

// step 3b — in the crossover/genome compatibility match
(CrossoverConfig::MyCrossover { .. }, GenomeConfig::Sda(_)) => Ok(()),
(CrossoverConfig::MyCrossover { .. }, GenomeConfig::EdgeEdit(_)) =>
    Err(invalid("crossover", "edge-edit cannot honour my_crossover")),

You cannot forget 3b, by construction. The match is written out in full rather than using a catch-all — every pairing spelled out even though every pairing is currently legal — so adding a variant stops it compiling. That forces whoever adds an operator to state which genomes can honour it, instead of a user discovering the answer part-way through a run.

Step 4 — dispatch

CrossoverConfig::MyCrossover { some_param } => {
    Crossover::MyCrossover { some_param: *some_param }
}

Steps 3a and 4 are one change split across two files, the same shape the selection chain has. The variant name becomes type = "my_crossover" under [crossover] via rename_all — you do not write that string.

Step 5 — Python, and optional

Leaving it out costs nothing elsewhere; the operator is then reachable from TOML but not from Python.

Testing it

Crossover is testable in isolation: build two known parents, recombine under a fixed seed, and assert the children are what the operator promises. The property worth pinning is whatever your operator claims to preserve — two-point preserves everything outside the swapped band, on both sides.

Then add the keys to config.example.toml, which the test suite parses and validates — so a broken example fails the build.

If you wanted mutation instead

Mutation is a separate chain and it branches per genome: git grep -n "ADD A MUTATION STEP" returns two interleaved chains, one marked (for EdgeEdit) and one (for SDA). See Add a mutation operator.
