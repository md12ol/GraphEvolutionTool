Using GET

Performance & memory

Where the time goes, where the parallelism comes from, and the one arithmetic result that surprises people: raising the core count multiplies your memory use by the same factor.

Where the time goes

Almost all of it is in the epidemics. One evaluation runs num_epidemics complete SIR simulations, and everything else — expressing a genome, comparing fitnesses, selecting parents, mutating — is cheap by comparison.

So the levers, in rough order of effect:

LeverEffect
num_epidemics Linear, and dominant. Halving it roughly halves the run — and roughly doubles the variance of every fitness number.
population_sizeLinear in evaluations per generation.
num_generations / num_mating_events Linear. Note a mating event is two evaluations, not a whole population.
network_size Superlinear: bigger graphs mean more edges to walk per epidemic step and quadratic memory.
infection_rate Indirect but real — a rate that spreads further makes each epidemic run longer before it burns out.
min_epidemic_length Indirect: a high threshold on a graph that fizzles often means most evaluations pay for up to max_epidemic_retries simulations instead of one.

Where the parallelism comes from

There are three levels, and they are not equally useful:

LevelParallel?Why
Replicate runsYes — the good one Embarrassingly parallel: independent, long-running, no synchronization.
The populationYes, but with a barrier Every generation is a barrier, so a generation costs as long as its slowest individual — and under a stochastic objective evaluation times vary widely. A fizzled outbreak returns almost immediately; one that burns through the graph does not.
Epidemics within one evaluationNo, deliberately The two levels above already provide far more independent work than any core count, and a third nesting level would add scheduling overhead for nothing. Keeping epidemics serial also makes each population-level task larger, which improves how well the other two amortize.

Prefer replicate-level concurrency where you have the choice.

A single steady-state run cannot use a big machine. It scores only the two new children per mating event, so its population-level parallelism is two-way regardless of max_cores. Replicates are the only way to fill the cores. This is the same conclusion the FFI-cost argument reaches from the other direction: one crossing per event rather than per generation also makes steady-state a poor fit for a Python objective.

Replicates: the engine chooses the mode

ObjectiveReplicates run
native Rust — epi_spread, epi_length, epi_prof_matchin parallel
pythonsequentially

With a Python objective, n concurrent runs would be n threads contending for one interpreter lock: slower than sequential and contended. The fitness type already determines the correct answer, so exposing the mode as a setting would only create a way to choose wrong.

Sequential replicates does not mean a sequential run. Expression is pure Rust and holds no Python lock, so a Python-fitness run still expresses its population across threads — only the single scoring call per batch is serialized.

max_cores planned

The one knob. Unset means all available; 1 means fully sequential. There is no point exceeding the replicate count, so the effective figure is min(max_cores, n). It governs both levels — one thread pool that replicate-level and population-level work both draw from — so total concurrency stays bounded no matter how the two nest.

The pool is built per call, not globally. A global thread pool can be configured only once per process, and GET is an extension module imported once per session — so a global configuration would make max_cores a property of whichever run call happened first, and a second call with a different cap would fail outright.

Memory, and the multiplication that catches people

Expression materializes the whole population as graphs before scoring, and a graph is a dense matrix — network_size × network_size however sparse the network actually is. Each concurrently-executing replicate holds its own expressed population. So peak memory is roughly: 

network_size² × 4 bytes × population_size × min(max_cores, n_replicates)

The three parameters interact rather than adding, so raising any one scales the whole product:

network_sizeone graphpopulation of 200 × 8 concurrent replicates

The failure mode is unintuitive. You run a configuration successfully, move to a bigger machine, raise max_cores to use it — and multiply peak memory by the same factor, exhausting it on hardware that handled the smaller setting comfortably. max_cores is a memory knob as much as a CPU one.

Practical guidance

  • Keep hot objectives native. The Python adapter is for prototyping. A naive per-individual Python objective can be hundreds of times slower wall-clock than parallel Rust; batched, only the speed of the Python body remains — which is why the batched contract is mandatory rather than a suggestion.
  • Vectorise your Python objective. The interface is shaped like pymoo's Problem._evaluate for exactly this reason: one call receives the whole population, so numpy can do the work in one pass. See Add an Objective.
  • Use generational with a Python objective, so you pay one crossing per generation rather than one per mating event.
  • Tune num_epidemics against noise, not against the clock. Too low and selection chases dice rather than structure, which wastes the whole run rather than part of it.
  • Estimate memory before raising max_cores, using the formula above.

Two structural rules that keep the parallelism real

Relevant if you are extending GET rather than using it:

  • Expression happens in parallel before any Python is called — never call Python from inside a parallel closure. Doing so deadlocks rather than merely slowing down.
  • The long Rust portion releases the interpreter lock, with the Python adapter re-acquiring it per batch.
