Extending GET

Add a Scope

Choosing which slice of the population a single breeding event may touch. Six edits across five files, and no strategy, genome or selection scheme is touched — scope is one of three independent axes, and it answers only this question.

The One Question a Scope Answers

A scope produces a list of population indices. Everything downstream works inside that list: [selection] picks parents from it, [replacement] picks who the children overwrite in it. The scope itself has no opinion about fitness — Global does not even read it.

AxisQuestionConfig
Scopewho is eligible for this event[scope]
Selectionwho among them becomes a parent[selection]
Replacementwho among them is overwritten[evolution] replacement

A variant's parameters are its own. size belongs to [scope] and nothing else reads it. That is the whole reason this axis exists as its own enum: steady-state used to take its scope size from [selection]'s tournament_size, which left a scheme with no tournament unable to say how large a scope it wanted.

What the User Ends Up Writing

Adding a scope called Neighbourhood is what makes this valid:

[scope]
type   = "neighbourhood"
radius = 3

You never write the string "neighbourhood" anywhere in the code — it is derived from the variant name, converted to snake_case, and the keys under it are your struct's field names. Every config carries a [scope] block, generational included (type = "global").

Scope is an enum, not a trait, so it cannot be extended from outside the crate. A program that merely depends on GET gets the scopes GET ships. Adding one means editing your own copy, which is what the steps below assume.

The Six Steps

Every step is marked at its own site. One command lists the chain:

git grep -n "ADD A SCOPE STEP" get/src config.example.toml
StepWhereWhat
1get/src/evolver/scope.rs:49 the variant, and whatever it needs to locate a slice
2get/src/evolver/scope.rs:103 the arm filling the buffer with your indices
3get/src/config.rs:138 the variant a user names under [scope], plus any constraint on it
4get/src/dispatch.rs:939 the arm mapping that config variant onto the engine one
5get/src/py_config.rs:264 and :876 the Python mirror — optional
6config.example.toml:156 a commented-out block naming your variant — optional, and the step people skip

Steps 1 and 2 — The Engine Side

Step 1 is the variant. Step 2 is the arm in the draw, and the match is exhaustive, so the compiler finds it for you — these two are the pair you cannot forget.

Three contracts the signature does not enforce.
  • Every index must be in range for the population. Nothing downstream re-checks, and an out-of-range index is an assertion in a debug build and a silent misread otherwise.
  • Distinctness is load-bearing where a replacement policy names positions. RandomSubset draws without replacement precisely so that "the worst two members" means something; over a multiset it does not. A scope that repeats an index has to be paired with a policy that tolerates it.
  • Take every random value from the RNG you are handed. A scope that reaches for a thread RNG produces a run that cannot be reproduced from its seed.

Global consumes no randomness at all, which is worth knowing when comparing two runs: switching a config from global to any drawing scope changes the whole downstream stream, not just the scope.

Steps 3 and 4 — The Config Side

These are one change split across two files: a config variant nothing maps is dead code, and a dispatch arm for a variant that does not exist will not compile. Any constraint on your own parameters goes in the config layer beside the variant.

Steps 5 and 6 — Python, and Optional

Skipping step 5 makes the scope TOML-only: it still runs from a config file and from the Rust library, and a Python caller simply cannot name it. Skipping step 6 costs nothing mechanically and means most people never find it, because the shipped example is what a user copies from.

The Other Two Axes

If what you want is who becomes a parent or who gets overwritten, those are their own chains: 

git grep -n "ADD A SELECTION STEP" get/src config.example.toml      # six steps
git grep -n "ADD A REPLACEMENT STEP" get/src    # three steps
