Extending GET

Add a selection scheme

Choosing which members of a scope become parents. Six edits, four files, and no strategy or genome is touched — selection is one of three independent axes, and it answers only this question.

The one question a scheme answers

Selection takes a scope — a list of population indices someone else chose — and returns count parent indices drawn from it. It does not decide who is eligible ([scope] does that) and it does not decide who dies ([replacement] does that). That separation is why every scheme works with every strategy, and why there is deliberately no scheme-by-strategy compatibility check to extend.

The six edits

Every location carries a literal marker in the source. Find the whole chain at once with git grep -n "ADD A SELECTION STEP" get/src, and jump to any one step by searching its number. The steps below are in the order the markers number them.

StepWhereWhat
1evolver/common.rs A Selection variant, carrying any parameters the scheme reads out of the file.
2evolver/common.rs The arm in Selection::pick that actually chooses parents.
3config.rs The mirrored SelectionConfig variant — the one a user names under [selection].
4dispatch.rs The arm mapping your config variant onto the engine variant. Steps 3 and 4 are one change split across two files.
5py_config.rs — two sites Optional. The Python-side variant and its matching arm.
6py_config.rs Optional. The to_toml_value arm that writes type = "my_scheme" and its fields under [selection].

Steps 1 and 2 — the engine side

Selection lives in evolver/common.rs. Add the variant, then the arm that performs it: 

// step 1 — in `enum Selection`
Roulette { pressure: f64 },

// step 2 — in `Selection::pick`
Selection::Roulette { pressure } => {
    let mut parents = Vec::with_capacity(count);
    for _ in 0..count {
        parents.push(spin(scope, fitnesses, *pressure, rng));
    }
    parents
}

The variant name becomes type = "roulette" under [selection], via the rename_all on config::SelectionConfig — you do not write that string anywhere.

Three contracts your arm must honour, none of which the compiler checks:

  • Pick only from scope. Returning a population index that is not in the scope silently ignores the [scope] block the user configured.
  • Compare through rank. It orders better-first with ties broken by lower index, which is what keeps a run reproducible when two individuals score identically. Comparing the raw f64 yourself reintroduces the tie.
  • Take every random value from rng. Any other source of randomness breaks seeded reproducibility, and it breaks it in the way that is hardest to notice: the run still works, it just cannot be repeated.

Steps 3 and 4 — the config side

One change, two files. The config variant, and the arm that maps it onto the engine variant:

// step 3 — in `config::SelectionConfig`
Roulette { pressure: f64 },

// step 4 — in `dispatch`'s selection mapping
SelectionConfig::Roulette { pressure } => {
    Selection::Roulette { pressure: *pressure }
}

If your scheme has parameters that can be wrong — a pressure that must be positive, a size that must be at least one — constrain them in validate_evolution_and_selection. There is no scheme-by-strategy check to extend there, only your own parameters.

Steps 5 and 6 — Python, and optional

Leaving these out costs nothing elsewhere; the scheme is then reachable from TOML but not from Python. Step 5 is the mirrored PySelectionConfig variant and its arm; step 6 is the to_toml_value arm that writes the block back out.

Step 5 is the one nothing checks. The source says so at the marker. A scheme that is missing its Python mirror does not fail to compile and does not fail a test — it is simply absent from the Python API, and the first person to notice is a user who cannot find it.

Testing it

Selection is unusually easy to test directly: it is a pure function from a scope, a fitness slice and an RNG to a list of indices. Assert that every returned index is in the scope, that a fixed seed gives a fixed answer, and that a population with one obviously-best member selects it more often than chance.

Then add the keys to config.example.toml, which the test suite parses and validates — so a broken example fails the build.

The other two axes

If what you actually want is to change who is eligible or who gets overwritten, you want a different chain: git grep -n "ADD A SCOPE STEP" or git grep -n "ADD A REPLACEMENT STEP". Both are separate axes for the same reason selection is — so that adding one does not constrain the others.
