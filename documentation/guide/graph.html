How it works

The graph

Every candidate solution in GET eventually becomes one of these. It is deliberately simple: a fixed number of nodes, an undirected edge between any pair, and a small integer weight saying how many parallel edges that pair has.

What it is

A Graph is an undirected multigraph on a fixed node count, stored as a symmetric adjacency matrix of u32 weights.

  • Weight 0 means no edge.
  • Weight k > 1 means k parallel edges between that pair.
  • Every graph carries its own max_edge_multiplicity. Set it to 1 and you have an ordinary simple, unweighted graph — which is the default and what most runs use.

The node count never changes during a run. There is no adding or removing nodes, no directed edges, and no node or edge attributes: see what it deliberately is not.

Behaviours that will surprise you

Four of the graph's design choices are deliberate, load-bearing, and not what you would guess. Every one of them exists so that genome expression never has to validate anything.

BehaviourConsequence
set_edge clamps to the cap rather than rejecting Feeding a cap-5 result into a cap-1 run silently collapses every weight to 1. This is the main trap when stacking two runs.
Self-loops and out-of-range vertices are silently ignored by set_edge and weight Genome expression relies on this — a decoded vertex pair is never validated before use.
degree counts distinct neighbours; total_edge_multiplicity counts edge copies They differ on any multigraph, and the edit operations depend on which one they use.
get_neighbor_at_index wraps modulo the degree Lets an arbitrary 32-bit payload always name a real neighbour. It returns None only for an isolated or invalid node.
get_edge_list returns each edge once, u < v, row-major The same order SDA expression writes in, and the shape the Python run call hands back.
Silence is the design, not an oversight. A genome decodes arbitrary 32-bit integers into vertex indices. If the graph rejected bad pairs, every operation would need a validity check and a decision about what to do when it fails. Instead an impossible edit is simply a no-op, and evolution routes around it. This is why five of the nine edge-edit operations do nothing on an empty graph without that being a bug.

Working with edges

CallDoes
add_edge(u, v) Adds one parallel edge, saturating at the cap. Reports whether the multiplicity actually changed — several operations only proceed if it did.
remove_edge(u, v)Removes one copy.
clear_edge(u, v)Removes all copies at once.
set_edge(u, v, w) Sets the weight directly, clamped to the cap. Silently ignores self-loops and out-of-range indices.
weight(u, v)Reads the multiplicity; 0 means no edge.
degree(u)How many distinct neighbours u has.
total_edge_multiplicity(u) Total edge copies at node u — despite the name this is a per-node figure, not a whole-graph one. On a multigraph it exceeds degree(u).
get_neighbor_at_index(u, i) The i-th neighbour of u, wrapping modulo the degree.
get_edge_list() Every edge once as (u, v, multiplicity) with u < v, row-major. This is what a run returns to Python.

Exact signatures and line numbers are on the graph.rs reference page.

What it deliberately is not

These are stated non-goals, so their absence reads as a decision rather than an oversight:

  • No directed edges. The matrix is symmetric by construction.
  • No variable node count. Every graph in a run has exactly network_size nodes.
  • No self-loops. The diagonal stays zero, and attempts to set it are ignored.
  • No node or edge attributes. An edge is an integer count and nothing else.
  • No sparse storage. The dense matrix is what makes every operation O(1) and expression cheap; the cost is memory, and it is quadratic in the node count.
The cap is not an SDA-only concern. max_edge_multiplicity motivates the SDA Alphabet, but it applies under every genome: a cap of 0 would clamp every edge to zero weight and give a permanently empty graph, which looks like a broken fitness function rather than a bad config. Validation therefore requires 1 ≤ cap ≤ 255.
