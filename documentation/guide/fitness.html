How it works

Fitness & orientation

A fitness function turns a graph into one number. Everything else on this page is about a single question that turns out to matter enormously: which direction is better, and who is allowed to know.

The contract

pub trait Fitness: Send + Sync {
    fn evaluate(&self, graph: &Graph) -> f64;
    fn direction(&self) -> Direction { Direction::Minimize }
    fn evaluate_batch(&self, graphs: &[Graph]) -> Vec<f64> { /* par_iter over evaluate */ }
}

evaluate returns a score in the objective's own units and sign — nothing is normalized, scaled or flipped for you. direction declares whether bigger or smaller is better. evaluate_batch scores a whole population at once, and exists so that a Python Objective pays one crossing per batch rather than one per individual.

Why declare a direction instead of just negating?

Because the two could then silently disagree. If evaluate returned an already-negated value and the trait declared Maximize, the run would optimize backwards — and a run optimizing backwards is indistinguishable from one that simply is not converging. Declaring it puts the fact in exactly one place.

Direction belongs to the objective, never to config. One fitness function is always maximized or always minimized; it is a property of what the function computes, not of the run. A config field that could say otherwise would only let it contradict the objective. A Python objective declares its direction when the callable is registered, because nothing can infer it from your function.

Your units and the engine's

There are two number systems, and every value in GET belongs to exactly one of them.

What it is
Your units Whatever your objective naturally returns. epi_spread counts infected nodes, so bigger is better. epi_prof_match is an RMSE, so smaller is better.
Engine orientation One rule, no exceptions: lower is better. Selection, elitism and replacement all assume it, which is what lets them work without ever asking what the objective was.

The conversion between them is a negation — and negation is its own inverse, so one function maps both ways. The entire design is about calling it in exactly two places.

One gate: express_and_score

common::express_and_score(batch, context, fitness) -> (Vec<Graph>, Vec<f64>)

This one function expresses every genome in parallel, scores the batch, applies the direction conversion, and rejects NaN. The fitnesses it returns are always lower-is-better, whatever the objective. Index i of both vectors is population[i].

It is the engine's single point of conversion, and the reason is that it is the only place the whole population is scored — so it is the only place "exactly once" can be guaranteed rather than remembered. The alternative, a direction-aware comparator, would need the direction at every comparison site: tournament ordering, the generational argmin, the steady-state best. A missed one fails silently.

The engine never calls Fitness::evaluate or evaluate_batch directly. express_and_score is the sole path from a batch of genomes to a set of fitnesses — generational scoring, steady-state child scoring, everything. The two trait methods exist to be implemented by an objective and called by express_and_score, never by the engine. A direct call would bypass orientation and the NaN rejection, and neither failure announces itself. Any new evolution strategy scores its population through this function or it is wrong.

NaN is forbidden; infinity is not

NaN is rejected at the gate, and the reason is sharper than it looks. Under minimization NaN sorts beyond +inf and reads as worst, which would be safe. But under Maximize the value is negated — and -NaN sorts below -inf, making it the best individual in every tournament it enters. One NaN from a maximizing objective fills the population with whatever genome produced it and leaves a run that looks converged.

±inf is allowed, deliberately. +inf under Minimize is the sanctioned way to say this individual is invalid, never select it. Removing it would push people toward a magic large number, which is worse because it stays silently comparable.

The three built-in objectives

All three read the same simulation. The expensive part of an evaluation is the epidemic, so one run returns everything and each objective is a thin reading of it: 

sir_sim(graph, params, rng) -> Epidemic { length, spread, profile }
ObjectiveReadsDirectionUse it when
epi_spreadTotal ever-infectedMaximize You want a network the disease saturates.
epi_lengthTimesteps to burn outMaximize You want a network that keeps an outbreak alive a long time.
epi_prof_matchRMSE against a target curve Minimize You have a real epidemic curve and want a network that reproduces its shape.

Each direction is fixed by the objective and is never configurable. What the simulator actually does — including the one-timestep infectious period and the trailing zero in the profile — is on The SIR Model.

How epi_prof_match handles a length mismatch

Your target and the simulated run will usually be different lengths. The rule is fixed by the target:

  • iterate 0 .. target.len(), never the run's length;
  • where the run is shorter, treat its value as 0 — the epidemic had ended, so nobody was newly infected that day;
  • where the run is longer, the surplus is ignored;
  • divide by target.len() always, then take the square root.
That asymmetry is deliberate and it changes what you are selecting for. A run that burns out early is penalised by the whole remaining target; a run that outlasts the target is not penalised at all. So this objective rewards matching or exceeding the target's tail, not matching it exactly. It is inherited from the original C++ for comparability with archived results.

Averaging, and why noise matters here

num_epidemics is how many independent outbreaks one evaluation averages over. It is not a tuning nicety. A single SIR draw is very noisy, and selection will happily chase that noise instead of graph structure — you would evolve lucky dice rather than good networks. It also dominates run time, since everything else in an evaluation is cheap by comparison.

The dice themselves are handled carefully enough to need their own page. The short version: within one evaluation every member of the population faces the same epidemic draws, so fitness differences reflect the graph rather than the dice; across evaluations the draws change, so a network cannot keep winning on one frozen sample of the disease.

Writing your own

Two routes, and neither is a fallback for the other — see Add an objective for both in full.

RouteWhat it looks likeFor
Python set_fitness_function(callable, direction), taking the whole batch at once Most users, and any prototype. No Rust, no compilation, config-driven.
Rust Depend on get as a crate, impl Fitness, drive an evolver directly A hot native objective, without forking GET.
Keep hot objectives native. The Python adapter is for prototyping, where developer speed matters more than run time. A per-individual Python objective can be hundreds of times slower wall-clock than parallel Rust; batched, only the speed of the Python body remains.

A user-supplied objective deliberately never gets a [fitness] variant of its own. The alternative — a string-keyed registry that config could name — would move validation out of the parser, which is exactly the failure the one-validator design exists to prevent. Keeping user objectives out of the schema means nothing user-supplied is ever deserialized, so there is nothing new to validate.
