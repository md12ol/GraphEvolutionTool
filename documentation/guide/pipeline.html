How it works

The pipeline

One loop, four stages, and a small number of rules about who is allowed to do what. This page is the map; every stage has its own page with the detail.

The loop

GET is an evolutionary algorithm. It keeps a population of candidate solutions, scores them, lets the better ones produce children, and repeats. The only thing that makes it a graph evolution tool is what a candidate solution is and how it gets scored.

Stage by stage

1. Config in, validated once

A run starts from a config document. Whether you wrote it as TOML by hand or built it out of Python objects, it ends up as the same Rust Config struct, and Config::validate checks it before a single graph is allocated. A bad config is a user mistake, so it comes back as a Python exception naming the offending field — never a panic crossing the FFI boundary. Everything downstream is allowed to assume the config is sane.

2. Two front ends, one parser

The Python configuration objects do not parse anything. They serialize to TOML, and that TOML is what Rust parses: 

Python config objects ──serialize──> TOML ──serde──> Config ──validate──> run
                                              hand-written TOML ─┘

Two things fall out of that, and both matter in practice. There is exactly one parser and one validator, so the Python path cannot accept a configuration the file path would reject. And the generated TOML is a provenance record: write it next to your results and the run can be reproduced verbatim.

3. Dispatch picks the concrete types

The engine is statically generic over the genome — Evolver::run is a generic method, so there is no Box<dyn Evolver> and no dyn Genome. Runtime choice is resolved by a match in dispatch.rs that instantiates real types.

The two axes are not symmetric, and only one of them is a match:

  • Genome cannot be erased. mutate and crossover are generic over the RNG, crossover takes &mut Self, Clone requires Sized, and Context is an associated type that differs per representation. So strategy × genome stays a match.
  • Fitness can be. No generic methods, no Self in argument position, and dyn Fitness is Send + Sync. The objective is erased to Box<dyn Fitness> before the evolver is built, which collapses dispatch from strategy × genome × objective down to strategy × genome.

The practical consequence: adding an objective is one match arm and never touches dispatch, while adding a genome or a strategy multiplies the dispatch table. See Add an Objective.

Dispatch also builds the starting population. The evolver deliberately cannot mint genomes: constructors differ per representation and some are fallible. Dispatch is where genome-specific knowledge already lives, so it builds the population and hands it in. That is what keeps bad dimensions a startup error rather than a mid-run panic, and it is why evolvers are testable from a hand-built population.

4. Express — genome to graph

Every genome in the population is expressed into a Graph, in parallel across rayon workers. Expression is pure Rust and holds no Python lock. See Genomes for what each representation does here.

5. Score — graph to a number

Each graph gets one f64. For the three built-in objectives that means running num_epidemics SIR simulations on the graph and reading one number off them. Scoring is batched: the whole population goes over in one call, which is what makes a Python objective viable at all.

6. Orient — the one conversion

Objectives return values in their own units and sign; the engine only ever minimizes. The conversion happens in exactly one function, common::express_and_score, which is also the gate that rejects NaN. This is important enough to have its own page — including why a single NaN from a maximizing objective can silently take over a whole run.

7. Select, breed, mutate

Tournament selection picks parents; crossover_rate decides whether a pair recombines; two further rolls decide whether and how much each child mutates. All of it is owned by the engine rather than the genome — see Crossover & mutation.

8. Out

A run produces an EvolutionOutcome: the best genome, its already-expressed graph, its fitness, and the full run history. The Python boundary converts fitness back into your units on the way out. See Logs & Results.

The three bounds that make it parallel

These appear on the traits and look like boilerplate. They are not — each is load-bearing, and removing any one of them stops the pipeline compiling in parallel form:

BoundWhy it is there
Genome: Clone + Send + Sync The population is expressed across rayon workers. Clone is how an individual is copied — there is no copy method.
Genome::Context: Send + Sync One &Context is shared by every worker during expression. Parallel expression does not compile without it.
Fitness: Send + Sync The default batch scorer fans out with par_iter.

Net effect: expression and native scoring are both parallel and free of the Python GIL. That property is exactly what makes the batched Python objective design work — see Performance & Memory.

Two rules worth memorising

The engine never calls Fitness::evaluate directly. common::express_and_score is the only path from genomes to fitness values, everywhere, in both strategies. A direct call would bypass orientation and the NaN gate, and neither failure announces itself.
Lower is better, inside the engine, always. Selection, elitism and replacement all assume it, which is what lets them work without ever asking what the objective was. Your units come back at the Python boundary.
