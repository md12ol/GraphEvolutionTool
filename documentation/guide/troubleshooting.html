Using GET

Troubleshooting

Symptom first, cause second. Most of these are documented behaviour rather than bugs — but they all look like bugs the first time.

Config errors

"missing field population_size" but I definitely wrote it

You wrote it after a [section] header. In TOML, once a table opens every following key belongs to that table — so your population_size became evolution.population_size, which GET does not know, and the real top-level key is genuinely missing. All top-level keys must appear before the first section header.

The error names a field I did not write

You setThe error saysBecause
num_states = 0init_state The init_state < num_states check fires first, and 0 < 0 is false.
population_size = 0 elite_count or tournament_size Nothing checks population_size by name; it is caught indirectly by whichever constraint it breaks first.

My change to a config value did nothing

Most unknown keys are silently ignored. A misspelled key does not error — it simply is not read, and the default applies. Two exceptions: [genome.operation_weights] rejects unknown keys, and two migration hazards are checked by name ([fitness] seed, and target_profile under the wrong objective).

Check by printing config.to_toml() and reading what GET actually received. That is the document it parsed.

"tournament_size must be at least 4" — but it worked yesterday

You switched to steady_state. That floor is strategy-specific: steady-state needs four distinct individuals per event (two parents and the two they replace), and generational has no such requirement. Switching strategies can invalidate a previously fine selection block.

My config validated and then run() raised

Two SDA dimensions — num_states outside 1..=65536, and max_resp_len = 0 — are checked when the population is minted rather than during validation. A config that loads cleanly can still fail on the first run.

The run behaves oddly

Nothing happens for the first many generations (edge-edit)

Expected. A run currently starts from an empty base graph, and five of the nine edit operations — Swap, Hop and the three Local* — need existing structure to walk. Until Add or Toggle have built something, more than half the operation mix does nothing. It is self-correcting.

To speed it up, weight add and toggle higher for the early phase, or set null = 0.0 so no gene is a deliberate no-op.

The fitness barely moves, or moves erratically

SuspectCheck
num_epidemics too low A single SIR draw is very noisy, and selection will chase that noise rather than structure. This is the most common cause by a distance.
Selection pressure too lowRaise tournament_size.
Too little variation Raise mutation_rate, or max_mutations — they mean different things.
Too much variation An SDA mutation can change every character after the one it touched, so a high max_mutations is far more disruptive there than for edge-edit.
infection_rate at an extreme At a rate so low that nothing spreads, or so high that everything does, every graph scores the same and there is nothing for selection to work with.

The population converged, but the answer is poor

Under steady-state with a stochastic objective, suspect stale fitnesses. Only the two new children are scored per event, so an individual that drew lucky dice keeps its inflated score for the rest of the run — nothing rescores it — and it wins tournaments it should not. Prefer generational when the objective is stochastic, which all three SIR objectives are.

The run looks converged almost immediately

If your own objective can return NaN, that is the first thing to check. Under a maximizing objective a NaN sorts as the best individual in every tournament, and fills the population with whatever produced it. GET rejects NaN at the gate, so you will get a failure rather than this — but only for values that pass through the gate. See Fitness & Orientation.

Every edge weight is 1 when I set the cap to 5

Something narrowed the cap. set_edge clamps rather than rejecting, so feeding a cap-5 result into a cap-1 run silently collapses every weight — this is the main trap when stacking two runs. Check that both configs carry the same max_edge_multiplicity.

My epi_prof_match scores look wrong

  • A profile copied from a legacy C++ run is wrong twice over. The old loader prepended patient zero, so the stored file omitted its own first element, and it rescaled every value by verts / 128. GET does neither and compares your profile verbatim.
  • Include the trailing zero. A GET profile always ends in one.
  • Overshooting is free. The RMSE iterates over the target's length only, so a run that outlasts the target is not penalised for the surplus at all, while one that burns out early is penalised by the whole remaining target. The objective rewards matching or exceeding the tail.

Values that surprise you

A probability outside [0, 1] runs happily

crossover_rate, mutation_rate and infection_rate are not range-checked. This is a gap in the design as well as the code. Check your own numbers.

The log's ci_95 is not the band on my plot

Correct — they are different statistics. ci_95 is within-population, per iteration: how tightly this generation is clustered around its own mean. The band on a published convergence plot is usually across replicates, computed when replicate logs are aggregated. See Logs & Results.

std_dev and ci_95 use different denominators

Deliberately. The population deviation divides by n because the population is the complete thing, not a sample; the confidence interval divides by n-1 because it is inherently a sampling statistic.

Performance

The run is far slower than expected

  • num_epidemics dominates run time. Everything else in an evaluation is cheap.
  • A per-individual Python objective is the classic disaster — it serializes every call behind the interpreter lock and throws away all the parallelism. It must be batched.
  • A Python objective with steady-state pays one crossing per mating event. Use generational.
  • A high min_epidemic_length on a graph that fizzles often means most evaluations pay for several simulations instead of one.

It ran out of memory after I gave it more cores

Expected, and it is the least intuitive thing in GET. Each concurrently-executing replicate holds its own expressed population, and a graph is a dense network_size² matrix regardless of how sparse it is. Doubling the cores doubles peak memory. The arithmetic and a worked table are on Performance & Memory.

A single steady-state run leaves my machine idle

Also expected. Steady-state scores two children per event, so its population-level parallelism is two-way regardless of the core count. Replicates are the only way to fill a big machine with it.

Build problems

import get fails after building

Check you built into the environment you are importing from — maturin develop installs into the active virtualenv. pip install . from the repository root is the alternative.

cargo test fails to link with undefined Py* symbols

The Python extension-module feature has been enabled in the crate's own manifest. It belongs in the build configuration instead, and enabling it in the crate makes the whole test suite fail to link regardless of how few tests touch Python. Use cargo test and maturin develop as separate commands.

Still stuck

Print config.to_toml() and read what GET actually parsed — a surprising number of problems are visible there in one line. Then check Implementation status, in case the thing you are reaching for is one of the pieces documented as designed but not yet built.
