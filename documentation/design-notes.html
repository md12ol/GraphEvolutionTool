Design notes

Why GET is shaped the way it is. Every decision here was made because the alternative fails silently — that is the thread running through all of them, and it is worth reading before changing anything structural.

The organising principle: make silent failure impossible

An evolutionary run that is subtly wrong looks exactly like one that is merely not converging. There is no crash, no stack trace, and no obviously bad number — just a curve that flattens out somewhere it should not have. Nearly every structural decision in GET is chosen to convert a silent failure into either an impossibility or a loud one.

Silent failure avoidedBy
Optimizing in the wrong direction One conversion point, not a direction-aware comparator. →
One NaN taking over the population Rejecting it at the same gate as the conversion.
An SDA alphabet biasing every graph Deriving it from the edge cap rather than configuring it. →
The Python front end accepting what a file would reject Making Python a builder for TOML, not a second parser. →
Reproducibility evaporating under load Per-run objective state, never shared across concurrent runs. →
Two config values disagreeing One source of truth for each — population size is the population's length, graph size belongs to the genome context.

Static generics, not trait objects

The engine is statically generic over the genome. That means no Box<dyn Evolver> and no dyn Genome, and runtime choice resolved by a match that instantiates concrete types.

This is forced rather than chosen. A genome cannot be a trait object because:

  • its mutation and crossover methods are generic over the random number generator;
  • crossover takes a mutable Self;
  • cloning requires a statically known size;
  • its context is an associated type that differs per representation.

Any one of those rules out erasure. Fitness has none of them — no generic methods, no Self in argument position, thread-safe through its supertrait — so the objective is erased, before the evolver is built. That asymmetry is the single most consequential shape decision in the codebase, because it collapses dispatch from strategy × genome × objective down to strategy × genome, and makes adding an objective free of dispatch entirely.

See Extension Points for what that costs each kind of addition.

One conversion, at one gate

Objectives return values in their own units and sign; the engine only ever minimizes. There are two obvious ways to reconcile that, and GET rejects the more common one.

ApproachFails how
A direction-aware comparator Needs the direction at every comparison site — tournament ordering, the generational argmin, the steady-state best. A missed one fails silently, and produces a run that looks like it simply is not converging.
One conversion in the batch scorer The only place the whole population is scored, so it is the only place "exactly once" can be guaranteed rather than remembered.

The same function is also the NaN gate: orientation and rejection share one door by design. And the invariant that makes it structural rather than habitual is that the engine never calls the fitness trait directly — anywhere, in either strategy.

Convert at the edges, never in the middle

An earlier design converted back immediately inside the statistics and the outcome, so a number flipped twice on a short trip and every internal type had to know the direction. The rule now is that everything inside the engine is lower-is-better and nothing in the middle converts. Three things fall out, and the third is the real prize:

  1. Exactly two conversions per run instead of one per statistics row.
  2. The statistics function loses its direction parameter entirely.
  3. The standard-deviation special case disappears. Deviation is invariant under negation, so a converting statistics function had to deliberately not convert it — an asymmetry that looked like a missed case and had to be defended by a test. When nothing converts internally, there is nothing to except.

The stated cost: a Rust embedder reading the outcome directly gets engine-oriented numbers. That is what the direction carried on the outcome is for.

Why the graph is silent and dense

A genome decodes arbitrary integers into vertex indices. If the graph validated them, every operation would need a check and a decision about what to do when it fails. Instead, self-loops and out-of-range vertices are ignored, and an impossible edit is simply a no-op that evolution routes around. That is why expression cannot fail and returns a graph rather than a result.

Dense storage is the other half. Every operation is constant time and expression is cheap; the cost is memory that grows with the square of the node count, and multiplies by the population and the concurrency. That trade is documented rather than hidden, because the failure mode — raising the core count and exhausting memory on hardware that coped before — is genuinely unintuitive.

Why replicate seeding is a stream

One master seed feeds a generator whose output is the per-run seed list. The property this buys, and which is easy to lose: a run's seed must not depend on how many runs you asked for. Ask for 50 and the first 30 reproduce exactly, so extending an experiment never invalidates the replicates you already have.

master + i or a hash of the two would work equally well. master ^ i would not, because nearby masters collide across run indices.

Two things accepted as costs, not solved

The epidemic re-roll is a biased resample

Discarding outbreaks shorter than a threshold shifts expected fitness upward, by an amount that depends on how often a given graph fizzles. It is therefore not interchangeable with averaging more epidemics, and the two do different jobs. It is kept because a fizzled outbreak carries no information about the graph — it reports the dice — and because the historical results GET is compared against were produced with it. Both constants are exposed rather than hardcoded precisely because the bias is real. →

Steady-state carries stale fitnesses

Incremental scoring plus a stochastic objective means the population's recorded fitnesses were computed under different dice than the children being compared against them. The alternatives — rescoring periodically, or freezing the seed across a generation equivalent — each trade it for a different distortion rather than removing it. So it is accepted and documented, with the guidance to prefer generational when the comparison needs to be fair. →

Smaller decisions, each with a reason

DecisionBecause
The evolver never builds genomes Constructors differ per representation and some are fallible. Dispatch builds the population, so bad dimensions surface at startup, and evolvers stay testable from a hand-built population.
Both crossover children are kept Crossover inherently produces two. Keeping one wastes half of every crossover.
mutate applies exactly one mutation A genome that rolled its own count would make max_mutations meaningless for that representation, and nothing would report it.
Direction is not configurable One objective is always maximized or always minimized. A config that could say otherwise would only let it contradict the objective.
A user objective gets no config variant A string-keyed registry would move validation out of the parser — the exact failure the single-validator design prevents. Nothing user-supplied is ever deserialized, so there is nothing new to validate.
The seed is not in the config The seed describes this invocation; the config describes the experiment. A separately configured fitness seed would leave replicates facing identical epidemics, which is what replicates exist to vary.
Validation is a function, not a parse side effect The Python front end bypasses the parser entirely. Without one shared validator it would silently accept what a file rejects — and Python is the path users take.
Validation returns an error, never panics A bad config is a user mistake. A panic crossing the FFI reaches the user as an opaque exception they cannot act on.
A pinned random generator, not the library default The default's algorithm may change between releases, which would defeat the entire purpose of a seed argument.
Epidemics within an evaluation run serially The two levels above already provide more independent work than any core count, and serial epidemics make each parallel task larger.
The engine chooses the replicate mode, not the user The fitness type already determines the correct answer, so a setting would only create a way to choose wrong.
Thread pool built per call, not globally A global pool configures once per process, and this is an extension module imported once per session — so the core cap would belong to whichever call happened first.
The reported best is the final population's best A running best under a stochastic objective is largely a record of which iteration drew the luckiest sample. And a non-elitist run genuinely can lose its best — reporting otherwise describes a population that no longer exists.
Tournaments break ties by lower index So an outcome depends only on which indices were drawn, not on the order the generator produced them.
A Python objective must be batched Per-individual callbacks serialize behind the interpreter lock, losing all the parallelism the expression stage just bought — orders of magnitude, not percentages.

Non-goals

Stated so their absence reads as a decision rather than an oversight.

Not in GET
Multi-objective optimization One f64 per individual. The pymoo-shaped interface is about the batched call signature, not about optimizing several objectives — there is no Pareto front, no non-dominated sorting, no crowding distance.
Fixed-length runs A run ends after its configured generations or mating events. No convergence detection, no stagnation cutoff, no target-fitness early stop.
Fixed-size genomes Gene length and the SDA dimensions are set once per run. Crossover tolerates unequal lengths defensively, but nothing produces them.
No random immigrants or restarts They would require putting genome-minting capability back into the engine, which the design deliberately removes.
Fixed node count Every graph in a run has network_size nodes.
One populationNo islands, no migration.

One item is a "not yet" rather than a "never": additional crossover operators per representation are wanted, and are sequenced after the rest of the design. Until a second operator exists there is nothing to select between, so no enum, no config field and no dispatch is built for it. When it lands it follows selection — one variant, one match arm, one config field.

Conventions, in one place

  • Lower is better inside the engine, always.
  • Fitness crosses back into the objective's own units only at the reporting boundary.
  • All randomness derives from one user seed.
  • Every value has exactly one source of truth.
  • A bad configuration is an error naming its field, never a panic.
