Source reference

genomes/edge_edit.rs

The edit-script genome: a fixed-length list of packed 64-bit integers, each one an instruction to add, remove or rewire an edge, applied in order to a starting graph. Where the automaton builds a graph from nothing, this one refines one. Concepts are in Genomes; the nine operations themselves have their own page.

What it is

A genome is a Vec<u64>. Each u64 is one gene, and each gene encodes one graph edit: an opcode in the low four bits saying which of nine operations to perform, and a 32-bit payload above it that gets unpacked into four vertex parameters.

Expression clones the base graph and applies every gene in order, each one seeing the graph as the previous one left it. The critical consequence: the genome is a script, not a graph. The same genome expressed against a different base graph gives a completely different result, and the genes have no meaning at all in isolation.

fn decode_vertices(gene: u64, num_nodes: usize) -> [usize; 4]
genomes/edge_edit.rs:182

Private. Shifts the opcode off and reads what is left as a number written in base num_nodes, peeling off four digits. Each digit is guaranteed to be a valid vertex index because it is a remainder modulo the node count: 

p  = gene >> 4
v1 = p % n
v2 = (p / n) % n
v3 = (p / n²) % n
v4 = (p / n³) % n

This is why the graph never has to validate a vertex pair — decoding cannot produce an out-of-range index in the first place. The one thing it can produce is a self-loop (v1 == v2), and every operation rejects that.

The formula is pinned to the legacy graph_refiner implementation by a test at edge_edit.rs:408–418 that checks agreement digit for digit across several node counts.

The payload is 32 bits but four base-n digits need n⁴, so v3 and especially v4 are biased toward low values on large networks. A u32 tops out at 4,294,967,295, and v4 is payload / n³. Two concrete cases:
  • n = 1000: n³ is one billion, so payload / n³ can only ever be 0, 1, 2, 3 or 4. v4 names one of five vertices out of a thousand, and not even uniformly — 0 through 3 come up about 23.3% of the time each and 4 about 6.9%.
  • n = 257: n³ is 16,974,593, so the quotient reaches at most 253. Vertices 254, 255 and 256 are never named by v4 at all.
How much this actually costs you is smaller than it looks, and worth being precise about. v1 and v2 — the plain vertex identifiers used by Add and Delete — are the least affected, since they are the low-order digits. v3 and v4 are mostly used as neighbour indices, which wrap modulo a node's degree, so a value biased into a small range still spreads reasonably over a low-degree node's neighbours. The one place it bites cleanly is LocalToggle's direction parameter, which is v4 and is read for its parity: at n = 1000 that parity comes out even about 53.4% of the time rather than 50%. Toggle's own direction is v3 and is close to uniform.

Nothing in the code or the spec sheet mentions any of this. It is inherited deliberately from the legacy implementation rather than being accidental — the test at edge_edit.rs:409–418 explicitly exercises n = 257 to keep the behaviour pinned — but nobody wrote down that the bias is a consequence.

Operation weights

pub struct EdgeEditOperationWeights { pub toggle: f64, pub hop: f64, pub add: f64, pub delete: f64, pub swap: f64, pub local_toggle: f64, pub local_add: f64, pub local_delete: f64, pub null: f64 }
genomes/edge_edit.rs:30

Nine numbers controlling how often each operation is generated. They are relative weights, not percentages — nine 1.0s and nine 7.0s mean exactly the same thing. Set them under [genome.operation_weights] in config.toml.

Every field defaults to 1.0 (edge_edit.rs:73–87), so any field you omit falls back to equal probability, and a weight of 0.0 disables its operation outright. The struct is #[serde(default, deny_unknown_fields)] (edge_edit.rs:29), which means a misspelled key is rejected at load time rather than silently ignored — a typo in a weight name is an error, not a shrug.

pub fn validate(&self) -> Result<(), &'static str>
genomes/edge_edit.rs:44

Two rules, both checked here:

  • every weight must be finite and non-negative, else "operation weights must be finite and non-negative";
  • at least one must be strictly positive, else "at least one operation weight must be positive".

The second rule is what stops an all-zero mix, which would leave nothing to sample from. Config::validate calls this before anything runs, so a bad mix surfaces as a config error naming the field.

fn values(&self) -> [f64; OPERATION_COUNT]
genomes/edge_edit.rs:58

Private. Flattens the nine named fields into an array in opcode order: toggle, hop, add, delete, swap, local_toggle, local_add, local_delete, null. This array is what becomes the sampler, so the array's index is the opcode.

The order of values() and the order of GraphOperation::from_opcode are the same mapping written twice, and nothing enforces the agreement. values() at edge_edit.rs:58–70 lists the weights in one order; from_opcode at edge_edit/operations.rs:19–30 maps integers to operations in another. They currently agree exactly — index 0 is toggle in both, index 4 is swap in both — but the agreement is carried by nothing except the two lists happening to be written the same way. There is no shared enum, no derive, no assertion.

Get one wrong and weights silently attach to the wrong operations: you would set swap = 0.0 and disable delete instead, with no error anywhere and a run that simply explores differently than you asked. The only thing that would catch it is the one test that zeroes eight weights and asserts the surviving opcode (edge_edit.rs:338–346), and that test pins a single opcode rather than the whole mapping. Anyone adding a tenth operation has to edit values(), from_opcode, the GraphOperation enum, the apply match and OPERATION_COUNT at edge_edit.rs:15, and only the last of those will fail to compile if forgotten.

The shared sampler

pub struct EdgeEditOperators { /* private: weights, distribution */ }
genomes/edge_edit.rs:98

A validated weight mix together with the WeightedIndex sampler compiled from it. Built once per run and shared by the whole population behind an Arc, so each individual carries a pointer rather than its own copy of the table.

The weights field is kept alongside the sampler purely so the type stays readable in debug output and comparable in tests — nothing samples from it.

Expression

fn express(&self, context: &EdgeEditContext) -> Graph
genomes/edge_edit.rs:203

Clone the base graph, then run the script over the clone.

  1. context.base_graph.clone() (edge_edit.rs:204). The base graph itself is never modified — it is shared read-only across every worker expressing every individual, and a test asserts it comes out untouched (edge_edit.rs:365–384).
  2. If the graph has zero nodes, return immediately (edge_edit.rs:205–207). This guard is load-bearing: decoding divides by the node count, so zero nodes would be a division by zero.
  3. For each gene in order: look up the opcode (edge_edit.rs:213), decode the four vertices (edge_edit.rs:216), and apply (edge_edit.rs:217).

The clone inherits the base graph's multiplicity cap, so an unweighted base graph stays unweighted no matter what the script does (edge_edit.rs:386–400).

Unknown opcodes are skipped, not rejected. The opcode field is four bits and holds 0..=15, but only 0..=8 are defined. A gene carrying 9 through 15 is simply passed over (edge_edit.rs:213–215) and the next gene runs. This is unreachable from generated genes — the sampler only ever produces 0..=8 — but entirely reachable if you hand a raw Vec<u64> to EdgeEditGenome::new.

Worked example

Five nodes, unweighted (cap = 1), starting from a path 0—1—2—3—4 — edges (0,1), (1,2), (2,3), (3,4).

Genes are ordinary integers, so we can write them out exactly. With payload = v1 + v2·n + v3·n² + v4·n³ and gene = (payload << 4) | opcode at n = 5:

#OperationOpcode(v1,v2,v3,v4)payloadgene
1Add2(0,4,0,0)0 + 4·5 = 20322
2Hop1(0,0,1,0)1·25 = 25401
3Toggle0(1,3,0,0)1 + 3·5 = 16256
4Null8(0,0,0,0)08

Sanity-check gene 2 by decoding it back: 401 >> 4 = 25; 25 % 5 = 0 so v1 = 0; 25 / 5 = 5 and 5 % 5 = 0 so v2 = 0; 5 / 5 = 1 and 1 % 5 = 1 so v3 = 1; 1 / 5 = 0 so v4 = 0.

Applying them in order

Gene 1 — Add(0, 4). The pair is valid and distinct, so add_edge(0,4) takes the weight from 0 to 1. The path has become a five-cycle 0—1—2—3—4—0, and every node now has degree 2.

Gene 2 — Hop(start = 0, first index = 0, second index = 1). Walk two hops from node 0. Node 0's neighbours in ascending order are [1, 4], so index 0 selects node 1. Node 1 has degree 2, so it is not a dead end. Node 1's neighbours are [0, 2], so index 1 selects node 2 — which is not the start, so the walk is accepted. add_edge(0,2) succeeds and returns true, so the hop commits and remove_edge(0,1) drops the original edge.

Edges are now (0,2), (0,4), (1,2), (2,3), (3,4). Degrees: node 0 has 2, node 1 has 1, node 2 has 3, node 3 has 2, node 4 has 2.

Gene 3 — Toggle(1, 3, direction = 0). The weight of (1,3) is 0, so the "absent → add" branch fires and the direction parameter is never consulted. Edge (1,3) appears.

Gene 4 — Null. Nothing, by design.

The result

get_edge_list() returns [(0,2,1), (0,4,1), (1,2,1), (1,3,1), (2,3,1), (3,4,1)] — six edges, with degrees 2, 2, 3, 3, 2.

Worth noticing what a fifth gene could not have done. A Swap here would do nothing at all. It requires both chosen vertices to have degree 3 or more, and only nodes 2 and 3 qualify — but those two are adjacent, and Swap also requires its two vertices to be non-adjacent. On a graph this small and sparse, Swap is inert almost always. The full precondition list is on the operations page.

Crossover and mutation

fn crossover<R: Rng + ?Sized>(&mut self, other: &mut Self, rng: &mut R)
genomes/edge_edit.rs:223

Two-point crossover over genes. A contiguous run of genes swaps between the parents.

  • Works over the shorter genome's length; a genome shorter than two genes is left alone entirely (edge_edit.rs:224–227).
  • start is drawn from 0..shared_length and end from (start+1)..=shared_length — an inclusive upper bound, so the segment can reach the last shared index (edge_edit.rs:229–232). The swapped segment is therefore never empty.
  • Any genes past the shared length stay where they are.
fn mutate<R: Rng + ?Sized>(&mut self, rng: &mut R)
genomes/edge_edit.rs:243

Pick one gene uniformly at random and replace it entirely — opcode and payload — with a freshly generated gene, its opcode drawn from the shared mix. An empty gene list returns unchanged.

Exactly one gene, per the mutation contract. This previously rolled 1..=4 internally against a hardcoded constant, which made the engine's max_mutations mean nothing for this representation. The count is the engine's to decide; if you want the old strength back, set max_mutations = 4. The test at edge_edit.rs:476–499 sweeps 64 seeds, because a single seed cannot tell "always one" from "one this time".

Crossover exchanges genes but not weight mixes. A gene generated under one mix can migrate into a genome carrying a different one, and a later mutation of that slot will reroll it under the new mix. In a config-driven run this can never be observed — the whole population shares one Arc — but it is a real edge case if you assemble a mixed population by hand.

The base graph

Expression needs something to edit. Where that comes from depends on how the run was started.

Supplying one from Python planned

A base graph is not a config value — it is either data you brought or the output of a previous run. So it arrives through a setter on the evolver, before run is called, rather than being serialized into the config document. Because a run already hands back (u, v, multiplicity) triples, the two representations stack with no new data format: evolve a topology with SDA, then refine it with edge-edit.

The setter owes three checks, all of which fail quietly if skipped:

  • The node count must match the configured network_size, or edges outside the range are silently dropped.
  • Cap narrowing must be rejected or warned about. This is the main stacking trap: set_edge clamps, so piping a cap-5 result into a cap-1 run silently collapses every weight to 1.
  • With no base graph supplied the run starts from an empty graph, which leaves five of the nine opcodes inert until Add or Toggle have built some structure.
What exists today. dispatch.rs always constructs an empty base graph at the configured network size and cap (dispatch.rs:236–238), so every config-driven edge-edit run currently starts from nothing. The setter is tracked as GitHub #28. You can already supply a base graph today from Rust by building an EdgeEditContext yourself and driving an evolver directly — see Extension points — which is what the worked example above assumes. Check Implementation status for where this stands.
Five of the nine operations do nothing on an empty graph, and that is not a bug. Swap, Hop and the three Local* operations all need existing structure to walk over. A from-scratch edge-edit run therefore does very little until Add and Toggle have built something for the others to act on. It is self-correcting — once there are edges, the rest come alive — but it does mean early generations look flatter than you might expect, and it is a reason to prefer a seeded base graph when you have one.
