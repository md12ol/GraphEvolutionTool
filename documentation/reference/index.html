Source reference

Module map

Every file in get/src/, what it owns, and where it sits in the stack. Start here when you know what you want to change but not which file holds it. The pipeline page is the same story told for someone learning how GET works rather than editing it.

The stack in one picture

The crate has a strict dependency direction, and it is worth learning before anything else because it explains most of the design decisions you will meet. The engine at the bottom knows nothing about configuration or Python. Only the top two layers do.

Top: the Python boundary

lib.rs

The crate root and the entire Python-facing surface. It declares every module, defines GraphEvolver — the object you construct from Python — and registers the seven configuration classes on the module. Its methods are the whole API: build an evolver from a file or from Python objects, register a Python fitness callable with its direction, and run(seed). It is also where the Python lock is released for the duration of a run, so a long evolution does not freeze the host interpreter. It contains no algorithm of its own; every method here is a thin wrapper over something below.

Middle: configuration and dispatch

config.rs

The schema, and the single validator behind both front ends. It defines the plain Rust types that a config.toml deserializes into — the top-level settings plus four tagged sections for the evolution strategy, selection, genome and fitness objective — and one validate function that checks every constraint the design lists and returns an error rather than panicking, because a bad config is a user mistake and a panic crossing into Python is unactionable. It builds nothing. If you want to know which keys exist, what they default to and what happens when one is wrong, this page carries the full reference table.

py_config.rs

The Python mirror of every type in config.rs, and nothing else. The objects you fill in from Python do not parse anything — they serialize to TOML, and that TOML is what the Rust side parses, so both routes converge before a single key is interpreted. The payoff is that the Python path cannot accept a configuration a file would reject, and config.to_toml() hands you an exact provenance record of what ran. This module also owns the translation of a validation error's field name into the Python attribute path that produced it, so a message about num_epidemics arrives as config.fitness.sir.num_epidemics.

dispatch.rs

Config in, running machinery out. This is the only module that knows both the schema and the engine, and every runtime choice is resolved here and nowhere else. It works in two steps: the fitness objective is hidden behind a pointer first, which collapses the problem from strategy × genome × objective down to strategy × genome, and only then are the genome and strategy matched. It also mints the starting population, because genome constructors differ per representation and the generic evolver deliberately cannot call them. Crate-private: a Rust user embedding GET drives an evolver directly and never comes through here.

Engine: the genetic algorithm itself

evolver/common.rs

The mechanics both strategies share, kept in one place so the two cannot drift apart: tournament selection, parallel expression and scoring of a whole population, the per-generation statistics row, and the two mutation rolls. It owns the single most important function in the engine — the one gate every fitness value passes through, which expresses the batch, scores it, rejects NaN, and applies the direction conversion exactly once. Nothing else in the engine is allowed to call an objective directly. The module tree above it, evolver/mod.rs, defines the evolver interface, the shared context and the outcome type, and has no page of its own.

evolver/generational.rs

One of the two strategies: the whole population is replaced each generation, with a configurable number of elites copied forward unchanged. Every individual is rescored each generation, elites included, which under a stochastic objective means an elite's recorded fitness moves while its genome does not — correct, because the new number is a fresh sample of the same individual. Prefer this one when the objective is stochastic and the comparison needs to be fair.

evolver/steady_state.rs

The other strategy: one mate-and-replace event at a time, so most of the population persists between events. Each event draws a single tournament, its two best breed, and the two children overwrite that same tournament's two worst — tournament-local rather than global, which makes it self-elitist and cheap. Only the two new children are scored per event, which is what makes it a poor fit for a Python objective and limits its parallelism to two-way however many cores you have.

fitness.rs

The objectives and the sign rule that makes them comparable. It defines the fitness interface, the direction that belongs to an objective rather than to your config, the three epidemic objectives built on a shared scorer that owns epidemic seeding, and the adapter that wraps a registered Python callable. The batched contract lives here too: one call receives the whole population, because a per-individual callback would serialize every score behind the Python lock and lose all the parallelism the engine was built for.

Primitives

graph.rs

An undirected multigraph on a fixed node count, stored as a symmetric adjacency matrix of weights. Weight zero means no edge; a weight above one means that many parallel edges. Two of its behaviours are relied upon everywhere and surprise people: setting an edge clamps to the cap rather than rejecting, and self-loops and out-of-range vertices are silently ignored — genome expression depends on that second one, since a decoded vertex pair is never validated before use.

genomes/genome.rs

The interface every representation implements: express yourself into a graph, recombine with another genome, mutate, and print yourself. It also defines the two expression contexts, which carry run-level configuration and are the authority on graph size and edge cap. Two details here are load-bearing across the whole crate — recombination happens in place, leaving one child in each parent, and mutation applies exactly one mutation per call, so the engine rather than the genome decides how many a child takes. The module file beside it, genomes/mod.rs, is seven lines of re-exports and has no page.

genomes/edge_edit.rs

The first representation: a genome is an edit script applied to a base graph, one packed operation per gene. Expression clones the base graph and applies every gene in order, so the same genome against a different base graph gives a different result. It also owns the nine operation weights, which are relative rather than percentages, are validated once at startup, and are compiled into a sampler the whole population shares behind one pointer.

genomes/edge_edit/operations.rs

The nine edit operations themselves — add, delete, toggle, their three local two-hop variants, the edge-moving hop, the 2-opt swap, and a deliberate no-op. All nine are no-ops when their preconditions fail. Worth reading before you tune the weights, and worth knowing that five of the nine need existing structure to walk, so they do nothing at all on a run that starts from an empty graph until add and toggle have built something.

genomes/sda.rs

The second representation: a self-driving automaton that generates a graph from scratch rather than editing one. It emits one character per upper-triangle vertex pair, and each character's raw value is that edge's weight. The alphabet is derived, never configured — it is the edge cap plus one, so every character the automaton can emit is a legal weight and none is ever clamped away. There is deliberately no num_chars setting.

sir.rs

One SIR epidemic over an expressed graph, ported from the legacy C++ that this project has always simulated. A node infected during a step spends the following step infectious, then recovers and never infects again. One simulation returns everything all three epidemic objectives need — length, total spread, and the profile of newly-infected counts per timestep — because the simulation is the expensive part and each objective is a thin reading of it. It takes its random generator as an argument rather than reaching for a global, which is what lets one seed drive a whole batch of graphs.

Where to start, by task

You want to…Read
Look up a config key or work out why one was rejected config.rs, or the friendlier Configuration reference
Write a run in Python py_config.rs and lib.rs
Add a new fitness objective fitness.rs, then one arm in dispatch.rs
Add a new genome representation genomes/genome.rs, then dispatch.rs
Understand why a maximizing objective's numbers are negative inside the engine Fitness & orientation
Understand what one seed actually reproduces Seeds & reproducibility and dispatch.rs
Embed GET as a Rust library rather than through Python fitness.rs and evolver/common.rs — the Rust route does not go through dispatch at all
Two front doors, and neither is a fallback for the other. Most users register a Python callable and drive everything from config. Advanced users depend on get as a Rust crate, implement the fitness interface for their own type, and drive an evolver directly — which needs no dispatch arm, because the evolver is generic over the objective. The engine types stay public specifically to keep that second door open.
