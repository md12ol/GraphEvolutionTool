The epidemic simulator: one outbreak over one graph, and the machinery that samples several of them reproducibly. If you have never met an epidemic model, start at What SIR is — this page is written to be read from cold, and the worked walkthrough is the part to read twice.

Source: get/src/sir.rs, 701 lines, of which 392 are tests. built — implemented, and matching the spec sheet §5.2 including the 2026-08-04 amendment about the burnout step. See The SIR Model for the modelling background and fitness.rs for the three objectives that read its output.

What SIR is

SIR is the standard way to describe an outbreak spreading through a group. Every individual is in exactly one of three states at any moment:

StateMeansCan catch it?Can pass it on?
S — SusceptibleHealthy, not yet infectedYesNo
I — InfectiousCurrently carrying itAlready has itYes
R — RemovedRecovered or dead — either way, out of the storyNoNo

The only moves allowed are S → I → R, never backwards. One individual starts infected ("patient zero"), and the outbreak ends when nobody is infectious any more — which can happen with plenty of susceptible people left over, because they were simply never reached.

On a network, transmission only travels along edges. That is the whole reason this project exists: the shape of the graph, not just the infection rate, decides how far and how long an outbreak runs, so "evolve a graph whose outbreaks look like this" is a meaningful thing to ask for.

The specific variant GET simulates

GET uses SIR with a one-timestep infectious period. There is no recovery probability to configure, because recovery is not random:

  • A node infected during step t is infectious for step t+1 — exactly one step.
  • During that one step it tries to infect each still-susceptible neighbour.
  • Then it becomes Removed, permanently, and never infects anyone again.

So the outbreak moves outward from patient zero in a wave, one hop per timestep, and burns out behind itself. The only randomness is whether each transmission attempt succeeds.

Why the one-step infectious period? It is the model the project has always simulated — sir.rs is a deliberate port of Graph::SIR in legacy/Graph.cpp, so that scores stay comparable with the archived C++ results (sir.rs:1-20). It also makes an epidemic cheap, which matters when every fitness evaluation runs dozens of them.

Parameters

#[derive(Clone, Debug, PartialEq)] pub struct SirParams { pub infection_rate: f64, pub patient_zero: Option<usize>, }
sir.rs:36-41

One epidemic's parameters.

infection_rate is the probability that transmission succeeds along one edge copy in one timestep. Per edge copy, not per neighbour — a doubled edge gets two independent chances. See exposure.

patient_zero pins the node the outbreak starts from. None draws a fresh node uniformly at random for every epidemic (sir.rs:225), which is usually what you want: pinning a node measures how good the graph is at spreading from that node, not in general.

This is deliberately a plain struct rather than the config type — the simulator has no business depending on the config schema (sir.rs:31-34). The mapping from config.rs happens in dispatch.rs.

#[derive(Clone, Debug, PartialEq)] pub struct SirSampleParams { pub epidemic: SirParams, pub num_epidemics: usize, pub min_epidemic_length: usize, pub max_epidemic_retries: usize, }
sir.rs:54-64

How one graph's epidemics are sampled — the epidemic itself, plus three sampling controls.

  • num_epidemics — how many outbreaks a graph's score averages over. At least 1. This is not a tuning nicety: a single SIR draw is very noisy, and selection will happily chase that noise instead of graph structure. It also dominates run time.
  • min_epidemic_length — outbreaks shorter than this are re-rolled. C++ default 3. Set it to 1 to disable the re-roll, since every real epidemic has length >= 1.
  • max_epidemic_retries — attempts before keeping whatever came out. C++ default 5. At least 1.

What one epidemic returns

#[derive(Clone, Debug, PartialEq, Eq)] pub struct Epidemic { pub length: usize, pub spread: usize, pub profile: Vec<usize>, }
sir.rs:170-181

Everything the three SIR objectives read, from one simulation. The epidemic is the expensive part and all three objectives want the same one, so a single run reports all three readings.

  • length — how many timesteps the epidemic occupied, including the final one in which the last infectious node recovers without infecting anybody.
  • spread — total ever-infected, including patient zero. The one reading that has never been ambiguous.
  • profile — the count of newly infected nodes at each timestep. profile[0] is always 1 (patient zero), and the last element is always a terminating 0.

The trailing zero, and why length is what it is

This trips up everyone once, so it is worth being explicit. Consider an outbreak that infects nobody at all — patient zero has no neighbours: 

profile = [1, 0]      length = 1      spread = 1

Read that as two facts:

  • The profile ends in a zero because the simulator records the step in which nothing happened, rather than suppressing it. The final entry is not padding; it is the burnout step being reported.
  • length is 1, not 0, because that burnout step is a real timestep — patient zero spent it being infectious and recovering. Even the emptiest outbreak occupies one step.

The three readings are consistent by construction (sir.rs:160-166):

spread  == sum(profile)        the trailing zero contributes nothing
length  == profile.len() - 1   the trailing zero is the "- 1"
A target profile captured from older GET output is off by one element. Until the 2026-08-04 amendment, the spec specified no trailing zero and length = 0 for a lone patient zero. The code now matches legacy/Graph.cpp instead. So a epi_prof_match target written against the old convention will not line up element for element, and the mismatch produces a plausible wrong number rather than an error.
length == 0 means "no epidemic existed", not "nobody was infected". Only a graph with zero nodes produces it, returning length: 0, spread: 0, profile: [] (sir.rs:215-221). That is deliberate and documented as not-to-be-fixed (sir.rs:203-208): a lone patient zero is length 1, so zero is unambiguously the "nothing to measure" signal.

Running one epidemic

pub fn sir_sim<R: Rng + ?Sized>( graph: &Graph, params: &SirParams, rng: &mut R, ) -> Epidemic
sir.rs:213

Runs one epidemic to completion and returns its three readings.

The random number generator is passed in rather than taken from a global. That is one of only two deliberate departures from the C++ port, and it is what lets a single seed drive a whole batch of graphs (sir.rs:11-14).

It never panics and never returns an error. An out-of-range patient_zero yields an outbreak that infects nobody rather than a failure (sir.rs:227-233) — config validation is what is supposed to make that unreachable.

The per-step update rule

The loop runs while at least one node is infectious (sir.rs:242). Each pass does four things in strict order:

1. Count exposure

For every node that is currently infectious, add the edge weight to every other node's exposure tally (sir.rs:249-258). So exposure[v] ends up as the total number of edge copies connecting v to infectious nodes.

A multiplicity of k contributes k, because parallel edges are k independent chances to transmit, not one. Two different infectious neighbours also contribute separately — exposure 2 means two chances, whether they came from one doubled edge or two single ones.

2. Draw for infection

Each node that is Susceptible and has exposure greater than zero gets one combined random draw (sir.rs:260-267). The private helper transmits (sir.rs:304) resolves it: 

escape      = (1 - infection_rate) ^ exposure
infected if   random() < 1 - escape

In words: the chance of escaping all exposure independent contacts is (1 − rate) multiplied by itself exposure times, and the node is infected if it does not escape. One draw, not exposure draws — mathematically identical, and cheaper.

Written as a power rather than the C++ 1 − exp(n · ln(1 − α)). The two are the same quantity, but the logarithm form computes ln(0) when infection_rate is exactly 1.0. The direct form has no such edge case, which is why every worked example on this page can safely use rate 1.0 (sir.rs:298-306).

3. Advance everybody at once

A newly infected node is parked in a staging state, JustInfected, so it cannot transmit during the same step it caught the infection (sir.rs:189-195). Only after every susceptible node has been resolved does the whole population step forward (sir.rs:271-281): every Infectious node becomes Removed, and every JustInfected node becomes Infectious.

This is what makes a timestep simultaneous rather than a cascade. Without the staging state, an infection early in the node ordering could spread all the way across the graph within a single step, and results would depend on node numbering.

4. Record the step

The number of nodes that just became infectious is pushed onto the profile (sir.rs:288). When that number is zero the loop condition fails and the epidemic ends — which is exactly how the terminating zero gets written.

Five nodes. Edges 0–1, 1–2, 2–3, 1–4, every one of them a single edge. infection_rate = 1.0 so every transmission succeeds and the trace is fully deterministic; patient_zero = Some(0).

Reading the trace line by line:

  • Step 1. Node 0 is infectious. Its only neighbour is node 1, so node 1 has exposure 1 and — at rate 1.0 — is certainly infected. Node 0 now recovers and is out for good.
  • Step 2. Node 1 is infectious and has three neighbours: 0, 2 and 4. Node 0 is already Removed and is skipped, so nodes 2 and 4 are infected in the same step. This is where the profile records a 2.
  • Step 3. Nodes 2 and 4 are infectious. Node 4 is a dead end. Node 2 reaches node 3. Note that node 1, their shared neighbour, is Removed — the wave never travels backwards.
  • Step 4. Node 3 is infectious but every remaining neighbour is Removed. Nobody is newly infected, so a 0 is recorded and the loop ends. This is the burnout step, and it counts.

The final result:

profile = [1, 1, 2, 1, 0]
length  = 5 - 1 = 4        four timesteps, the last one being burnout
spread  = 1+1+2+1+0 = 5    all five nodes were reached

The same graph, at a rate below 1

Only step 2 changes in character. Nodes 2 and 4 each have exposure 1, so each is infected independently with probability 1 − (1 − rate)¹ = rate. At rate = 0.5 the step infects both, one, or neither, and the outbreak may stop early — which is precisely the noise num_epidemics and the re-roll exist to manage.

Had 1–2 been a doubled edge, node 2's exposure at step 2 would be 2 and its infection probability 1 − (1 − rate)². At rate 0.3 that is 0.51 rather than 0.30. The test parallel_edges_are_independent_chances_to_transmit (sir.rs:402-443) pins this down empirically against the analytic values.

That is the clearest possible statement of why epi_spread and epi_length select for different structures: spread rewards reaching everybody, length rewards reaching them slowly, along a long thin path. Sampling many epidemics, and the re-roll

pub fn simulate_epidemics( graph: &Graph, params: &SirSampleParams, batch_seed: u64, ) -> Vec<Epidemic>
sir.rs:110

Runs one graph's whole set of epidemics — num_epidemics of them — re-rolling ones that fizzle, and returns them all. This is what an objective calls; each of the three SIR objectives is just a reading over the epidemics it returns.

The epidemics run sequentially (sir.rs:131-151). Parallelism comes from the levels above: many graphs at once, and many replicate runs at once.

Panics if num_epidemics or max_epidemic_retries is zero (sir.rs:115-122). Config validation rejects both, so a config-driven run cannot reach it; the assertion is a backstop for direct Rust use. Zero epidemics would leave the objective averaging nothing, producing the NaN the fitness contract forbids.

Why short outbreaks are re-rolled

An outbreak that fizzles immediately tells you almost nothing about the graph. It reports that the dice went badly, not that the network is poor. Without a re-roll, a large share of evaluations come back near-empty and selection chases the dice instead of structure.

So the loop is (sir.rs:137-148):

for each epidemic i:
    for attempt a in 0 .. max_epidemic_retries:
        run the epidemic with seed[i, a]
        keep it                          <- every attempt overwrites `kept`
        if length >= min_epidemic_length: stop

Two details that are easy to get wrong when reading it. The kept epidemic is the first long-enough one — or, if none of the attempts qualified, the last one tried, not the best one (sir.rs:144). And the epidemic is never discarded for being too long; the threshold is one-sided.

The re-roll is a biased resample, not variance reduction. It pushes expected fitness upward by an amount that depends on how often a given graph fizzles — so a graph that fizzles often gains more from it than one that rarely does. It is not interchangeable with raising num_epidemics, and the two do different jobs. It is kept deliberately, for comparability with the archived C++ results, which is why both values are exposed rather than hardcoded (sir.rs:49-52).
To turn it off, set min_epidemic_length = 1. Every real epidemic has length >= 1, so nothing is ever rejected. max_epidemic_retries = 1 is equivalent — one attempt, kept regardless. Both must be at least 1; 0 panics rather than being caught gracefully.

Seeding

pub fn epidemic_seeds( batch_seed: u64, num_epidemics: usize, max_epidemic_retries: usize, ) -> Vec<u64>
sir.rs:83

Builds the pool of seeds one batch draws its epidemics from. A ChaCha8Rng is seeded with batch_seed and its output stream is the seed list — num_epidemics × max_epidemic_retries of them.

Epidemic i, attempt a uses the seed at the fixed position i * max_epidemic_retries + a (sir.rs:138).

The fixed position is the load-bearing part. Two properties depend on it, and both break quietly if seeds are drawn sequentially instead (sir.rs:66-82):

  • Every graph in a batch draws from the same pool, so differences in fitness reflect the graph rather than the dice. This is what "common random numbers" means. A retry only changes which of the shared draws a particular graph stops on.
  • Extending appends. Raising num_epidemics from 30 to 50 leaves the first 30 epidemics replaying unchanged, so extending an experiment never invalidates what you already have. Verified at sir.rs:527-537.

Sequential drawing would break both, because a graph that retries consumes extra draws and every later epidemic in that evaluation would be offset from the graphs that did not retry. Positional indexing resynchronises at the next epidemic. It is also what makes scoring order-independent, so a population evaluated across threads reproduces exactly regardless of which worker got there first. 

batch_seed
    |
    +-- ChaCha8Rng stream --> [ s0  s1  s2  s3  s4 | s5  s6  s7  s8  s9 | ... ]

Where batch_seed comes from. Not from here. It is handed down by EpidemicScorer, which derives one seed per batch of graphs from the run's master seed and an atomic counter. This file only consumes it. The full chain is on Seeds & Reproducibility.

Gotchas

An out-of-range patient_zero fails quietly. It returns length 0, spread 0 (sir.rs:227-233) rather than erroring, and that zero is then averaged into the graph's score, dragging it down. Config validation checks patient_zero < network_size, so this only bites code that builds a Config in Rust without validating it.
RNG consumption is data-dependent. An unpinned patient_zero consumes one draw per epidemic (sir.rs:225), and only susceptible nodes with non-zero exposure consume a draw at all (sir.rs:260-267). That is harmless — each epidemic gets its own freshly seeded generator — but it means you cannot reason about stream position across epidemics, only within one.
The exposure scan touches every node, not just susceptible ones. Removed and infectious nodes accumulate exposure too (sir.rs:253-257); those entries are simply never read. It costs a little work and keeps the loop simple — not a bug, but it will look like one if you are reading the loop closely.
Cost. One epidemic step is O(infectious × n) for the exposure scan plus O(n) for the draws, so an epidemic is O(n²) in the worst case and one evaluation multiplies that by num_epidemics. This is why num_epidemics dominates run time — everything else in an evaluation is cheap by comparison.
