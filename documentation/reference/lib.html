Reference

lib.rs

The crate root and the Python front door. This is the entire surface a Python user touches: one class, six methods, the result types a run hands back, and the module registration that gives them their names. Everything else in this reference section sits behind it.

Source: get/src/lib.rs, 722 lines, of which about 440 are tests. For the task-level view of the same API, see Python API.

The module tree

pub mod config; mod dispatch; pub mod evolver; pub mod fitness; pub mod genomes; pub mod graph; pub mod py_config; pub mod py_result; pub mod sir;
lib.rs:1-12

Nine modules, eight of them public. dispatch is deliberately private (lib.rs:2-5): it is the config-to-concrete-type layer that run goes through — machinery rather than API. A Rust user who wants to embed the engine uses the engine types directly instead of going through dispatch, so nothing is lost by hiding it.

There are two front doors, and only one of them is on this page. The Python route goes through GraphEvolver below. The Rust route — depend on get as a crate, implement Fitness for your own type, and drive an evolver directly — bypasses this file entirely, because Evolver::run is generic over the objective. Neither is a fallback for the other. See Extension points.

GraphEvolver

#[pyclass] pub struct GraphEvolver { config: Config, fitness_function: Option<PyFitness>, }
lib.rs:35 — fields at :36, :43

The Python-facing entry point to the engine. Both fields are private; Python sees only the methods below.

It holds no results. A run's state lives in the RunResult that run returns and nowhere else, so one evolver drives replicate runs without a previous run's numbers surviving into the next.

  • config — the parsed and validated run configuration.
  • fitness_function — the objective registered by set_fitness_function, set only when [fitness] type = "python". Runtime configuration that cannot live in a config file arrives through a setter instead: the config selects Python, this is the callable.

Constructing

GraphEvolver(config_path: str) -> GraphEvolver
lib.rs:50

Loads configuration from a config.toml file. Raises ValueError if the file cannot be read, parsed, or validated — the message names the offending field and its constraint, which is what a bad config is required to reach the user as (lib.rs:52-55). 

import get

evolver = get.GraphEvolver("config.toml")
GraphEvolver.from_config(config: Config) -> GraphEvolver
lib.rs:95

Builds from configuration assembled in Python rather than from a file. A static method.

The config object is rendered to TOML and parsed by exactly the same parser and validator the file path goes through (lib.rs:96-114). Python is a builder for the config format, not a second parser of it — so this cannot accept a configuration a config.toml would reject, and both front ends report the same constraint in the same words. 

config = get.Config(
    population_size=200,
    network_size=100,
    crossover_rate=0.9,
    mutation_rate=0.2,
    evolution=get.EvolutionConfig.Generational(num_generations=500),
    selection=get.SelectionConfig.Tournament(tournament_size=5),
    genome=get.GenomeConfig.EdgeEdit(gene_length=256),
    fitness=get.FitnessConfig.EpiSpread(
        sir=get.SirParams(infection_rate=0.05, num_epidemics=30)
    ),
)
evolver = get.GraphEvolver.from_config(config)

Errors are reported through a translation layer that rewrites the TOML field name into the Python attribute path that produced it (lib.rs:109-114) — the bare field name is right for the file front end and unhelpful here, where the user never saw a document.

config.to_toml() is the run's provenance record. It returns the document that was actually parsed. Write it beside your results and the run reproduces verbatim.

Registering a Python objective

evolver.set_fitness_function(callable, direction: str) -> None
lib.rs:148

Registers a Python callable as the objective, together with the direction it is meant to be optimised in. direction is "minimize" or "maximize", case-insensitive.

The direction is supplied here rather than in the config because nothing can infer whether a user's function wants its value large or small. It is spelled as a string rather than an imported enum so the Python side needs no import to say which way is better (lib.rs:171-181). 

evolver.set_fitness_function(
    lambda batch: [score(n, edges) for (n, edges) in batch],
    "maximize",
)

The callable takes the whole batch and returns one float per graph, in the same order. See PyFitness for the full contract, what each batch item looks like, and why a per-graph callback is not an option.

It raises ValueError in three cases, and the third is the interesting one:

CaseMessage namesSite
callable is not callablethe type you passed instead lib.rs:164-170
direction is neither wordwhat you gave and what is allowed lib.rs:177-181
the config did not select Pythonthe configured type, and what to change it tolib.rs:156-162
Registering against a non-Python config is refused, not ignored. Silently accepting a callable the run would never consult is indistinguishable, from Python, from having registered it successfully — you would sit watching an SIR objective's numbers and wondering why your own function never runs. So set type = "python" in the config first.
"maximise" is rejected. The British spelling is the most likely near-miss, and silently defaulting it to Minimize would run a maximising search backwards — which looks exactly like a run that is failing to converge. The accepted spellings are closed and the error names both. Test: lib.rs:401.

Running

evolver.run(seed: int) -> RunResult
lib.rs:235

Evolves a population and returns everything that run produced — best_fitness, best_edges, best_genome_repr and history. The edge list is (u, v, multiplicity) triples, each edge once, with u < v: that is Graph::get_edge_list's output.

One master seed drives everything: the starting population, the evolution loop, and the epidemics. There is no seed in the config, deliberately — the config describes the experiment, while the seed describes this invocation.

Nothing is stored on the evolver. The result is the return value, so there is no accessor that has to answer something before a run has happened, and one evolver is reusable across replicates with nothing stale hanging off it.

The method does three things, in this order (lib.rs:235-259):

  1. Builds the objective first, and fallibly (lib.rs:243). The objective is erased to a box before any strategy or genome is chosen. Doing it first means a config selecting Python with no callable registered is reported before any population is built, which is cheaper than discovering it at the first scoring call.
  2. Releases the Python lock for the whole run (lib.rs:253), then calls into dispatch. Holding it would buy nothing — everything between scoring calls is pure Rust, and the Python adapter re-acquires the lock per batch on its own. Keeping it would block every other Python thread for the entire run and serialise the thread pool against any Python caller: a run that works and is inexplicably slow, or a host application that freezes, neither pointing back here.
  3. Wraps the erased outcome and returns it (lib.rs:258). Every number in it has already been converted back into the objective's own units, by dispatch's erase step — this only re-homes them onto the Python-visible type.

Memory: the three sizes multiply, they do not add

Expression materialises the whole population as graphs before scoring, and a graph is a dense network_size × network_size matrix however sparse it actually is. So peak memory is roughly: 

network_size² × 4 bytes × population_size × min(max_cores, replicates)
network_sizeone graphpopulation of 200 × 8 concurrent replicates
10040 KB8 MB64 MB
5001 MB200 MB1.6 GB
10004 MB800 MB6.4 GB

Treat those as a floor rather than an exact figure: each matrix row carries its own allocation header on top of the weights. That overhead is well under 1% at these sizes and does not change the shape of the problem.

The failure mode is unintuitive, which is why it is documented on the call itself (lib.rs:203-234). A configuration that ran fine, given a larger core count to exploit a bigger machine, multiplies peak memory by that same factor and can exhaust hardware that handled the smaller setting comfortably. The three parameters interact rather than adding, so raising any one of them scales the whole product.

Reading results

RunResult
py_result.rs:68

Frozen and read-only. best_fitness is in the objective's own units and sign — the engine's internal lower-is-better orientation never leaks out here. For epi_spread that is a node count, and bigger is better.

best_edges is the winning network; best_genome_repr is the winning genome through the genome trait's own print method, which is the type-erasure hook that lets a non-generic entry point record which individual won without knowing its representation.

history builds a fresh list of GenerationStats on each access, so bind it once rather than re-reading it in a loop.

GenerationStats
py_result.rs:34

One log row: iteration, best_fitness, mean_fitness, std_dev. The two fitness columns are converted into the objective's units; std_dev is not, because a spread is identical under negation.

evolver.save_logs(filename: str) -> None
lib.rs:266

planned

Writes the per-iteration evolution log to filename as CSV — one row per logged iteration, which is every generation for generational and every population_size events for steady-state.

ColumnMeaning
iterationGeneration number, or mating-event number
best_fitnessBest in the population at that iteration, in your units
mean_fitnessPopulation mean, in your units
std_devPopulation deviation, dividing by n — these are all the individuals there are, not a sample, so a single individual has deviation zero
ci_9595% confidence interval half-width on the mean, 1.96 · s / √n, using the sample deviation

best_fitness and mean_fitness are converted back into your units on the way out; std_dev and ci_95 cross unchanged, because a spread is identical under negation. Each row also carries the run's seed and run index, so several runs can be concatenated into one file and still be separable.

The deliberate mismatch between the two spread columns is not a mistake. std_dev describes the population as the complete thing it is, so it divides by n. A confidence interval is inherently a sampling statistic and needs the sampling denominator to mean anything, so ci_95 divides by n-1. Reporting both is fine; computing the interval from the population deviation would not be. A single individual has std_dev = 0 and an undefined ci_95, reported as 0.
evolver.save_results(filename: str) -> None
lib.rs:272

planned

Writes the best individual to filename: the winning genome in its own textual form, the network it expressed as a weighted edge list, and its fitness in your units.

The genome is written through the genome trait's own print method, which is the type-erasure hook — it lets this non-generic entry point record which individual won without knowing its representation.

What exists today. Both methods are declared and registered on the class, so evolver.save_logs("x.csv") resolves — but the body of each is a todo!() placeholder (lib.rs:266-269 and :272-275), so calling either panics rather than writing a file. They also still take &self, and the evolver holds nothing to write now that a run's state lives in the returned result — re-homing them onto RunResult is part of GitHub #21, along with the ci_95 field GenerationStats does not yet carry. Until that lands, take run's returned history and write the CSV yourself.

Replicate runs planned

Research use is n runs at identical parameters, so the run count is a parameter of the run call — like the seed, it describes this invocation rather than the experiment — and run returns a list of results, one per replicate, collected in run order rather than completion order.

evolver.run(seed: int, n_runs: int = 1, max_cores: int | None = None)
lib.rs:235

planned — the seed parameter exists today; the other two are designed.

One master seed, not n of them. The master seed seeds a generator whose output stream is the per-run seed list, and run i takes draw i. One property is preserved deliberately: a run's seed does not depend on how many runs you asked for, so requesting 50 replicates reproduces the first 30 exactly, and extending an experiment never invalidates the replicates you already have.

max_cores is the only concurrency knob. Unset means all available; 1 means fully sequential. There is no point exceeding the replicate count, so the effective figure is min(max_cores, n_runs). It governs both levels at once — replicate work and population work draw from a single bounded pool, built locally rather than globally, because a process-wide pool can only be configured once and would make the setting a property of whichever run call happened first.

The engine chooses whether replicates run in parallel; the user does not. The fitness type already determines the correct answer, so exposing it as a setting would only create a way to choose wrong:

ObjectiveReplicatesWhy
native Rust — epi_spread, epi_length, epi_prof_matchparallel Independent, long-running, no synchronisation
pythonsequential n concurrent runs would contend for one Python lock: slower than sequential and contended

Sequential replicates does not mean a sequential run: expression is pure Rust and lock-free, so a Python-fitness run still expresses its population across threads, and only the single scoring call per batch is serialised.

What exists today. run takes a seed and nothing else, performs exactly one run, and returns one result — the signature at lib.rs:235 is run(&mut self, seed: u64) -> PyResult<PyRunResult>. There is no n_runs, no max_cores, and no local thread pool anywhere in the crate. The per-run machinery the replicate layer depends on is already in place and correct: the objective is rebuilt per call so each run gets its own epidemic counter (dispatch.rs:117), and a Python callable is shared by reference count rather than duplicated (PyFitness::clone_ref). To run replicates today, call run in a Python loop with your own seeds and collect the results yourself.

A complete run, end to end

import get

# 1. Configure — from a file, or from Python objects.
evolver = get.GraphEvolver("config.toml")

# 2. If [fitness] type = "python", register the objective and its direction.
#    The callable takes the whole batch and returns one float per graph.
evolver.set_fitness_function(
    lambda batch: [float(len(edges)) for (num_nodes, edges) in batch],
    "maximize",
)

# 3. Evolve. One seed drives the population, the evolution and the epidemics.
result = evolver.run(seed=2026)

# 4. Read the result. `best_edges` is [(u, v, multiplicity), ...] with u < v.
print(result.best_fitness)      # in your objective's own units
print(len(result.best_edges), "edges in the best network")
print(len(result.history), "rows of convergence log")

best_edges is also the input format for a future run's base graph, so the two genome representations stack with no new data format — evolve a topology with one, then refine it with the other.

Gotchas

An objective that misbehaves panics rather than raising. Config mistakes come back as proper ValueErrors naming the field, but a registered Python callable that raises, returns the wrong type, returns the wrong number of scores, or returns NaN causes a panic crossing the FFI boundary — the fitness trait has no error path. See PyFitness for the exact messages, which do at least name the offending batch item.
Everything downstream may assume the config is valid. Validation runs in Rust before a population is minted or a graph allocated, and it is a real function that both front ends call — not a side effect of parsing. That is why the Python builder cannot accept anything the TOML file would reject. See config.rs.
