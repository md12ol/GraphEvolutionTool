dispatch.rs

Where a validated configuration becomes running machinery. This is the only module that knows both the config schema and the engine, and it is where every runtime choice — which objective, which genome, which strategy — is resolved exactly once.

The problem this module solves

A config file says type = "sda" and type = "steady_state". Those are strings. The engine needs real types: a concrete genome, a concrete evolver, a population of actual individuals. Something has to stand between the two and turn one into the other, and in a language without runtime type lookup that something is a match.

The naive version would match on all three axes at once — 2 strategies × 2 genomes × 4 objectives = 16 arms, and adding a fifth objective would add four more. GET does it in two steps instead, which brings that to 1 objective match + 2 genome arms + 2 strategy arms:

Why the two axes are not symmetric. The objective can be hidden behind a pointer because the fitness trait has no generic methods, never takes itself as an argument, and is thread-safe. The genome cannot: its mutation and crossover methods are generic over the random number generator, crossover needs mutable access to itself, cloning requires a known size, and each representation has a different associated context type. Four independent reasons, any one of which would be enough. So strategy × genome stays a match, and the objective does not. The practical consequence is that adding an objective is one arm here and touches nothing else, while adding a genome or a strategy is a real change to the table.

Why it is its own module

This layer is the only place that knows both sides. It reads the config schema and it talks to Python, so it depends on both. Everything below it — the evolvers, the genomes, the simulator, the graph — deliberately depends on neither, which is what lets the engine be tested without a config file or a Python interpreter anywhere in sight.

Putting these functions in evolver/common.rs would drag both dependencies into the engine core, and that file is genome-agnostic generic code where these functions name concrete genome types. Hence a separate module.

None of this module is public API. It is declared privately in lib.rs and every item is crate-internal. That is deliberate: a Rust user who wants to embed GET writes their own objective and drives an evolver directly, using the engine types, and never goes through dispatch at all. Dispatch exists to turn a config document into concrete types. The items are documented here because understanding them explains the run, not because you can call them.

Step 1 — erase the objective

pub(crate) fn objective(&self, run_seed: u64) -> PyResult<Box<dyn Fitness>>
dispatch.rs:117

Builds the objective for one run and hides its concrete type behind a pointer. Four arms: the three epidemic objectives each map their [fitness] block onto the simulator's own parameters and take the run seed; the python arm hands off to python_fitness below.

This is called before anything else in a run, which is why a config that selects Python with no callable registered fails immediately rather than at the first scoring call, with no population built and nothing to clean up.

Once per run, never once per evolver. Every epidemic objective owns a per-run counter that decides which dice each evaluation batch sees. Two runs sharing one objective would let thread scheduling decide which run saw which seed, and reproducibility goes with it. The function takes the seed as an argument rather than reading a field precisely to make that misuse awkward to write.
pub(crate) fn python_fitness(&self) -> PyResult<Box<dyn Fitness>>
dispatch.rs:171

The python arm, split out so the match above stays one call per objective. Returns a fresh adapter around the registered callable — a fresh instance per call, because replicate runs each need their own objective. The callable itself is shared by reference count, which is right: it is the scorer state that must stay per-run, and this has none.

Two ways it fails, both reported rather than asserted:

  • No callable registered. The message names the fix: call set_fitness_function(callable, direction) before run().
  • The config did not select Python. That is a caller mistake rather than a user one, but it is still reported, so it cannot become a panic in a release build.

Step 2 — match the genome, mint the population

The evolver deliberately cannot build genomes. Constructors differ per representation — one needs a gene length and an operation mix, the other needs three dimensions and can fail — so a generic evolver has no way to mint one. That knowledge lives here, where genome-specific detail already is, which also means a bad dimension surfaces as an error at startup rather than as a panic mid-run inside generic code.

pub(crate) fn edge_edit_start(config, gene_length, weights, rng) -> PyResult<(EdgeEditContext, Vec<EdgeEditGenome>)>
dispatch.rs:218

Builds population_size random edit scripts and the context they express against. The operation mix is compiled into a sampler once and shared across the whole population behind a reference-counted pointer — building it per individual would rebuild the same lookup table hundreds of times.

The base graph is empty: network_size nodes, no edges, at the configured cap.

Five of the nine edit operations are inert on an empty graph. Swap, Hop and the three Local variants all need existing structure to walk, so early generations of a from-scratch edge-edit run genuinely do nothing until Add and Toggle have built something. It is self-correcting, and it is stated here so it is not read as a defect. See the nine operations.
pub(crate) fn sda_start(config, num_states, max_resp_len, init_state, rng) -> PyResult<(SdaContext, Vec<SdaGenome>)>
dispatch.rs:263

Builds population_size random automata and their context. The alphabet is derived, never configured: num_chars = max_edge_multiplicity + 1, so every character the automaton can emit is a legal edge weight and none is silently clamped away. The same cap goes into the context, so the genome and the graph it expresses against agree by construction rather than by the caller remembering to pass the same number twice.

Errors here are all backstops rather than the first line of defence:

  • init_state not less than num_states — already rejected by Config::validate, and re-checked because an out-of-range value would panic deep inside expression, which reaches a Python user as an opaque PanicException. Reporting beats asserting for anything that can reach a release build.
  • Dimensions that do not fit the genome's storage: num_states up to 65536, the derived alphabet up to 256, max_resp_len at least 1. These are not checked by Config::validate at all — a config that loaded cleanly can still fail here, on the first run().

Step 2 continued — match the strategy and run

pub(crate) fn evolve<F: Fitness>(config: &Config, fitness: &F, seed: u64) -> PyResult<ErasedOutcome>
dispatch.rs:312

Runs one complete evolution. Seeds a reproducible random generator from seed, maps the selection block onto the engine's own strategy, then matches the genome — two arms, one per representation — building the population and handing everything to the strategy match.

Arranged as genome outside, strategy inside, which is why there are two arms here and two in the private helper below rather than four copies of the same body. Adding a third genome is one arm here; adding a third strategy is one arm there.

The evolver's seed is drawn, not reused. The population is built first, then a fresh value is drawn from the same stream and given to the evolver. Handing it the master seed instead would make it re-seed its own generator and replay the exact draws that just built the population — correlating the initial genomes with the first mutations, which looks like nothing at all in the output. There is a test named after this (dispatch.rs:762).

The strategy match itself is a private helper, run_strategy (dispatch.rs:362). It is generic over the genome, so both representations share one body. It assembles the shared evolution context — genome context, crossover rate, mutation rate, max_mutations, selection — and then picks GenerationalEvolver or SteadyStateEvolver.

The result, with the genome type dropped

pub(crate) struct ErasedOutcome { pub best_fitness: f64, pub best_edges: Vec<(usize, usize, u32)> }
dispatch.rs:57

One run's result with the genome type removed. The Python entry point cannot be generic — a Python class cannot carry a type parameter, but the engine's own outcome does — so every dispatch arm erases the genome before returning.

best_fitness is in the objective's own units and sign, not engine orientation. Inside the engine everything is lower-is-better, so a maximizing objective's numbers are negative in there; converting once at this boundary is what keeps that an engine-internal detail. The conversion is a negation, and negation is its own inverse — the same call that oriented the value on the way in undoes it on the way out. See Fitness & Orientation.

best_edges is the best individual's expressed network as (u, v, multiplicity) triples, each edge once, in row-major order.

Mapping the config onto engine types

Three small private functions do the actual translation. They are separate from the matches above so they can be tested from a bare config with no evolver to construct.

FunctionMapsWhere
selection The [selection] block onto the engine's selection strategy. One variant each today; kept as a function so a second scheme is one arm here and touches neither evolver. dispatch.rs:436
sir_sample_params The [fitness] block onto the simulator's own sampling parameters. The shape changes: the config block is flat, while the simulator separates the epidemic's two parameters from the batch settings around them. dispatch.rs:461
erase Drops the genome type and converts the fitness back to the objective's units. dispatch.rs:411
Two types called SirParams, and neither is redundant. config::SirParams is the deserializable [fitness] block; sir::SirParams is what the simulator takes, and it is deliberately independent of the config schema so sir.rs never depends on how a TOML key is spelled. sir_sample_params is the seam between them. A field mapped to the wrong place still compiles when the types agree, so there is a test that checks each one individually (dispatch.rs:565).

No seed is mapped. One master seed reaches run and every objective derives from it, so a seed in the config would be a second, competing source — which is why config.rs rejects a stray seed key outright instead of ignoring it.

The whole sequence, end to end

  1. evolver.run(seed) is called from Python.
  2. Step 1: objective(seed) builds the objective and hides its type. If the config says python and nothing is registered, the run stops here.
  3. The Python lock is released. Everything between scoring calls is pure Rust, and the Python objective adapter re-acquires the lock per batch on its own. Holding it across the run would block every other Python thread and serialize the parallel work against any Python caller — a run that works and is inexplicably slow, with nothing pointing back at the cause.
  4. evolve seeds a reproducible generator from the master seed and maps [selection].
  5. Step 2a: the genome match calls edge_edit_start or sda_start, which mints the population and builds the expression context.
  6. A fresh seed is drawn from the same stream for the evolver.
  7. Step 2b: run_strategy assembles the shared context and picks the evolver, then runs it.
  8. erase drops the genome type, converts the fitness back into your units, and takes the winning graph's edge list.
  9. The Python lock is re-acquired and the edge list is returned.

All four combinations of strategy and genome are exercised end to end by a single test (dispatch.rs:848), which exists because the types line up whether or not each arm is wired to the right evolver — before it, three of the four had never actually been executed.

Reproducibility

One seed argument reproduces an entire run: the starting population, the evolution, and the epidemics all derive from it. Two tests pin this — the same seed gives the same score and the same network, and a different seed does not (dispatch.rs:962).

The generator is a fixed algorithm chosen for exactly this reason rather than the library's default, whose algorithm may change between releases — which would defeat the entire purpose of a seed argument. Details on Seeds & Reproducibility.

Designed but not yet here

Replicate runs planned

Research use is n runs at identical parameters, so run count is a parameter of the run call and the call returns a list of results, one per replicate. Three rules make that correct rather than merely fast:

  • One master seed, not n of them. The master seeds a generator whose output stream is the per-run seed list, and run i takes draw i. That gives a property worth having deliberately: a run's seed does not depend on how many runs were requested, so asking for 50 replicates reproduces the first 30 exactly and extending an experiment never invalidates the ones you already have.
  • Per-run state stays per-run. Each replicate gets its own objective instance and therefore its own epidemic counter. This is why objective is a factory taking a seed rather than a value built once — the shape it already has today.
  • Results come back in run order, never completion order, or the same master seed would produce differently ordered output on different machines.

Replicates run in parallel with a native Rust objective and sequentially with a Python one — the engine chooses, because the fitness type already determines the correct answer and exposing it as a setting would only create a way to choose wrong. The single knob is max_cores on the run call: unset means all available, 1 means fully sequential, and there is no point exceeding the replicate count.

Today: run(seed) performs exactly one run and returns one edge list, and the master seed is handed straight to both the objective and the evolution. There is no replicate count, no max_cores, and no thread pool built anywhere in this module. The per-run factory rule is already honoured. Tracked as GitHub #20.
When it lands, max_cores will be a memory knob as much as a CPU one. Expression materializes the whole population as graphs before scoring, and a graph is a dense network_size × network_size matrix however sparse it actually is. Peak memory is roughly network_size² × 4 bytes × population_size × min(max_cores, replicates) — the three sizes multiply. Raising max_cores to exploit a bigger machine multiplies peak memory by the same factor and can exhaust hardware that handled the smaller setting comfortably. See Performance & Memory.

The full result object

A run produces two things: a best individual and a convergence log. The erased outcome carries both — best fitness, the best graph's edge list, the best genome's printed form, and the log rows (dispatch.rs:57) — and that object is the return value of run. The printed genome is what the genome trait's print method exists for: it lets a non-generic entry point record which individual won without knowing its representation.

The private erase function is the orientation boundary (dispatch.rs:411), and it converts the log row by row as well as the headline number. Only the two fitness columns are converted: std_dev is left exactly as the engine computed it, because a spread is identical under negation. Orienting it too would be a silent defect — the number stays positive, so nothing would look wrong.

Starting from an existing graph planned

An edge-edit run can start from a graph you supply rather than an empty one — your own data, or the output of a previous run. Since a run already returns (u, v, multiplicity) triples, the two representations stack with no new data format: evolve a topology with the automaton, then refine it with edit scripts.

Today: edge_edit_start always builds an empty base graph (dispatch.rs:236) and there is no setter to supply one. The consequence — five of the nine operations inert until Add or Toggle build structure — is live right now. Tracked as GitHub #28; the validation the setter owes is described on config.rs.

Extending dispatch

You want to addWhat you touch
A fitness objective One arm in objective, plus the config variant and its Python mirror. No genome and no strategy code is touched — that is the entire payoff of erasing the objective first. See Add an Objective.
A genome representation One arm in evolve's genome match, plus a new *_start function beside the two existing ones. The strategy match is untouched, because it is generic over the genome. See Add a Genome.
An evolution strategy One arm in run_strategy, building its type-specific context. The genome match is untouched. Add any strategy-specific constraint to Config::validate. See Add a strategy.
A selection scheme One arm in selection. Note that the validation function in config.rs deliberately destructures the single selection variant directly, so adding a second one stops that file compiling until you answer the question of what needs validating.
