The type

#[derive(Clone, Debug, PartialEq, Eq)] pub struct Graph { pub num_nodes: usize, pub max_edge_multiplicity: u32, adjacency: Vec<Vec<u32>>, }
graph.rs:1-10

An undirected multigraph on a fixed node count. The adjacency field is private: a symmetric num_nodes × num_nodes matrix where the entry at [u][v] is the number of parallel edges between u and v. Zero means no edge.

The two public fields are plain data with no accessors. num_nodes is the node count; max_edge_multiplicity is this graph's own weight cap, which every write clamps to. A cap of 1 makes the type behave as an ordinary simple, unweighted graph.

Three consequences of the derived traits are worth knowing before you rely on them:

  • Clone copies the whole matrix — cost O(n²). The evolver clones graphs freely, and edge-edit expression begins by cloning its base graph.
  • PartialEq compares all three fields, including the cap. Two graphs with identical edges but different max_edge_multiplicity are not equal.
  • There is no Default and no deserialization. A graph is only ever built by Graph::new and then edited.
num_nodes is public and mutable, and nothing keeps it in step with the matrix. Writing graph.num_nodes = 10 on a graph whose adjacency is 5×5 leaves the two disagreeing, and the next call to weight indexes out of bounds and panics. Nothing in the type prevents this — it is convention only. Treat both public fields as read-only after construction; if you need a different size, build a new graph. The same applies to max_edge_multiplicity: raising it after the fact does not un-clamp weights that were already clamped on the way in.

Constructing

pub fn new(num_nodes: usize, max_edge_multiplicity: u32) -> Self
graph.rs:16

An empty graph: num_nodes nodes, no edges, weights capped at max_edge_multiplicity. Pass 1 for a simple unweighted graph.

Allocates the full num_nodes × num_nodes matrix of zeros immediately (graph.rs:21) — O(n²) time and memory, and it is n separate row allocations rather than one block. This is the allocation that makes memory quadratic in the node count.

A zero node count is legal here and is not rejected. Graph::new(0, 1) builds a graph with an empty matrix. It is a real case in the simulator, where it is the one situation that produces an epidemic of length zero — see sir.rs. Config validation is what stops a run ever reaching it.

Reading edges

pub fn weight(&self, u: usize, v: usize) -> u32
graph.rs:31

The edge multiplicity between u and v: 0 for no edge, k for k parallel edges.

Returns 0 rather than panicking for out-of-range vertices (graph.rs:32-34). It also returns 0 for weight(u, u), because the diagonal is never written. Both are deliberate: genome expression decodes arbitrary 32-bit payloads into vertex indices and never validates them first.

pub fn has_edge(&self, u: usize, v: usize) -> bool
graph.rs:26

True if at least one edge exists between u and v. Exactly self.weight(u, v) != 0, so it inherits the same silence on invalid vertices.

pub fn get_edge_list(&self) -> Vec<(usize, usize, u32)>
graph.rs:88

Every edge exactly once, as (u, v, multiplicity) with u < v, in row-major order — so the list is sorted by u then v. Edges with weight zero are omitted.

This is the shape that leaves the system: it is what GraphEvolver.run hands back to Python, and what a Python Objective receives for each graph. Cost is O(n²) — it scans the upper triangle of the matrix regardless of how many edges there are.

Writing edges

set_edge is the only writer. Every other mutating method funnels through it, which is what makes the matrix symmetric by construction rather than by discipline — the asymmetric state is unreachable through the public API.

pub fn set_edge(&mut self, u: usize, v: usize, weight: u32)
graph.rs:43

Sets the multiplicity directly, writing both [u][v] and [v][u] (graph.rs:49-50). A weight of 0 clears the edge.

Three things it does silently, all load-bearing:

  • Clamps to max_edge_multiplicity (graph.rs:48) rather than rejecting. set_edge(0, 1, 12) on a cap-5 graph stores 5.
  • Ignores self-loops. u == v returns immediately.
  • Ignores out-of-range vertices. Either index at or beyond num_nodes returns immediately.

It returns nothing, so a caller cannot tell any of these apart from success.

pub fn add_edge(&mut self, u: usize, v: usize) -> bool
graph.rs:56

Adds one parallel edge, saturating at the cap. Returns true if the multiplicity actually increased, and false if the pair was invalid, a self-loop, or already at the cap.

That boolean is the one place the graph reports a refused write, and several edit operations only proceed when it comes back true.

pub fn remove_edge(&mut self, u: usize, v: usize)
graph.rs:64

Removes one copy if any exists. On a weight-3 edge this leaves weight 2; on a weight-0 pair it does nothing. Never underflows.

pub fn clear_edge(&mut self, u: usize, v: usize)
graph.rs:72

Removes all parallel edges between the pair at once — set_edge(u, v, 0). Note the contrast with remove_edge: on a multigraph these are different operations, and picking the wrong one is not a type error.

pub fn set_edges(&mut self, edges: &[(usize, usize, u32)])
graph.rs:77

Applies set_edge to every triple in the slice, in order. Cost is linear in the slice length. Convenient for building a graph from a get_edge_list() result — but see the clamping warning below before you do that across two different caps.

The clamp is the main trap when stacking runs. set_edges on a list captured from a cap-5 graph, applied to a cap-1 graph, silently collapses every weight to 1. Nothing returns an error, nothing logs, and the resulting run looks like a poorly performing objective rather than a data problem. The base-graph setter owes an explicit check for exactly this.

Neighbourhood queries

Three queries, and the first two differ on any multigraph. Choosing the wrong one compiles fine and gives plausible numbers.

pub fn degree(&self, node: usize) -> usize
graph.rs:127

The number of distinct nodes connected to node — a row scan counting non-zero entries, O(n). A double edge counts once. Returns 0 for an out-of-range node.

pub fn total_edge_multiplicity(&self, node: usize) -> usize
graph.rs:139

The total number of incident edge copies, counting parallel edges separately — a row scan summing the weights, O(n). A double edge counts twice. Returns 0 for an out-of-range node.

Despite the name this is a per-node figure, not a whole-graph total. It takes a node argument and sums only that node's row.

pub fn get_neighbor_at_index(&self, node: usize, index: usize) -> Option<usize>
graph.rs:103

The index-th distinct neighbour of node, in ascending node order, wrapping modulo the degree (graph.rs:113). So any index at all names a real neighbour: on a node of degree 2, indices 0, 2, 4… all give the first neighbour.

Returns None in exactly two cases: the node is out of range, or the node is isolated (degree 0). Cost is O(n) — it calls degree and then rescans the row.

Wrapping is why an arbitrary payload is always usable. A genome gene carries a 32-bit number with no idea what the graph looks like; the modulo turns it into a valid choice instead of an error path. The cost is that a genuine off-by-one in a caller silently becomes a different, perfectly valid neighbour rather than a failure — so this is not a function to reach for when you want bounds checking.

Nothing here allocates except new, clone and get_edge_list. That is what makes expression cheap enough to run a whole population through every generation — and it is bought with the dense matrix, so the bill arrives as memory rather than time. The memory table on lib.rs has the numbers.

Worked example

Four nodes, cap 5, two edges — one of them doubled:

let mut graph = Graph::new(4, 5);
graph.set_edge(0, 1, 2);   // a double edge between 0 and 1
graph.set_edge(0, 3, 1);   // a single edge between 0 and 3

What the cap does

let mut graph = Graph::new(2, 3);   // cap of 3
graph.set_edge(0, 1, 5);
assert_eq!(graph.weight(0, 1), 3);  // clamped on the way in, no error

graph.add_edge(0, 1);               // returns false — already at the cap
assert_eq!(graph.weight(0, 1), 3);

graph.remove_edge(0, 1);
assert_eq!(graph.weight(0, 1), 2);  // one copy removed, not all of them

Verified by explicit_multiplicity_cap_is_enforced (graph.rs:204-211) and multiplicity_is_capped_at_five (graph.rs:171-187).

Gotchas

The public fields can desynchronise the type. num_nodes and max_edge_multiplicity are pub while the matrix is not, so nothing stops you setting a node count the matrix cannot honour. See the warning at the top of this page — the failure is a panic on the next read, in a place unrelated to the assignment.
Two failure modes look identical to a caller. set_edge returns nothing, so "the edge was set", "that was a self-loop", "that vertex does not exist" and "the weight was clamped" are all indistinguishable. If you need to know, read the weight back, or use add_edge, whose boolean is the only refusal signal the type offers.
Equality includes the cap. If you are comparing an expressed graph against a fixture, build the fixture with the same max_edge_multiplicity or the assertion fails on a field you were not testing.
degree vs total_edge_multiplicity is the recurring bug. They are equal on any simple graph, which is the default, so a mix-up survives every cap-1 test and only shows up when someone runs with parallel edges enabled.
