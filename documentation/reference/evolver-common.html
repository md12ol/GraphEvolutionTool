Reference

evolver/common.rs

The shared half of the evolution engine: the Evolver trait and its context types, the result and log-row types, tournament selection, the mutation helper, and express_and_score — the one function every fitness value in GET passes through. For the gentle introduction to what an evolver is, read Evolution strategies first; this page is the precise companion to it.

Two files are covered here, because they are two halves of one thing: get/src/evolver/mod.rs declares the interface and the data types, and get/src/evolver/common.rs holds the machinery both strategies call. The strategies themselves have their own pages — evolver/generational.rs and evolver/steady_state.rs.

The engine never calls Fitness::evaluate or Fitness::evaluate_batch directly. Ever. common::express_and_score is the sole path from a batch of genomes to a set of fitness values — generational scoring, steady-state child scoring, the final outcome, all of it. It is simultaneously the orientation point (the one place a score is flipped so that lower always means better) and the NaN gate (the one place a broken objective is caught). A direct call to either trait method compiles fine and returns plausible-looking numbers, and both failures it lets through are silent: under a maximizing objective every comparison in the run quietly runs backwards, and a single NaN becomes the best individual in every tournament it enters, filling the population with whatever produced it and leaving a run that looks converged. If you are writing a new strategy, this is the rule to get right first — see Add a strategy.

The Evolver trait

An evolver is a thing that takes a population, improves it, and reports what it found. The trait is deliberately tiny: build one, run it.

pub trait Evolver<G: Genome>
evolver/mod.rs:131

A genetic-algorithm evolution strategy over genome type G. Generic over the genome rather than using a trait object, because a Genome cannot be erased — see The pipeline for why the two dispatch axes are not symmetric.

type TypeContext;
evolver/mod.rs:138

The strategy-specific settings block: GenerationalContext or SteadyStateContext. This is an associated type — each implementor fixes it to one concrete type, which is neater than making the trait take a second type parameter.

fn new( shared: SharedEvolutionContext<G>, type_context: Self::TypeContext, population: Vec<G>, ) -> Self where Self: Sized
evolver/mod.rs:148-157

Build an evolver from the two settings blocks and a ready-made starting population.

The caller supplies the population because the evolver cannot build one: genome constructors differ per representation and some can fail, so a generic evolver has no way to mint a G. Building it in dispatch.rs keeps that knowledge where it already lives, turns a bad dimension into a startup error rather than a mid-run panic, and makes both evolvers testable from a hand-built population.

The Self: Sized bound opts only this one method out of dynamic dispatch — a constructor cannot be called through a trait object anyway — so the rest of the trait stays usable as dyn Evolver<G>.

fn run<F: Fitness>(&mut self, fitness: &F, seed: u64) -> EvolutionOutcome<G>
evolver/mod.rs:162

Evolve the population against fitness, deriving all randomness from seed, and return the best genome with its expressed graph and the run history.

Being generic over F is what makes the Rust extension route work without touching dispatch: if you already hold a concrete objective type, you instantiate an evolver with it directly. See Add a strategy and fitness.rs.

Context types — the settings

Settings are split in two: what both strategies need, and what only one of them needs. The split is what lets dispatch.rs build the shared block once and hand it to whichever strategy the config named.

pub struct SharedEvolutionContext<G: Genome> { pub genome_context: G::Context, pub crossover_rate: f64, pub mutation_rate: f64, pub max_mutations: usize, pub selection: Selection, }
evolver/mod.rs:38-65

Run-level configuration shared by every evolution strategy. Five fields, and no more:

  • genome_context — the genome's own expression settings (EdgeEditContext, SdaContext; see genomes/genome.rs). It is also the authority on network size and the edge-weight cap.
  • crossover_rate — the probability that a selected pair is recombined. Rolled once per pair, never per child.
  • mutation_rate — the probability that a child mutates at all.
  • max_mutations — if it does mutate, the upper bound on how many mutations it takes, drawn uniformly from 1..=max_mutations.
  • selection — the parent-selection strategy, used by both.
Every value has exactly one source of truth, and that is why the list is short. Population size is not here — it is population.len(). Network size and the edge cap are not here — they belong to the genome context. All three are in config.toml, but dispatch.rs is the only place they are read. A second copy of a value can drift out of step with the original, and nothing in the system would report the disagreement.
pub struct GenerationalContext { pub num_generations: usize, pub elite_count: usize, }
evolver/mod.rs:68-74

Generational-only settings: how many generations to run, and how many best individuals are copied forward unchanged into each next generation. elite_count defaults to 1 in config.toml. See evolver/generational.rs.

pub struct SteadyStateContext { pub num_mating_events: usize, }
evolver/mod.rs:77-80

Steady-state-only settings: how many mate-and-replace events to perform. See evolver/steady_state.rs.

What a run hands back

pub struct EvolutionOutcome<G: Genome> { pub best_genome: G, pub best_graph: Graph, pub best_fitness_engine: f64, pub direction: Direction, pub history: Vec<GenerationStats>, }
evolver/mod.rs:115-124

The result of one run. Both strategies return this same type — they differ only in how they fill it in.

The expressed Graph travels with the genome so a caller can use the final network without re-expressing it. best_fitness_engine is named the way it is on purpose: it is in engine orientation, lower-is-better, whatever the objective actually computed. direction is what undoes that — direction.orient(best_fitness_engine) gives the number back in the objective's own units, and because negation is its own inverse it is literally the same function that converted it on the way in.

The struct derives nothing — no Debug, no Clone. It is a plain value you take apart.

If you are embedding GET as a Rust crate, the numbers in here are negated under a maximizing objective. That is the stated cost of converting exactly twice per run instead of once per stats row. The field name says _engine so it cannot be mistaken, and direction is the fix. The Python boundary does this for you — see Fitness & orientation.

The log row

pub struct GenerationStats { pub iteration: usize, pub best_fitness: f64, pub mean_fitness: f64, pub std_dev: f64, pub ci_95: f64, }
evolver/mod.rs:96-107

One row of the evolution log. iteration counts generations for the generational strategy and mating events for steady-state.

best_fitness and mean_fitness are in engine orientation like everything else inside the engine; the boundary converts them when it writes the log. std_dev is left alone, because a spread is the same number whichever sign the values carry.

The log the reporting layer writes has seven columns:

ColumnMeaning
iteration generation number, or mating-event number
best_fitness best individual in the population at that iteration, in your units
mean_fitness population mean, in your units
std_dev population deviation — divides by n, because these are all the individuals there are, not a sample of a larger group. A single individual therefore has a deviation of exactly zero. Crosses the boundary unchanged.
ci_95 95% confidence half-width on the mean, 1.96 · s / √n, where s is the sample deviation — divides by n−1. It answers "how tightly is this generation clustered around its mean". A single individual has an undefined interval, reported as 0.
seed and run_index stamped on every row, so 30 replicate runs can be concatenated into one file and still be separated afterwards. These two are fields on the result, not on GenerationStats — save_logs repeats them down every row.
The two deviations in that table are deliberately different, and it is not a mistake. std_dev describes the population as the complete thing it is, so it divides by n. ci_95 is inherently a sampling statistic and needs the sampling denominator n−1 to mean anything. Reporting both is fine; computing the interval from the population deviation would not be.
How a row reaches Python. The boundary (dispatch::erase) converts each row's two fitness columns out of engine orientation and carries the whole log out on the result object. seed and run_index are added there, from the result, rather than being carried per row through the engine. A Rust embedder calling Evolver::run directly gets the same history on EvolutionOutcome, unconverted — and without those two columns, which exist only in what save_logs writes.

Selection — picking parents

pub enum Selection { Tournament { tournament_size: usize }, }
evolver/common.rs:22-25

The parent-selection strategy. It is an enum so that a second mechanism (roulette-wheel, truncation, rank, …) is one extra variant plus one match arm, mapping straight onto a config.toml field. One variant exists today.

A tournament, in plain terms: pick a few individuals at random, and the best of them wins. A bigger tournament_size means more competitors per pick, so stronger individuals win more often — that is what "selection pressure" means. At tournament_size = 1 there is no competition at all and selection is uniformly random.

There are two draw methods, and they sample differently on purpose:

MethodSamplingUsed byWhy
select(count)with replacement generational the textbook default; nothing downstream needs the entrants to be distinct
tournament_indices()without replacement steady-state it feeds tournament-local replacement, and "the worst two members" means nothing if an individual can appear twice

The consequence is small but real and was accepted deliberately: one configured tournament_size implies marginally different selection pressure in each strategy (roughly 4.90 expected distinct entrants at k = 5 in a population of 100 — about 2%, which is noise against a stochastic run). A second consequence matters more when reading generational traces: two picks can be the same individual, so a "pair" can be one genome and its own clone, and crossover between them does nothing at all.

pub(super) fn select<G, R>( &self, population: &[G], fitnesses: &[f64], count: usize, rng: &mut R, ) -> Vec<G> where G: Genome, R: Rng + ?Sized
evolver/common.rs:67-73

Run count independent tournaments and return a clone of each winner. Sampling is with replacement at both levels: an individual can be drawn twice inside one tournament, and can be returned more than once across the batch. Callers who need distinct individuals must enforce that themselves — select cannot know whether its output is a mating pair or an unrelated batch.

Guards: the population and fitness slices must be the same length, the population must be non-empty, and tournament_size must be at least 1. There is deliberately no upper check against the population size — with replacement, an oversized tournament still draws perfectly well.

The ?Sized on R is what lets a caller pass a trait-object RNG such as &mut dyn RngCore; the same bound appears on every RNG parameter in this file.

pub(super) fn tournament_indices<R>(&self, fitnesses: &[f64], rng: &mut R) -> Vec<usize> where R: Rng + ?Sized
evolver/common.rs:109-112

Draw one tournament of distinct individuals and return their indices sorted best first. The front of the result are the parents, the back are the individuals they will displace — which is exactly the shape steady-state's replacement rule needs.

Distinctness comes from rejection sampling: draw an index, keep it if it is not already in the list, otherwise draw again (common.rs:126-132). tournament_size is small in practice, so a linear membership scan beats a hash set and avoids the population-sized buffer a shuffle would need on every event.

Guards: tournament_size at least 1, and tournament_size no larger than the population — without the second, the rejection loop could never finish.

The comparator

pub(super) fn rank(fitnesses: &[f64], a: usize, b: usize) -> Ordering
evolver/common.rs:33

Order two individuals, better first, ties broken by lower index. The whole body is one line: fitnesses[a].total_cmp(&fitnesses[b]).then(a.cmp(&b)) — the .then(..) only takes effect when the fitness comparison came out equal, so it is a tie-break and not a second sort key.

The tie-break is load-bearing: it makes a tournament's outcome depend only on which indices were drawn, never on the order the RNG produced them. Fitnesses arriving here are already oriented so lower is better, and NaN cannot reach this point because Direction::orient rejected it first.

pub(super) means "visible inside the evolver module" — both strategy files use it, nothing outside the engine can.

pub(super) fn best_index(fitnesses: &[f64]) -> usize
evolver/common.rs:47

The index of the best individual, using the same rank ordering across the whole slice — so "best" means one identical thing whether it is decided inside a tournament, by elitism, or when packaging the final result. Both strategies call it to pick their winner.

Panics on an empty slice. Both callers construct a non-empty population and neither ever removes an individual, so an empty slice is a bug rather than an input.

The scoring gate

pub fn express_and_score<G, F>( batch: &[G], context: &G::Context, fitness: &F, ) -> (Vec<Graph>, Vec<f64>) where G: Genome, F: Fitness
evolver/common.rs:253-261

Express every genome in the batch, score the whole batch, and return the expressed graphs alongside their fitnesses. Index i of both returned vectors belongs to batch[i]. Three steps, in order:

  1. Express, in parallel. batch.par_iter().map(|g| g.express(context)) (common.rs:263). This is the only par_iter in the whole evolver subsystem, and it is what Genome: Send + Sync and Genome::Context: Send + Sync exist for.
  2. Score, in one batched call. It defers to Fitness::evaluate_batch, so a native objective fans out over rayon and a Python-backed one crosses the FFI boundary once for the whole batch instead of once per individual.
  3. Orient, exactly once. Each returned score goes through direction.orient(score) (common.rs:265-270), which flips the sign under Maximize and panics on NaN.

The returned fitnesses are therefore always lower-is-better, whatever the objective's own direction, and everything downstream compares them without ever asking which way the objective ran.

The graphs come back rather than being dropped because scoring had to build them anyway. Handing them over costs nothing and saves generational from re-expressing its winner at the end. A caller that only wants the scores can ignore the first element and let it drop — steady-state does exactly that.

Panics if the objective returns NaN for any individual.

Why one function and not a direction-aware comparator? Because a comparator needs the direction at every comparison site — tournament ordering, the generational argmin, the steady-state best — and a single missed site fails silently. This is the only place the whole batch is scored, so it is the only place "exactly once" can be guaranteed rather than remembered. Orientation and NaN rejection share one door by design. The full argument lives in Fitness & orientation.

Variation helpers

pub fn mutate_child<G, R>(child: &mut G, context: &G::Context, mutation_rate: f64, max_mutations: usize, rng: &mut R) where G: Genome, R: Rng + ?Sized
evolver/common.rs:186-190

Apply the engine's two mutation dice rolls to one child, in a fixed order:

  1. mutation_rate — does this child mutate at all? If not, return immediately.
  2. max_mutations — if it does, how many mutations, drawn uniformly from 1..=max_mutations; then call Genome::mutate that many times.

Both rolls live here, in one helper that both strategies call, so the two can never drift apart on what mutation means — which is exactly what happened once on selection sampling. Neither roll belongs to the genome: Genome::mutate applies exactly one mutation per call, and a representation that rolled its own count internally would make max_mutations meaningless for that representation with nothing to report it.

Note that "one mutation" is measured by count, not strength: one edge-edit gene out of 256 is a far smaller perturbation than one SDA transition out of 24. See Crossover & mutation.

Panics if max_mutations is zero — 1..=0 is an empty range with no meaningful draw. This is a backstop; Config::validate rejects it first.

The count roll consumes randomness even when the answer is forced. At max_mutations = 1 the draw from 1..=1 has only one possible outcome, but it still advances the RNG state (measured 2026-08-03). That means a seeded run does not reproduce what the pre-max_mutations engine produced, even at the default. Skipping the draw at 1 would restore the old sequence and is deliberately not done: a special case that changes the random stream based on a config value is a worse thing to own than a one-time change in seeded output. See Seeds & reproducibility.
pub fn breed_pair<G, R>(first: &mut G, second: &mut G, shared: &SharedEvolutionContext<G>, rng: &mut R) where G: Genome, R: Rng + ?Sized
evolver/common.rs:227-231

Recombine a selected pair and mutate both children, in the fixed order every strategy uses: one crossover roll for the pair, then one mutate_child call per child. The two parents are mutated in place into the children.

Both strategies breed through here, so the rolls happen in the identical order — crossover, then child one, then child two — and the two consume randomness the same way. That is now guaranteed by there being one copy of the sequence rather than by two copies agreeing: the order is part of the reproducibility contract, and it is the one kind of divergence that would stay invisible until a seeded run quietly stopped reproducing.

Takes the whole SharedEvolutionContext rather than the four fields it reads, so a field added there cannot be forgotten at one of the two call sites.

Nothing is scored here — the caller decides when, and in what batch.

Logging

pub(super) fn generation_stats(iteration: usize, fitnesses: &[f64]) -> GenerationStats
evolver/common.rs:292

Summarize a scored population into one log row: the minimum, the mean, and the population standard deviation (variance = Σ(f − mean)² / n, common.rs:315, then a square root). Written as plain loops rather than iterator chains, per the project's readability convention.

Every field comes out in engine orientation, because nothing here converts. This function used to take a Direction and convert best and mean back into the objective's units — which meant std_dev had to be deliberately skipped, since a deviation is unchanged by negation. That exception read like a missed case and needed a test to defend it. With nothing converting here, there is nothing to except.

Panics on an empty population.

Validation: two layers, and they are not identical

Both evolvers carry assert!s in their constructors. Those are backstops for direct Rust use — tests, and embedding GET as a crate. A config-driven run should never reach one, because Config::validate checks the same ground first and returns a proper error naming the offending field, rather than a panic crossing the FFI boundary as an opaque PanicException. See config.rs.

The config path is stricter than the engine on one rule. Config::validate enforces population_size >= tournament_size for both strategies (get/src/config.rs:408), but GenerationalEvolver::new deliberately omits that assert — generational samples with replacement, so an oversized tournament draws perfectly well and there is nothing to reject. Steady-state does assert it (get/src/evolver/steady_state.rs:170), because its without-replacement draw genuinely cannot be satisfied. So a hand-built generational evolver with a tournament larger than its population is legal and works; the same thing expressed as a config document is rejected. Worth knowing if you are writing tests, or if a config error surprises you.
