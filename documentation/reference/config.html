Source reference · get/src/config.rs

config.rs

The schema. Every key a config.toml file may contain, the Rust types it parses into, and the one function that decides whether a configuration is allowed to run. If you are looking for "what can I put in the file and what happens if I get it wrong", the key reference table below is the whole answer.

What this module owns

A GET run is described by a document — either a TOML file you wrote, or the same document generated from Python objects (see py_config.rs). This module turns that document into plain Rust data and then checks it. It does two jobs and deliberately not a third:

  • Parse. Turn TOML text into a Config value, using serde. Missing keys, wrong types and unknown section tags are caught here.
  • Validate. Check the constraints that serde cannot express — a node index that must be inside the network, a tournament that must fit in the population — and return an error naming the offending field.
  • Not: build anything. No graphs, no genomes, no evolver. Turning a validated Config into running machinery is dispatch.rs's job.

The types here are flat, owned structs rather than the engine's own context types. That is on purpose: SharedEvolutionContext is generic over the genome and carries a non-deserializable associated type, so configuration is parsed into this plain shape first and mapped onto real engine types afterwards. The narrative version of this is on The pipeline; the user-facing version is Configuration reference.

Validation is a function, not a side effect of parsing. Config::validate is called by both front ends — the file path reads the file, calls from_toml_str and then calls it, and the Python path calls it after rendering its objects to TOML. If it were folded into deserialization, the Python route would silently accept configurations the file route rejects, and Python is the route users actually take.

The type map

Four of these are tagged enums: the TOML table has a type = "…" line that picks which set of keys the rest of the table may use. Writing type = "steady_state" and then num_generations is an error, not a silently ignored key.

TypeTOML sectionChoices
Configthe whole document—
EvolutionConfig[evolution] generational · steady_state
SelectionConfig[selection] tournament
GenomeConfig[genome] edge_edit · sda
FitnessConfig[fitness] epi_spread · epi_length · epi_prof_match · python
SirParamsflattened into [fitness] shared by the three epidemic objectives
EdgeEditOperationWeights[genome.operation_weights] defined in edge_edit.rs, not here

"Flattened" is worth understanding because it explains a gotcha further down. The three epidemic objectives all need the same five epidemic settings, so rather than writing them out three times the shared block is flattened — its keys appear directly in [fitness] rather than in a sub-table. That keeps the TOML flat and the Rust DRY, and it is the reason serde cannot reject unknown keys in that one table.

Key reference

Every key the parser accepts. "Required" means the document will not load without it; a default in the default column means you may omit the line entirely. The last two columns are the useful ones: what is checked, and what you get told when it fails.

There is no num_chars key, and adding one would be a mistake rather than a feature. The automaton's alphabet is derived as max_edge_multiplicity + 1, so every character it can emit is a legal edge weight. A separately configured alphabet that was too large would bias the graph toward the cap as surplus characters got clamped down onto it, and one that was too small would make the upper weights unreachable — both silent. Details on sda.rs.

[genome.operation_weights]

Edge-edit only. Nine floats, one per edit operation, each defaulting to 1.0. They are relative weights, not percentages: all-equal is the same distribution whether every value is 1.0 or 10.0. Setting one to 0.0 disables that operation outright.

KeysTypeDefaultCheckedError
toggle, hop, add, delete, swap, local_toggle, local_add, local_delete, null float1.0 each Every weight finite and non-negative, and at least one strictly positive. operation_weights — "operation weights must be finite and non-negative" or "at least one operation weight must be positive"

[fitness]

The first three objectives all read the same SIR simulation and share the same five settings; only epi_prof_match adds anything. The python objective takes no keys at all — its parameters live in your callable, which you register from Python.

Supplying it under any other objective is rejected as a contradiction. target_profile — "must have at least one element…", "element N is NaN; every element must be finite", or "belongs to `epi_prof_match` alone…"

Three rates are never validated. crossover_rate, mutation_rate and infection_rate are read as plain floats and no range check is applied to any of them, so mutation_rate = 5.0 or infection_rate = -1 loads without complaint and produces nonsense at run time. The design in official_spec_sheet.md §7 does not list them either, so this is a gap in the design rather than a bug in the code — but it is the mistake most likely to cost you a run.

A complete example

Everything below is a key verified to exist. This is a steady-state run of an automaton genome scored against a target epidemic curve. 

population_size = 200         # 200 individuals; must be >= tournament_size
network_size    = 100         # every expressed graph has 100 nodes
max_edge_multiplicity = 3     # parallel edges up to 3; also fixes the SDA alphabet at 4
crossover_rate  = 0.9         # 90% of selected pairs recombine
mutation_rate   = 0.2         # 20% of children mutate at all
max_mutations   = 2           # a mutating child takes 1 or 2 mutations, uniformly

[evolution]
type              = "steady_state"   # one mate-and-replace event at a time
num_mating_events = 100000           # logs one row per population_size events

[selection]
type            = "tournament"
tournament_size = 6           # >= 4 is REQUIRED here, because the strategy is steady_state

[genome]
type         = "sda"          # a self-driving automaton, generating a graph from scratch
num_states   = 12             # 12 automaton states
max_resp_len = 4              # each transition emits 1..=4 characters
init_state   = 3              # must be < num_states, or expression would panic
                              # note: NO num_chars — it is max_edge_multiplicity + 1 = 4

[fitness]
type           = "epi_prof_match"   # RMSE against a curve; minimized
infection_rate = 0.05               # per-edge, per-timestep transmission probability
num_epidemics  = 30                 # each evaluation averages 30 outbreaks
patient_zero   = 0                  # pinned to node 0; must be < network_size
min_epidemic_length  = 3            # re-roll outbreaks shorter than 3 timesteps
max_epidemic_retries = 5            # after 5 attempts, keep whatever came out
target_profile = [1, 3, 8, 17, 24, 19, 11, 5, 2, 1]
                              # newly-infected per timestep; compared verbatim

Loading it:

import get
evolver = get.GraphEvolver("experiment.toml")   # reads, parses AND validates
result = evolver.run(20260812)                  # one master seed drives everything

The shipped config.example.toml at the repository root is the annotated version of this, and it is not decoration: two tests parse and validate it, so a broken example breaks the build.

Config

pub struct Config
config.rs:21

Everything the genetic algorithm needs for a run. Ten fields, all public: evolution (line 23), population_size (25), network_size (27), max_edge_multiplicity (30), crossover_rate (32), mutation_rate (34), max_mutations (41), selection (43), genome (45), fitness (47).

pub fn from_toml_str(text: &str) -> Result<Self, ConfigError>
config.rs:341

Parse TOML text into a Config. It runs the two raw-text checks (a stray seed, a misplaced target_profile) but it does not call validate. That split exists so a test can build a config that deliberately breaks one constraint — if you are calling this yourself, call validate too.

pub fn validate(&self) -> Result<(), ConfigError>
config.rs:371

Check every constraint, in four groups and in this order: top-level (line 380), evolution and selection together (403), genome (443), fitness (474). The first failure wins, so a document with two problems reports one of them.

It returns an error and never panics. A bad config is a user mistake, not a bug, and a panic crossing the Python boundary arrives as an opaque PanicException with nothing actionable in it. The assert!s inside the evolvers remain as backstops for direct Rust use, but a config-driven run must never reach one.

It runs before anything is built — no population, no graph — so everything downstream may assume a valid config. The one thing it deliberately does not check is the base graph.

Errors

pub enum ConfigError { Io(std::io::Error), Toml(toml::de::Error), Validation { field: &'static str, constraint: String } }
config.rs:208

Three ways loading a config can fail: the file could not be read, the text was not valid TOML for a Config, or it parsed but broke a constraint.

The Validation variant keeps the field and the constraint apart rather than pre-formatting them into one string. Two consumers need that: the Python front end has to rewrite the field name into a Python attribute path before building its exception, and tests assert on field instead of matching prose that would break every time the wording changed.

Displayed, a validation failure reads invalid config: `field` constraint — for example invalid config: `max_mutations` must be at least 1, since a mutating child takes 1..=max_mutations mutations.

The two raw-text checks

Almost all parsing is handled by serde. Two keys are checked by reading the raw text before deserialization instead, in a private function (reject_stray_fitness_keys, config.rs:287), and the reason is mechanical rather than stylistic.

Because the epidemic block is flattened into [fitness], serde deserializes it through a buffered map of contents — and in that mode its "reject unknown fields" switch never fires. An unrecognised key under [fitness] is therefore discarded without a word. Two such keys are dangerous enough to be caught by name:

KeyWhy it is caught
seed A config written before the seed moved out of [fitness] still parses, and would run under a different seeding model than its author believes. There is now one master seed, supplied to the run call, and everything derives from it — see Seeds & reproducibility.
target_profile Someone who switches objective and forgets the profile behind would believe they are matching a curve while the run maximizes spread. So a profile under any objective other than epi_prof_match is a hard error.
Deliberately two keys by name, not a general unknown-key sweep. A general sweep would hand-roll what serde does everywhere else and would start rejecting keys as the schema grows. The narrowness is a recorded decision, and it is pinned by a test whose name says so: an_unknown_fitness_key_outside_the_two_named_ones_is_still_ignored. The practical consequence for you: a typo under [fitness] is silent.

This is the TOML path only. The Python front end has no text to inspect, and its target_profile exists only on the EpiProfMatch object, so the contradiction cannot be expressed there in the first place.

Gotchas

  • Parsing and validating are separate calls. from_toml_str parses and does not validate, so a Config it returns is unchecked until validate is called on it — which is exactly why dispatch.rs keeps its own backstop checks. There is no single call that does both: reading the file, parsing it and validating it are three steps the caller makes in order.
  • Unknown keys are rejected under [genome], ignored elsewhere. [genome] and [genome.operation_weights] both refuse a key they do not recognise, under either genome type. [fitness] cannot: it uses #[serde(flatten)] for the shared SIR block, and flatten swallows unrecognised keys into the flattened field's content map before deny_unknown_fields could fire. So a stray top-level key still vanishes, and a misspelled required key is caught only as a "missing field" error naming the correct spelling.
  • Switching strategy can invalidate a working [selection] block. The tournament_size ≥ 4 floor applies to steady-state only, because that strategy needs two parents and two individuals to replace, all distinct. Generational has no such floor.
  • min_epidemic_length = 1 is legal and meaningful — it is the supported way to switch the re-roll off. Only 0 is an error. Do not "correct" the floor to 2.
  • num_states = 0 reports the wrong field. The init_state < num_states check runs first and 0 < 0 is false, so the error names init_state even though you never wrote it.
  • population_size = 0 is rejected, but never by name. Under generational the elite_count check catches it; under steady-state the tournament checks do. Either way the message names a field you may not have written. A population of exactly 1 does validate if you write elite_count = 0 and tournament_size = 1.
  • SDA dimensions are checked late. num_states outside 1..=65536, and max_resp_len = 0, are not caught by validate at all — they surface as a ValueError the first time you call run(). A config that "loaded fine" can still fail there.
  • The target profile is compared verbatim. Nothing is prepended for patient zero and nothing is rescaled for the network size, unlike the legacy C++ loader. A profile copied out of an archived run will be off by one element and by a scale factor. Supply the curve you want, at the size of the network you are building.

Designed but not yet here

Base-graph validation planned

An edge-edit run can start from an existing graph rather than an empty one — your own data, or the output of a previous run, which is what lets the two representations stack. The base graph arrives through a setter rather than the config file, because it is bulk data, and Config::validate's remit stops at the document. Three checks belong to that setter, and all three fail quietly if skipped:

  • the base graph's node count must match network_size, or out-of-range edges are silently dropped;
  • narrowing the cap must be rejected or warned about — setting an edge clamps to the cap, so piping a cap-5 result into a cap-1 run silently collapses every weight to 1. This is the main stacking trap;
  • with no base graph supplied the run starts from an empty one, which leaves five of the nine edit operations inert until Add or Toggle have built some structure.
Today: there is no base-graph setter in the code, so every edge-edit run starts from an empty graph built in dispatch.rs. Config::validate's doc comment names this exclusion explicitly (config.rs:369). The third bullet above — the empty-graph consequence — is true right now and is not a future concern.
