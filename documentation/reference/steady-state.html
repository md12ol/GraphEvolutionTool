Reference

evolver/steady_state.rs

The steady-state strategy: one mate-and-replace event at a time. Each event draws a small tournament, breeds its two best, and overwrites that same tournament's two worst — so almost the whole population survives every event untouched. The concepts are in Evolution Strategies; this is the precise companion.

The contrast with evolver/generational.rs is the whole point of having two strategies, so this page names the differences explicitly at each step. The shared machinery — selection, the scoring gate, the mutation helper, the log row — lives in evolver/common.rs.

The loop, step by step

  1. Construct — Evolver::new (steady_state.rs:151). Assert tournament_size >= 4 and population.len() >= tournament_size.
  2. Seed the random number generator — ChaCha8Rng::seed_from_u64(seed) (steady_state.rs:192). Same generator choice as generational, for the same reason.
  3. Score the whole starting population, once — common::express_and_score (steady_state.rs:194-195). The graphs are discarded immediately; only the fitness vector is kept, and it is threaded through the rest of the run as a mutable slice. This is the only time the full population is ever scored.
  4. Enter evolve (steady_state.rs:196). Set log_interval = self.population.len() (steady_state.rs:108) — the "generation equivalent". Clear the history and log iteration 0 (steady_state.rs:110-111).
  5. For each event from 1 to num_mating_events (steady_state.rs:113):
    1. Draw one tournament of distinct individuals — Selection::tournament_indices(fitnesses, rng) (steady_state.rs:48). The result is a list of slot indices sorted best first, with no repeats.
    2. Clone the two best as parents — tournament[0] and tournament[1] (steady_state.rs:50-51). The originals stay in the population; the children are built from copies.
    3. One crossover roll for the pair — rng.random_bool(crossover_rate), then first.crossover(&mut second, rng) if it passes (steady_state.rs:57-59).
    4. Mutate each child — common::mutate_child on the first, then the second (steady_state.rs:60-71), in the same fixed order generational uses.
    5. Score the two children, in one batch — express_and_score(&children, ..) on a two-element array (steady_state.rs:75-76). One call rather than two, which halves the FFI crossings a Python objective pays per event.
    6. Overwrite the tournament's two worst — the last and second-to-last entries of the sorted tournament (steady_state.rs:78-81). Both the genome and its fitness are written in the same loop (steady_state.rs:84-87), so the fitness array stays exactly in step with the population.
    7. Log, but only on the interval — if event % log_interval == 0, push a row stamped with the event number (steady_state.rs:116-118).
  6. Report — self.outcome(&fitnesses, fitness.direction()) (steady_state.rs:197). Find the winner with common::best_index (steady_state.rs:133), clone its genome, re-express its graph (steady_state.rs:137), and take the history. 
score once ─→ log(0) ─→ ┌─ mating event ─→ log only every population_size events ─┐ ─→ outcome

The rules worth knowing

Tournament-local replacement

This is the idea the whole strategy is built on, and it is worth stating slowly. When an event happens, the engine draws a handful of individuals at random — say five out of two hundred — and everything about that event happens inside those five. The best two of the five become parents. The worst two of the same five get overwritten by the children. The other one hundred and ninety-five individuals are not consulted, not compared, and not touched.

Three consequences follow, and each is a design goal rather than a side effect:

  • Self-elitist. The tournament's best is never among the replaced, so the population's best individual can never be discarded — whenever it is drawn, it is by definition the best of that tournament. No elite_count setting is needed, and there isn't one.
  • Diversity-preserving. A globally poor individual is not hunted down; it survives until it happens to be drawn into a tournament. That keeps unusual genomes in the population much longer than a global replace-the-worst rule would.
  • Cheap. Each event costs about k log k for a tournament of k, rather than an O(population) scan to find the global worst. At a hundred thousand events that difference is the run.
Replacement is unconditional. A child takes its slot even if it scores worse than the individual it displaces (steady_state.rs:84-87 — there is no comparison before the write). The best-is-never-discarded guarantee comes from the tournament structure, not from a comparison, so no extra check is needed and adding one would change the search behaviour.

Why tournament_size >= 4, and only here

An event needs four distinct roles: two parents, and two individuals to replace. A tournament smaller than four cannot supply them:

SizeWhat happens
2Both parents are replaced by their own children. The tournament's best is not carried forward, so the strategy stops being self-elitist outright — the guarantee the whole design rests on is gone.
3The best is still preserved, but the second parent is also one of the replaced. Workable, yet it quietly changes what an event means.
4The smallest size at which parents and replaced are fully disjoint. This is MIN_TOURNAMENT_SIZE (steady_state.rs:32).

The constraint is strategy-specific. Generational has no such floor and needs none — its tournaments only ever choose parents, and nothing is defined in terms of a tournament's worst members. Configuration validation reflects that: the tournament_size >= 4 rule is applied for steady-state only (get/src/config.rs:431).

The config path is stricter than the engine on the population rule. Config::validate enforces population_size >= tournament_size for both strategies (get/src/config.rs:408), and steady-state asserts it too (steady_state.rs:170) because its without-replacement draw genuinely cannot be satisfied otherwise — the rejection sampler would loop forever looking for a distinct index that does not exist. GenerationalEvolver::new deliberately omits that assert, since sampling with replacement copes with an oversized tournament perfectly well. So the same configuration that a hand-built generational evolver accepts is rejected when it arrives as a config document. Worth knowing if a validation error surprises you, or if you are writing tests.

Stale fitnesses — the accepted limitation

Steady-state scores only the two new children per event. Every other slot keeps whatever number it was given when it entered the population, and nothing ever rescores it.

Under a deterministic objective that is simply an optimization. Under a stochastic one — which the SIR objectives are — it has a real consequence: the objective's batch counter advances once per event, so the children being compared against the population were scored under different dice than the population itself. An individual that drew lucky dice keeps its inflated score for the rest of the run, because nothing will ever take a second look at it.

Prefer generational when the objective is stochastic and the comparison needs to be fair. This limitation is inherent to combining incremental scoring with a noisy objective rather than being a defect in the implementation: the alternatives — rescoring the population periodically, or freezing the seed across a generation equivalent — each swap it for a different distortion rather than removing it. It was accepted deliberately. See Fitness & Orientation.

The winner's graph is re-expressed

outcome calls best_genome.express(&self.shared.genome_context) (steady_state.rs:137) to fill in EvolutionOutcome::best_graph. Generational instead moves the winner's graph out of the vector its final scoring pass already built. The reason for the difference is cost, not behaviour: steady-state has no such vector, and keeping one Graph per individual alive for the whole run — a dense matrix each — to save a single expression at the end would be a bad trade. Both strategies return the identical graph, because expression is deterministic.

The winner itself is chosen by the same rule generational uses: the best of the final population, via common::best_index. Here that is also the best individual the run ever held, since the tournament structure means the best is never discarded.

Logging cadence

Logging every event would give a 100,000-row history for a 100,000-event run, which is useless. So steady-state logs the starting population as iteration 0, then one row per population_size events — a "generation equivalent", chosen so a steady-state log is comparable with a generational one. Rows are stamped with the event number, not a row counter. 

log_interval = population_size
history.len() == num_mating_events / population_size + 1
iterations:       0, population_size, 2×population_size, …

The iteration-0 row is what makes a log self-contained: without it there would be no way to see where a run started, and a run shorter than one interval would produce nothing at all.

Trailing events after the last full interval are not logged. Twenty-five events over a population of ten logs rows at 0, 10 and 20 — events 21 to 25 really happened and are reflected in the final outcome, but no row describes them. This falls out of the interval rule; it is not a separate rounding decision.
What exists today. The rows are built correctly and travel out on EvolutionOutcome::history, readable by a Rust caller of Evolver::run. The Python boundary (dispatch::erase, get/src/dispatch.rs:411) converts each row's two fitness columns out of engine orientation and carries the whole log out on the result object, so a config-driven run can read its own convergence log. The ci_95 column and the per-row seed and run index described in Logs & Results are still not fields on GenerationStats. See Status.

A small run, narrated

Population of 6, tournament_size = 4, num_mating_events = 12. Same toy genome as on the generational page: the individual is a number v, fitness is v + 1, lower is better, one mutation adds 100. Starting values [5, 3, 9, 1, 7, 2], so the starting fitnesses are [6, 4, 10, 2, 8, 3].

  1. Score once. All six are expressed and scored — the only full-population scoring the run will do. The graphs are dropped; the fitness vector is kept.
  2. Log row 0 — best 2.0, mean 5.5, std_dev ≈ 2.81. Identical to generation 0 on the generational page, because it is the same starting population.
  3. Event 1 — draw. Four distinct slots come out, say slots 3, 1, 4 and 2, with fitnesses 2, 4, 8 and 10. Sorted best-first the tournament is [3, 1, 4, 2].
  4. Event 1 — breed. Parents are slots 3 and 1 (values 1 and 3). One crossover roll, then a mutation roll per child. Say both mutate: the children become 101 and 103, scoring 102 and 104.
  5. Event 1 — replace. The tournament's worst two are slot 2 (fitness 10) and slot 4 (fitness 8). The children are written into those slots and the fitness array is updated in the same step: slot 2 becomes 102, slot 4 becomes 104. Note both children are worse than what they displaced and are installed anyway — replacement is unconditional. Slot 3, the tournament's best, is untouched. Slots 0 and 5 were never drawn and are not even looked at.
  6. Events 2 to 12 repeat that, each drawing a fresh tournament of four.
  7. Logging. log_interval is 6, so rows land after event 6 and after event 12. With row 0 that is three rows — matching 12 / 6 + 1.
  8. Outcome. best_index finds whichever slot holds the lowest fitness at the end — here still the individual with value 1, which was never eligible for replacement in any tournament it won. Its graph is expressed fresh, and the outcome carries it with best_fitness_engine = 2.0, direction = Minimize, and three history rows.

Costs and when to choose it

PropertySteady-state
Evaluations per event2
Parallelism during scoring two-way, regardless of how many cores you have
Python objective cost one FFI crossing per event — a poor fit for Python fitness
Are old scores ever stale?yes, and permanently so
Elitismautomatic; there is no setting and none is needed
Selection samplingwithout replacement; self-mating is impossible
A single steady-state run cannot use a big machine. It only ever expresses and scores two genomes at a time, so its population-level parallelism is two-way no matter what you set max_cores to. Replicate runs are the only way to fill the cores — the same conclusion the FFI-cost argument reaches from the other direction. See Seeds & Reproducibility for how replicates are seeded.

Choose steady-state when the objective is cheap and native, when you want the diversity that tournament-local replacement preserves, or when you want elitism without having to reason about elite_count. Choose generational when the objective is stochastic and comparisons must be fair, when scoring is expensive and you want it parallel across the whole population, or when the objective is written in Python.
