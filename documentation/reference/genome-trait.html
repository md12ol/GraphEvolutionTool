Source reference

genomes/genome.rs

The interface every genome implements, and the two configuration types that go with the two genomes that exist. Four methods, one associated type, and exactly one hard behavioural promise. For the gentle introduction, read Genomes first — this page is the precise companion to it.

What lives here

Two files, both small. genomes/mod.rs is seven lines of module declarations and re-exports; genomes/genome.rs is 75 lines, of which about half are comments explaining why the bounds are there. Between them they define the contract that sda.rs and edge_edit.rs fulfil, and that a third genome would have to fulfil too.

A genome is a compact, mutable encoding that can be turned into a Graph. It is not itself a graph. The evolutionary algorithm only ever handles genomes — copying them, recombining them, mutating them — and converts each one into a graph at the moment it needs to be scored. That conversion is called expression.

The Genome trait

pub trait Genome: Clone + Send + Sync {
    type Context: Send + Sync;
    fn express(&self, context: &Self::Context) -> Graph;
    fn crossover<R: Rng + ?Sized>(&mut self, other: &mut Self, rng: &mut R);
    fn mutate<R: Rng + ?Sized>(&mut self, rng: &mut R);
    fn print(&self) -> String;
}

There are no defaulted methods. All four are required, and so is the associated type. If the trait compiles for your type, you have written all five things.

The supertraits

pub trait Genome: Clone + Send + Sync
genomes/genome.rs:9

Clone is how the engine copies an individual — there is no copy method anywhere in GET, so an elite carried forward and a child about to be mutated are both just clones. Send + Sync is what allows a whole population to be expressed across rayon worker threads at once.

These look like boilerplate and are not. Removing any one of them stops parallel expression compiling — see The pipeline for the three bounds and why each is load-bearing.

The associated type

type Context: Send + Sync;
genomes/genome.rs:16

Run-level configuration that the genome needs in order to be expressed, but which is not part of the evolved data. It is fixed for the whole run and shared read-only.

The Send + Sync bound exists because express_and_score hands one &Self::Context to every worker at once. Without the bound, parallel expression does not compile. The comment in the source says exactly this, because an implementor who sees the bound undocumented will try to remove it.

The four methods

fn express(&self, context: &Self::Context) -> Graph
genomes/genome.rs:19

Turn this genome into a graph. Note the signature carefully: it takes &self and no random number generator. Expression must be pure and deterministic — the same genome against the same context must always produce the same graph.

The engine depends on that. The generational strategy reads its winning graph out of the vector its last scoring pass already built, while steady-state re-expresses its winner from scratch; both are documented as returning the identical graph, and that claim is only true because expression is deterministic.

It must also not modify the context. EdgeEditGenome clones the base graph before touching it for exactly this reason.

fn crossover<R: Rng + ?Sized>(&mut self, other: &mut Self, rng: &mut R)
genomes/genome.rs:29

Recombine two parents in place. When it returns, self holds one child and other holds the other. Crossover here inherently produces two children, and an engine that kept only one would waste half of every crossover.

The ?Sized in the bound is a small Rust technicality worth decoding: normally a generic type has to have a size known at compile time. Opting out of that lets a caller pass either a concrete random number generator or a trait object like &mut dyn RngCore through the same parameter. The same bound, for the same reason, appears on mutate.

Both existing implementations tolerate parents of unequal size by working over the shorter one, even though nothing in GET ever produces unequal sizes — genome dimensions are fixed for a run. That is defensive, not a feature.

fn mutate<R: Rng + ?Sized>(&mut self, rng: &mut R)
genomes/genome.rs:51

Apply exactly one mutation to this genome, in place. This is the trait's one hard behavioural promise and it has its own section below.

fn print(&self) -> String
genomes/genome.rs:54

A human-readable description of the genome. This is the type-erasure hook: the Python entry point cannot be generic over the genome type, so it records which individual won by calling print and keeping the resulting string. That is the whole reason this method exists — it is not a debugging convenience.

The mutation contract

This is the part of the trait that a new genome is most likely to get wrong, so the source spells it out at length at genomes/genome.rs:31–51. There are five parts.

  1. One call, one mutation. Not "some mutations", not "between one and four" — exactly one atomic change per call.
  2. The engine owns both dice rolls, in one shared helper, common::mutate_child. Roll one is mutation_rate: does this child mutate at all? Roll two is max_mutations: if it does, how many times is mutate called, drawn uniformly from 1..=max_mutations. A genome that rolled its own count internally would make max_mutations silently meaningless for that representation only, and nothing would report the disagreement.
  3. What "one mutation" means belongs to the representation, and the magnitudes are deliberately not equalised. One gene out of 256 is a far smaller perturbation than one transition out of 24. A shared max_mutations buys equal mutation count, not equal strength.
  4. A genome with nothing to mutate leaves itself unchanged rather than panicking — an empty gene list, a zero-state automaton. Both implementations honour this and both have a dedicated test for it.
  5. The rolls happen in a fixed order, rate then count, so a seeded run reproduces exactly.
"Exactly one" is measured as "at most one field changed", not "the RNG was consulted once". A mutation is allowed to redraw a value and land on the value it already had — that is a genuine no-op and is fine. Both implementations' tests assert changes <= 1 rather than == 1, and a new genome's test should do the same.

The reason this is a trait-level contract rather than a per-representation choice is recorded in the source itself: it is "precisely how the two genomes here drifted apart before it was written down". Crossover & mutation has the fuller story, including the one-off change to seeded output that landing the contract caused.

The context types

Each genome declares its own. They are the authority on graph size and edge cap: SdaContext states both directly, EdgeEditContext carries them implicitly inside its base graph.

pub struct EdgeEditContext { pub base_graph: Graph }
genomes/genome.rs:59

The graph an edit script is applied to. Because a Graph already knows its own node count and multiplicity cap, this one field carries everything expression needs. Derives Clone and Debug.

pub struct SdaContext { pub num_nodes: usize, pub init_state: usize, pub max_edge_multiplicity: u32 }
genomes/genome.rs:65

Everything an automaton needs in order to generate a graph from nothing: how many nodes to produce pairs for (genome.rs:66), which state the machine starts in (genome.rs:72), and the edge multiplicity cap (genome.rs:74 — pass 1 for unweighted graphs). Derives Clone, Debug, PartialEq, Eq.

init_state lives here rather than on the genome for a specific reason, stated in the source: mutation and crossover never touch it, so it is fixed run configuration rather than evolved data. Contrast init_char, which is evolved and therefore lives on SdaGenome.

Writing a third genome

Seven things in the genome's own file, six more to register it with the config-driven path. The full checklist with line numbers is on Add a genome; the short version is that you implement the five trait items above plus a random constructor, and then add one arm to the match in dispatch.rs.

Nothing in evolver/common.rs, generational.rs, steady_state.rs, fitness.rs or graph.rs changes. The evolvers are generic over G: Genome, and the objective has already been erased to Box<dyn Fitness> before genome dispatch runs, so genome and objective never multiply into a combinatorial table.

The evolver cannot build genomes, and this is deliberate. Constructors differ per representation and some are fallible — the automaton's dimensions can be rejected, the edit script's weights can be rejected. A generic evolver has no way to call either. So dispatch.rs builds the starting population, where genome-specific knowledge already lives, and hands it in as a ready-made Vec<G>. That is what turns a bad dimension into a startup error naming the field instead of a panic partway through a run.
