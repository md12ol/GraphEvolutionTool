Direction and orientation

Every fitness number in the engine is in one of two forms, and mixing them up is the bug this type exists to prevent:

  • original — what the fitness function returned, in its own units. 28 nodes infected is 28.0, and bigger is better.
  • oriented — the same number after conversion, so that smaller is always better. That 28 becomes -28.0.

The engine only ever compares fitnesses, so it works in oriented values throughout and never asks what the objective was. Logs and results are turned back into originals at the boundary.

#[derive(Clone, Copy, Debug, PartialEq, Eq)] pub enum Direction { Minimize, Maximize, }
fitness.rs:47, variants :49 and :52

Whether an objective wants its value small or large. Minimize is the default and suits an error or a distance; Maximize is for a count you want more of.

pub fn orient(self, value: f64) -> f64
fitness.rs:70

Converts an original into an oriented value. Under Minimize it returns the number unchanged; under Maximize it returns the negation, so the largest original becomes the smallest oriented value.

Negation is its own inverse, so this one function converts both ways — an original in to compare, an oriented value in to report. That is why the whole design comes down to calling it in exactly two places.

Panics on NaN — see below.

An objective never negates its own output. If evaluate returned an already-negated value and declared Maximize, the two could silently disagree — and a run optimising backwards looks exactly like a run that is simply not converging. So the objective states its units and its direction, and the engine does the arithmetic once.

NaN is forbidden, and enforced

One NaN from a maximising objective can silently take over a whole run. Under minimisation NaN sorts beyond +inf and reads as worst, which is safe. But under Maximize the value is negated, and -NaN sorts below -inf — so it becomes the best individual in every tournament it enters, fills the population with whatever genome produced it, and leaves a run that looks converged. Nothing panics and no number looks wrong.

So orient checks for it with assert!, which survives a release build (fitness.rs:71-76) — this is not a debug-only check. The test an_unchecked_negated_nan_would_have_sorted_best (fitness.rs:1110) exists purely to record why the assertion is there rather than trusting the ordering.

Common ways to produce one accidentally: dividing by a count that can be zero, 0.0 / 0.0, and inf - inf.

±inf is allowed and is useful. +inf under Minimize is the sanctioned way to say "this individual is invalid, never select it". Banning it would push people toward a magic large number, which is worse because it stays silently comparable.

The Fitness trait

pub trait Fitness: Send + Sync { fn evaluate(&self, graph: &Graph) -> f64; fn direction(&self) -> Direction { Direction::Minimize } fn evaluate_batch(&self, graphs: &[Graph]) -> Vec<f64> { /* par_iter over evaluate */ } }
fitness.rs:105

An objective over expressed graphs. The Send + Sync bound is what lets the default batch scorer fan out across threads.

fn evaluate(&self, graph: &Graph) -> f64
fitness.rs:108

The only required method. Score one graph and return the original — in the objective's own units and sign, never an oriented value. Must not return NaN.

fn direction(&self) -> Direction
fitness.rs:112

Which way is better. Defaults to Minimize, so an error or distance objective can say nothing at all. Override it if bigger is better — forgetting to is one of the silent failures listed below.

fn evaluate_batch(&self, graphs: &[Graph]) -> Vec<f64>
fitness.rs:131

Score a whole batch, returning one original per graph in the same order. The default runs evaluate on each graph across rayon (fitness.rs:132-135), which suits a simple deterministic Rust objective and nothing else.

The batch is not always a generation. Generational hands over the whole population each cycle; steady-state hands over just the two new children per mating event, and its starting population once. A single graph is a batch of one. Nothing in this file needs to know which.

Two kinds of objective must override evaluate_batch, and the default will not tell you.
  • Any stochastic objective. The default draws a fresh seed per graph, so graphs inside one batch stop being comparable — a graph could rank first for having been handed a milder outbreak. Use EpidemicScorer::mean_batch.
  • Any Python objective. The default takes the Python lock once per graph from inside a thread pool, which deadlocks — see PyFitness.
Implement these; never call them. Only common::express_and_score calls evaluate or evaluate_batch. A direct call from engine code compiles and returns plausible numbers, but hands the engine an original where an oriented value belongs — so under Maximize every comparison runs backwards. It skips the NaN check too. (fitness.rs:94-99)

The boxed objective

impl Fitness for Box<dyn Fitness> { fn evaluate(&self, graph: &Graph) -> f64; fn direction(&self) -> Direction; fn evaluate_batch(&self, graphs: &[Graph]) -> Vec<f64>; }
fitness.rs:167 — methods at :168, :172, :176

"A boxed objective is an objective." The config layer erases its chosen objective to one Box<dyn Fitness> before instantiating anything, so that adding an objective is one match arm rather than one arm per strategy × genome combination. But Evolver::run<F> requires F: Fitness, and a box holding a Fitness is not itself one until this says so.

It has to live in this file — Rust's orphan rule rejects it anywhere else.

Every method is forwarded, including the two that have defaults — and omitting either one compiles. This is the single most dangerous edit in the file:
  • Drop direction and the box reports Minimize whatever it actually holds. Both maximising objectives then run the search backwards, while looking merely unconverged.
  • Drop evaluate_batch and the box falls back to the trait default, which fans out over rayon and calls evaluate per graph. For a Python objective that deadlocks; for an epidemic objective it re-seeds per graph and destroys comparability.
Neither omission produces a compiler error, a panic, or a wrong-looking number. The test a_boxed_objective_forwards_every_method_including_the_defaulted_ones (fitness.rs:640) is the only thing standing between this file and both failures.

EpidemicScorer

Two requirements pull in opposite directions, and a stochastic objective has to satisfy both:

  • Within one batch, every graph must face the same epidemic draws, so that differences in fitness reflect the graph rather than the dice. This is common random numbers.
  • Across batches, the same graph must not keep getting the same epidemic, or the run optimises against one frozen sample of the disease rather than against the disease.

EpidemicScorer is what delivers both. Every SIR objective holds one, and it is the reason none of them calls the simulator directly.

pub struct EpidemicScorer { params: SirSampleParams, run_seed: u64, batches_scored: AtomicU64, }
fitness.rs:200

All three fields are private. The nesting it sits in, widest first:

experiment  = many runs at one set of parameters
  run       = one evolution, one master seed        <-- one scorer covers one run
    batch   = whatever the evolver scores at once
      graph = one candidate network
        epidemic = one outbreak; a graph averages num_epidemics of them

One scorer per run, never shared. The counter is per-run state; two replicate runs sharing a scorer would let thread scheduling decide which run saw which seed, and reproducibility goes with it.

pub fn new(params: SirSampleParams, run_seed: u64) -> Self
fitness.rs:212

Builds a scorer for one run. run_seed is this run's share of the master seed handed to GraphEvolver.run — the [fitness] config block has no seed of its own, deliberately.

pub fn next_batch_seed(&self) -> u64
fitness.rs:260

The seed for the next batch of graphs. Every call returns a different one, because it advances the counter. Call it once per batch, then give that one seed to every graph in the batch.

The derivation is SplitMix64 over (run_seed, counter) — the private mix_seed at fitness.rs:310. It is emphatically not run_seed ^ counter: under xor, run seed n's batch 1 is run seed n+1's batch 0, so two replicates would replay each other's epidemics one batch out of step. The test neighbouring_run_seeds_share_no_batch_seed (fitness.rs:1300) pins that down.

The AtomicU64 is not a concurrency flourish: evaluate only gets &self, so a plain += 1 will not compile, and the obvious single-threaded alternative is not Sync, which the trait requires. Nothing is actually contended.

pub fn mean_batch( &self, graphs: &[Graph], read: impl Fn(&Epidemic) -> f64 + Sync, ) -> Vec<f64>
fitness.rs:280

Scores a whole batch: one seed for every graph, one tick of the counter. This is the only way to score an epidemic objective, and the method that actually delivers common random numbers.

The seed is taken once, before the parallel loop (fitness.rs:283). Then each graph, in parallel, runs simulate_epidemics with that shared seed, applies read to each returned epidemic, and averages (fitness.rs:285-296).

The read closure is what keeps each objective down to a single line — it turns one epidemic into one number. Averaging matters: a single epidemic is noisy enough that selection would chase the dice instead of the graph. The division is safe because simulate_epidemics rejects an empty set.

What that produces across a run, and note that the batch size is not fixed: 

generational   batch 1   seed A   all 200 of the population
               batch 2   seed B   all 200 of the next generation

steady-state   batch 1   seed A   the 200 starting graphs
               batch 2   seed B   the 2 children of one mating event
               batch 3   seed C   the 2 children of the next event
Steady-state pays a known cost here, and it is accepted rather than fixed. Its two children are scored under a newer seed than the population they are compared against, and a graph that drew an easy outbreak keeps that inflated score until something replaces it. Prefer generational when the objective is stochastic and the comparison needs to be fair — generational rescores everyone each generation under one seed, so it is immune.

The three SIR objectives

The epidemic is the expensive part and all three objectives want the same one, so sir_sim returns everything and each objective is a thin reading of it. All three follow an identical shape: hold an EpidemicScorer, and write both entry points as one line over mean_batch.

ObjectiveConfig typeReadsDirection
EpiSpreadepi_spreadtotal ever-infected Maximize
EpiLengthepi_lengthtimesteps to burn out Maximize
EpiProfMatchepi_prof_match RMSE against a target profileMinimize

Each direction is fixed by the objective and is never configurable. One fitness function is always maximised or always minimised — it is a property of what the function computes, not of the run, so a config that could say otherwise would only let it contradict the objective.

EpiProfMatch

pub struct EpiProfMatch { /* private */ } pub fn new( params: SirSampleParams, run_seed: u64, target: Vec<f64>, ) -> Result<Self, &'static str>
fitness.rs:385, constructor :398

Root-mean-square error between the epidemic's profile and a target profile you supply. Minimised — zero is a perfect match.

The only fallible constructor of the three. It rejects an empty target (which would be the divisor of every RMSE, giving NaN) and any non-finite value (fitness.rs:404-408). Config validation already rejects both, so this is a backstop for a Config built in Rust without validation.

This objective's direction comes from the trait default, not an override. There is no fn direction in its impl block (fitness.rs:440-450) — it is Minimize because that is what the trait says when nothing is stated. Correct today, but it means no line in the file asserts the direction of this objective.

How the RMSE is computed

The private rmse method (fitness.rs:425) is the reading. The rule is fixed by the target, not by the epidemic:

  • Iterate 0 .. target.len(), never the epidemic's length.
  • Where the epidemic is shorter, treat its value as 0 — the outbreak had ended, so nobody was newly infected that day.
  • Where the epidemic is longer, the surplus is ignored entirely.
  • Divide by target.len() always, then take the square root.
The scoring is deliberately asymmetric. An epidemic that ends early is penalised for the whole remaining target; one that outlasts the target is not penalised at all. So this objective rewards matching or exceeding the target's tail, not matching it exactly. That is inherited from the C++ (legacy/main.cpp:545-553) for comparability, and it is worth knowing when reading a score. Tests: fitness.rs:986, :1000, :1022.

Worked, against the target [1, 2, 3, 4]:

Epidemic profileCompared asSquared errorsRMSE
[1, 2, 3, 4]1, 2, 3, 40+0+0+0 0.0 — perfect
[1, 2]1, 2, 0, 00+0+9+16 = 25 sqrt(25/4) = 2.5
[1, 2, 3, 4, 9, 9, 0]1, 2, 3, 4 — surplus ignored 0+0+0+00.0

The middle row is the test at fitness.rs:986-996. Note the divisor is always the target length — if it were the overlap, the second row would be sqrt(25/2). Pinned by the_divisor_is_the_target_length_not_the_overlap (fitness.rs:1022).

Worked example across all three

Take the five-node graph from the SIR walkthrough — edges 0–1, 1–2, 2–3, 1–4, rate 1.0, patient zero 0. Its single epidemic is length 4, spread 5, profile [1, 1, 2, 1, 0]. At rate 1.0 every epidemic is identical, so the average over num_epidemics is just that value and the seed is irrelevant.

ObjectiveOriginal (your units)Oriented (engine)Why
EpiSpread5.0-5.0 All five nodes reached. Maximize, so orient negates
EpiLength4.0-4.0 Three transmission steps plus the burnout step. Maximize

The RMSE row shows the asymmetry in miniature: this graph infects two nodes at step 2 where the target wanted one, and none at step 4 where the target wanted one — the early burnout costs exactly as much as the overshoot did. Against the shorter target [1, 1, 2] the score would be 0.0, because the surplus tail is never examined.

PyFitness — a Python callable as an objective

pub struct PyFitness { /* private */ } pub fn new(callable: Py<PyAny>, direction: Direction) -> Self
fitness.rs:500, constructor :507

Wraps a user's Python function and the direction declared alongside it. The config only selects Python ([fitness] type = "python"); the callable itself arrives at runtime through GraphEvolver.set_fitness_function, and so does its direction, because nothing can infer whether a user's function wants its value large or small.

pub fn clone_ref(&self) -> Self
fitness.rs:521

A second handle on the same callable. Replicate runs need one objective instance each, and this is how dispatch produces them. The Python object is shared rather than copied — the reference count is bumped — which is correct: the user's function is stateless as far as the engine is concerned, and it is the scorer state that must not be shared, of which this has none.

The callable takes a whole batch

One call receives the entire batch and returns one float per graph, in the same order. The shape is modelled on pymoo's Problem._evaluate, which this audience already knows: 

def fitness(batch):
    # batch: list[(num_nodes, [(u, v, weight), ...])]
    return [score(n, edges) for (n, edges) in batch]

The edge list each graph arrives as is exactly Graph::get_edge_list's output: each edge once, with u < v. Those tuples are built before the Python lock is taken (fitness.rs:545-548), because that part is plain Rust work and holding the lock across it would block every other Python thread for no reason.

A per-graph callback does not merely run slowly — it deadlocks. Measured 2026-08-07 by deleting the evaluate_batch override and running the batching test. The trait default then fans out over rayon, each worker tries to take the Python lock, and the calling thread is holding that lock while blocking on rayon to finish. The suite hung until it was killed — it did not fail, which is worse, because a hang carries no message saying why. (fitness.rs:477-484)

Two structural rules keep that from happening, and neither is advisory:

  • Python is never called from inside a rayon closure. Expression fans out across threads into a list of graphs first; only then does the single batched call happen.
  • The Rust-heavy part of a run releases the Python lock, and this adapter re-acquires it once per batch. That is the caller's job, at the entry point — run does it.

What happens when a callable misbehaves

Fitness's methods return f64, with no error path, so every violation is a panic — each naming what was expected and which item was at fault (fitness.rs:550-585):

What the callable didMessage containsTest
Raised an exception"the registered Python objective raised: …" fitness.rs:821
Returned the wrong type"must return one float per graph, as a sequence" fitness.rs:834
Returned too few or too many scores"returned 1 scores for a batch of 2" fitness.rs:847
Returned NaN"returned NaN for batch item 1" fitness.rs:862

The NaN check is done here as well as in orient for one reason: orient sees a lone number and cannot say which graph produced it, and a user debugging their own function needs the index (fitness.rs:572-581).

An empty batch never reaches Python. score_batch returns immediately (fitness.rs:539-541), so a user's function does not have to handle a batch of nothing.

Writing your own objective

The full route is on Add an Objective. The part that belongs here is the shape, and the two traps:

  1. Implement Fitness. evaluate is the only required method; add direction if bigger is better.
  2. If it is epidemic-based, build on EpidemicScorer rather than calling the simulator yourself. It owns the seeding, and wrong seeding still gives numbers that look fine. Copy the shape EpiSpread uses: both evaluate and evaluate_batch hand mean_batch a closure saying what to read off one epidemic.
  3. Write the same reading in both entry points. Each objective deliberately writes its reading twice rather than hiding it behind an indirection — the test both_entry_points_use_the_same_reading (fitness.rs:1176) is what catches the two drifting apart. Extend it when you add an objective.
Do not write evaluate as a call to self.evaluate_batch(...). It is the obvious implementation and it is a latent stack overflow: the trait's default evaluate_batch calls evaluate, so any objective that forwards one way without also overriding the other recurses until the stack dies. Route both through an inherent method instead — that is exactly what PyFitness::score_batch (fitness.rs:528-535) and EpidemicScorer::mean_batch are for. A single graph is a batch of one: mean_batch(slice::from_ref(graph))[0].
