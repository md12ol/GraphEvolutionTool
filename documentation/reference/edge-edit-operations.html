Source reference

genomes/edge_edit/operations.rs

The nine edits an edge-edit gene can encode. Every one of them is a silent no-op when its preconditions fail — nothing errors, nothing is retried, and evolution routes around the impossible edits.

The gentle introduction is on Genomes. This page is the precise behaviour: exactly what each operation does, exactly when it does nothing, and the two places where the wording elsewhere and the code do not quite line up.

The enum and its opcodes

Crate-internal — it is reached through a gene's opcode, never named from outside.

pub(super) fn from_opcode(opcode: u8) -> Option<Self>
operations.rs:18

Maps the low four bits of a gene onto an operation. Opcodes 9–15 return None and the gene is skipped entirely — which is how an unknown opcode becomes a no-op rather than a panic.

OpcodeOperationParameters used
0Toggle v1, v2, v3 as direction
1Hop v1 start, v2/v3 neighbour indices
2Addv1, v2
3Deletev1, v2
4Swap v1, v2 vertices; v3, v4 neighbour indices
5LocalToggle v1 start, v2/v3 neighbour indices, v4 as direction
6LocalAdd v1 start, v2/v3 neighbour indices
7LocalDelete v1 start, v2/v3 neighbour indices
8Nullnone
9–15nonegene skipped
This ordering is coupled to the weights table, implicitly and unenforced. The [genome.operation_weights] values are flattened into an array whose order must match the opcode order above. Nothing checks that it does. Reordering either side — or inserting a tenth operation anywhere but the end — silently remaps every weight onto the wrong operation, and the only symptom is a run that explores differently than configured. If you touch either, change both in the same commit and add a test that pins the pairing.

Dispatches to the operation's implementation. The four parameters are already decoded from the gene's payload — see edge_edit.rs for the mixed-radix decoding and its bias on large networks. Note that operations take different numbers of them, so a gene's unused parameters simply do not matter.

The shared guard

fn valid_pair(graph: &Graph, u: usize, v: usize) -> bool
operations.rs:47

u < num_nodes && v < num_nodes && u != v. Every direct operation checks this first, which is why an out-of-range vertex or a self-loop is a no-op rather than an error.

The three direct operations

fn add(graph: &mut Graph, u: usize, v: usize)
operations.rs:64

Adds one edge copy between u and v.

No-op when: the pair is invalid, or the edge is already at the cap — the underlying add saturates rather than wrapping.

fn delete(graph: &mut Graph, u: usize, v: usize)
operations.rs:70

Removes one edge copy. On an unweighted graph that removes the edge.

No-op when: the pair is invalid, or there is no edge to remove.

fn toggle(graph: &mut Graph, u: usize, v: usize, direction: usize)
operations.rs:51

The interesting one. Its behaviour depends on where the current weight sits:

Current weightDoesWhy
0Add Forced — there is nothing to remove.
at the capRemove Forced — there is no room to add.
anything between direction even → remove, odd → add The only case with a genuine choice, and the payload parameter decides it.
On an unweighted graph (cap = 1) the middle case cannot arise, since every weight is either 0 or at the cap. Toggle is then a true toggle and direction is ignored — which is why it reads as absent/present in the common case.

The two-hop walk

fn two_hop_endpoint(graph: &Graph, start: usize, first_neighbor_index: usize, second_neighbor_index: usize) -> Option<(usize, usize)>
operations.rs:76

The shared machinery behind Hop and the three Local* operations. Step from start to one of its neighbours, then to one of that node's neighbours. Returns both the intermediate node and the far endpoint.

Neighbour indices wrap modulo the degree, so an arbitrary payload always names a real neighbour rather than failing.

Returns None — and the operation is a no-op — when:

  • start has no neighbours at all (or is out of range);
  • the intermediate neighbour has degree < 2, so the walk has nowhere to go but back;
  • the far endpoint is start — a walk that returned to where it began.

The three local operations

Each one takes the two-hop walk and then applies its direct counterpart to (start, endpoint). So every no-op condition of the direct operation applies on top of every no-op condition of the walk.

fn local_add(graph, start, first_neighbor_index, second_neighbor_index) fn local_delete(graph, start, first_neighbor_index, second_neighbor_index) fn local_toggle(graph, start, first_neighbor_index, second_neighbor_index, direction)
operations.rs:108, :122, :93

LocalAdd creates a shortcut across a two-hop path — the classic triangle-closing move. LocalDelete removes one. LocalToggle does whichever the current weight and direction call for.

Note LocalToggle is the only operation that uses all four decoded parameters: v4 is its toggle direction.

Hop — move an edge

fn hop(graph: &mut Graph, start, first_neighbor_index, second_neighbor_index)
operations.rs:136

Walk two hops, connect start to the far endpoint, then drop the edge to the intermediate neighbour. The effect is to move one edge copy outward along the path, leaving the total edge count unchanged.

The order matters and is deliberate: the removal only happens if the addition actually took. If the new edge is already at the cap, adding fails, and hop returns before removing anything — so a saturated target leaves the graph completely untouched rather than destroying an edge for nothing.

No-op when: the walk fails, or the new edge is already at the cap.

Swap — a 2-opt rewire

fn swap(graph: &mut Graph, first_vertex, second_vertex, first_neighbor_index, second_neighbor_index)
operations.rs:154

Take two vertices and one neighbour of each. Cut both edges and cross-connect: the first vertex takes the second's neighbour and vice versa. Total edge multiplicity is preserved exactly — this is a pure rewiring, which is what makes it useful for exploring topology without changing density.

It is by far the fussiest operation, and rejects in two stages.

Stage one — before looking up neighbours

Rejected whenBecause
num_nodes < 4 Four distinct vertices are needed and there are not four to have.
Either vertex is out of range, or they are the same vertex—
Either vertex has degree ≤ 2 Removing one of its edges would leave it with no spare.
The two vertices are already adjacent The swap could not yield two disjoint edges.

Stage two — after looking up neighbours

Rejected whenBecause
Any two of the four vertices coincide Checked by sorting the quartet and looking for adjacent duplicates. A collision would make the "swap" meaningless or produce a self-loop.
first_vertex is already joined to second_neighbor One of the two edges the swap would create already exists.
second_vertex is already joined to first_neighbor The other one already exists.
first_neighbor is already joined to second_neighbor See the warning below — this is not one of the created edges.
Two discrepancies worth knowing, both real.
  • The third adjacency check is not a "would-be edge". The design document describes Swap as rejecting when "none of the three would-be edges already exists", but the swap creates only two edges. The check between the two neighbours is an additional rejection whose purpose is not documented anywhere, and it is the one branch here with no test coverage. It makes Swap strictly rarer than the description implies.
  • The degree floor is > 2, and the original implementation used ≥ 2. The design and the code agree with each other; the historical Java version this descends from did not. It matters if you are comparing against archived results, because it makes Swap fire less often on sparse graphs.

Worked example

before:  0—1 (weight 2)   0—4   0—5   2—3   2—4   2—5
swap(first_vertex = 0, second_vertex = 2, both neighbour indices = 0)

  first_neighbor  = a neighbour of 0  ->  1
  second_neighbor = a neighbour of 2  ->  3

  cut   0—1  and  2—3
  add   0—3  and  2—1

after:   0—1 (weight 1)   0—3   2—1   0—4   0—5   2—4   2—5
         total edge multiplicity unchanged

Note the first edge had weight 2 and dropped to 1 rather than vanishing — the cut removes one copy, like every other operation here.

Null

Does nothing, deliberately. It exists so that the operation mix can include "no change" as an outcome; set null = 0.0 in the weights to make every gene do something.

Why silence rather than errors

A gene's payload is an arbitrary integer decoded into vertex indices, so most conceivable edits are invalid on most graphs. If invalid edits errored, expression would need a policy for what to do when one fails — retry, skip, abort — and every one of those choices distorts the search. A no-op is the neutral option: the gene contributes nothing this generation, and selection sorts out whether that was a good use of a gene slot.

The practical consequence for a from-scratch run. Five of the nine operations — Swap, Hop and the three Local* — need existing structure to walk, so on an empty starting graph they all do nothing. Until Add and Toggle have built something, well over half the operation mix is inert. This is self-correcting and is not a bug, but it makes early generations look stalled. See Troubleshooting.
