py_config.rs

The configuration objects you fill in from Python. They mirror config.rs field for field, and their only job is to serialize back to TOML — so the Python route and the file route meet before anything is parsed, and there is exactly one parser and one validator behind both.

What this module is for

You can describe a run two ways: write a config.toml by hand, or build the same description out of typed Python objects. The second route is what most users take, and it is built on a deliberate constraint: 

Python config objects ──serialize──> TOML ──serde──> Config ──validate──> run
                                              hand-written TOML ─┘

Python is a builder for the config format, not a second parser of it. The objects on this page never interpret anything. They render a TOML document, and that document goes through exactly the same Config::from_toml_str and Config::validate a hand-written file goes through. Two things fall out, and both are the point:

  • The Python path cannot accept a configuration the file path would reject. There is no second set of rules to drift.
  • You get provenance for free. config.to_toml() returns the exact document that was parsed — write it beside your results and the run reproduces verbatim.

Why these are a separate mirror

The obvious design would be to put the Python annotations directly on config.rs's own types and skip the duplication. That does not compile, and the reason is worth recording because it looks like a stylistic choice and is not. Measured on pyo3 0.27.2 and serde 1.0.228:

  • pyo3 rejects a unit variant in a complex enum — it wants an empty tuple variant instead. So FitnessConfig::Python would have to become Python().
  • serde then rejects that: a tagged enum cannot use tuple variants. And the tag is exactly what deserializes type = "python" for the file front end.

So annotating the config types directly would break the TOML front end in order to serve the Python one. The mirror also confines every pyo3 annotation to this one file, which matters with two people editing the crate at once.

The cost of a mirror is drift. A field added to config.rs and not here is invisible from Python, silently. Two tests hold the line: one destructures Config exhaustively so a new field fails to compile until the mirror has it (py_config.rs:735), and one scrapes config.rs's own validation calls out of its source text and checks each has a Python attribute path (py_config.rs:990). Neither is a hand-maintained list, because a hand-maintained list is exactly the thing that goes stale.

Constructor signatures

Every default below is the same value config.rs's serde defaults supply, so omitting an argument in Python and omitting the line in TOML give identical runs.

Config(evolution, population_size, network_size, crossover_rate, mutation_rate, selection, genome, fitness, max_edge_multiplicity=1, max_mutations=1)
py_config.rs:323

The whole configuration. Note the argument order: the two defaulted arguments come last, after fitness, which is not the order the fields are documented in. Pass them by keyword and the order stops mattering.

There is no seed argument, and that is deliberate — one master seed is supplied to the run call and everything derives from it. See Seeds & Reproducibility.

All ten fields are readable and writable as attributes (py_config.rs:282).

GenomeConfig.EdgeEdit(gene_length, operation_weights=None) GenomeConfig.Sda(num_states, max_resp_len, init_state=0)
py_config.rs:224

The representation and its dimensions. Leaving operation_weights as None omits the table from the generated document entirely, so all nine weights fall back to 1.0.

There is no num_chars argument on Sda: the alphabet is derived as max_edge_multiplicity + 1, so every character the automaton can emit is a legal edge weight and none is ever clamped away. init_state must be less than num_states — an out-of-range value would panic during expression, so Config::validate rejects it first.

FitnessConfig.EpiSpread(sir) FitnessConfig.EpiLength(sir) FitnessConfig.EpiProfMatch(sir, target_profile) FitnessConfig.Python()
py_config.rs:250

The objective. target_profile is an ordinary Python list of numbers, written into the document like any other value. Python() takes no arguments — you register the callable and its direction separately, with evolver.set_fitness_function(callable, direction).

Python() needs those empty parentheses because pyo3 rejects unit variants in a complex enum. This is the single variant that forced this whole module to exist.

SirParams(infection_rate, num_epidemics, patient_zero=None, min_epidemic_length=3, max_epidemic_retries=5)
py_config.rs:92

The epidemic settings shared by the three SIR objectives. The two retry defaults are the legacy C++ constants, so omitting both reproduces historical behaviour. patient_zero=None means a fresh node is drawn for every epidemic.

Unrelated to fitness::PyFitness, despite both starting with Py: that one adapts a registered Python callable to the fitness trait, this one is configuration.

OperationWeights(toggle=1.0, hop=1.0, add=1.0, delete=1.0, swap=1.0, local_toggle=1.0, local_add=1.0, local_delete=1.0, null=1.0)

Relative probability of each edit operation. Every field defaults to 1.0, giving all nine equal probability; a weight of 0.0 disables its operation outright. See the nine operations for what each one does.

Config.to_toml() -> str
py_config.rs:376

Render this configuration as the TOML document the Rust side parses. This is the provenance record: the generated text is what was run, so writing it beside your results lets you re-run verbatim, and it is also the exact seam GraphEvolver.from_config goes through — the document you inspect is byte-for-byte the one that was parsed.

Raises ValueError if a field is too large for a TOML integer. That gap is real and reachable: population_size=2**63 converts into Rust happily and only fails here, where it is reported by field name rather than wrapping silently to a negative number.

A worked example

The same experiment as the one on the config.rs page:

import get

config = get.Config(
    evolution=get.EvolutionConfig.SteadyState(num_mating_events=100_000),
    population_size=200,
    network_size=100,
    crossover_rate=0.9,
    mutation_rate=0.2,
    selection=get.SelectionConfig.Tournament(tournament_size=6),
    genome=get.GenomeConfig.Sda(num_states=12, max_resp_len=4, init_state=3),
    fitness=get.FitnessConfig.EpiProfMatch(
        sir=get.SirParams(
            infection_rate=0.05,
            num_epidemics=30,
            patient_zero=0,
            min_epidemic_length=3,
            max_epidemic_retries=5,
        ),
        target_profile=[1, 3, 8, 17, 24, 19, 11, 5, 2, 1],
    ),
    max_edge_multiplicity=3,
    max_mutations=2,
)

# The provenance record: this is the document Rust parses, verbatim.
with open("provenance.toml", "w") as f:
    f.write(config.to_toml())

evolver = get.GraphEvolver.from_config(config)   # renders, parses, validates
result = evolver.run(20260812)

With a Python objective instead:

config = get.Config(
    # ... everything else the same ...
    fitness=get.FitnessConfig.Python(),
)
evolver = get.GraphEvolver.from_config(config)

# The config only SELECTS python. The callable and its direction arrive here,
# because nothing can infer whether your function wants a big number or a small one.
evolver.set_fitness_function(
    lambda batch: [score(n, edges) for (n, edges) in batch],
    "maximize",
)
result = evolver.run(1)

Runnable versions of every objective, both genomes and both strategies live in examples/config_builder.py at the repository root, and in Examples.

How a Python object becomes TOML

Each mirror type knows how to write itself into a TOML table. The rules are small but a couple of them are load-bearing:

RuleWhyWhere
Tagged types write their type key first, then their own fields. That is the discriminator the file front end deserializes on. py_config.rs:514, 550, 566, 612
The epidemic block is written into [fitness], not as a sub-table. It is flattened on the Rust side, so a sub-table would not parse. py_config.rs:470
An unset patient_zero is omitted entirely, never written as a null or a sentinel. A null would not parse, and a sentinel would pin patient zero to a node the user never chose. py_config.rs:490
Unset operation_weights are left out, so serde's defaults supply all nine. Writing them out would work but would put nine lines of noise in every provenance document. py_config.rs:580
Every whole number goes through a checked conversion to a TOML integer. TOML integers are 64-bit signed; wrapping to a negative number would be a silently wrong config. py_config.rs:454

Error messages point at your Python, not at a document

Config::validate names the offending field as it appears in the TOML. That is the right answer for someone who wrote a file and a poor one here: a user who wrote SirParams(num_epidemics=0) and is told num_epidemics has to work out which of the objects they assembled owns it. So validation failures are rewritten on the way out.

pub fn config_error_to_py(error: &ConfigError) -> PyErr
py_config.rs:437

Turns a config error into a Python ValueError, replacing the TOML field name with the attribute path that produced it wherever one can be identified. The constraint text itself is carried through unchanged.

Anything with no Python equivalent — a parse failure, an I/O error — passes through with its original wording, which is already the useful one.

Gotchas

  • One check exists on the file route and not here. Supplying a target_profile under an objective that is not epi_prof_match is a hard error in a TOML file. From Python the mistake cannot be made in the first place — the field only exists on FitnessConfig.EpiProfMatch — so there is nothing to reject. The two front ends are equivalent in what they accept; this is the one place their error surfaces differ.
  • The document is re-parsed, every time. Building an evolver from Python serializes to text and parses it back. That is the design — one parser, one validator — not an oversight, and it costs nothing measurable against a run.
  • Very large integers fail at to_toml(), not at construction. population_size=2**63 is accepted by the constructor and rejected when the document is rendered.
  • Attribute writability on the four enum classes is not something this source settles. Config and SirParams are explicitly readable and writable field by field. EvolutionConfig, SelectionConfig, GenomeConfig and FitnessConfig are pyo3 complex enums whose variant fields carry no explicit accessor annotation, and the error-path table above assumes they are at least readable. Treat them as read-only and rebuild the variant rather than mutating it in place, unless and until someone verifies otherwise against pyo3 0.27.
  • A failure to parse the generated document is reported as a GET bug, not yours. If the mirror ever emits something the parser rejects, the exception says so and prints the whole document for a bug report — see lib.rs.
